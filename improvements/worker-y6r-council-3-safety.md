## 1. Measurement validity

### 1a. A retry WITHOUT the optics profile applied would NOT answer I11 as designed

I11 (todolist 2.2.3) asks: does the pill reproduce under nested Hyprland with hyprglass, testing the 20/11 idle-pill flicker hypothesis (animated backdrop, LIQUID mode). The designed measurement condition is the G11 candidate profile applied: blur 0.15, refraction 0.55 copied from upstream, contour mask on the computer-use-indicator layer (optics.lua, F3). A run without the profile answers a different, weaker question: does the pill flicker under hyprglass DEFAULTS (upstream default preset, no contour layer registration for the pill namespace).

What a no-profile run COULD prove:

- A REPRODUCED verdict under defaults would prove flicker is possible under some glass configuration. It would be a real signal, but it would not show the flicker happens under the deployed candidate, and it could be an artifact of the default mask path rather than the contour path the pill actually uses when profiled.
- A NOT-reproduced verdict under defaults would prove only that the defaults do not flicker in the nest. That is a narrow negative about an unshipped configuration.

What a no-profile run could NOT prove:

- It could NOT exonerate the G11 candidate. The candidate differs from defaults in the exact parameters that decide the rendering: blur 0.15 vs the default, the refraction path, and above all the contour mask registration on the pill namespace (F9). A defaults-negative is the dangerous false negative: it would be reported as "NOT reproduced in the nest" while the designed question remains unanswered.
- It could NOT reproduce the 20/11 incident conditions in any form, since the incident ran under a live-applied profile, not defaults.
- It could NOT be rescued by the liquid gate or the status check, because both pass without the profile (F6, F7). A run that passes the liquid gate and prints NOT reproduced without the profile would look like a clean answer and would be a wrong one.

Note on the as-is runner: as written, a no-profile retry CANNOT silently produce such a verdict, because U6 fails the run first (F5). The measurement-validity hazard is therefore conditional: it bites only if U6 is bypassed, weakened, or replaced without a positive gate. The AMEND in section 4 closes that conditional. As-is, the retry fails at U6 with no measurement at all (deterministic: count=0 observed twice, F2), which wastes the window but produces no wrong verdict.

### 1b. The U6 hook-marker gate: right as a negative fail-fast, wrong as a positive assertion

The U6 gate UNDER-constrains as a profile-applied assertion. It is a negative-exclusion test (absence of a failure marker), not a positive test (presence of a success marker). It would PASS each of these profile-not-applied runs:

- (i) The hook never runs at all. If the dofile of nested-visuals-hook.lua fails or the config evaluation aborts before line 18, no marker is printed and the gate passes. Nothing in the runner verifies the hook itself executed.
- (ii) The hook runs, sees the plugin, dofiles optics.lua, but optics.lua silently skips. optics.lua is guarded by `if hl.plugin.hyprglass then`; if the plugin object is not yet exposed at that instant even though get_loaded_plugins lists it, the whole file is a no-op with no marker and no error. The gate cannot distinguish this from a successful application.
- (iii) The dofile throws. A Lua error in optics.lua would surface as a config error, not as the hook marker. The runner never checks `hyprctl configerrors` before the pill, so a throwing optics.lua passes U6.
- (iv) The profile is applied and then lost. The gate is a one-time log grep before the liquid gate; nothing re-checks between the gate and the pill arms, and the log is history, not state: a later config reset would not erase the marker's absence. In the current runner there is no re-parse between the gate and the arms (verified by reading lines 305-330: liquid gate, renderer lines, mpv, control frames, pill start, no reload or eval), so this path is hypothetical today, but the gate as designed cannot detect it. Any future edit that inserts a config re-parse between the gate and the arms would silently open this hole.

The U6 gate does NOT over-constrain the current runner. When the marker appears, the profile genuinely was not applied (the hook is the only apply path in the nest, F3), and no later step in the current runner applies it (the liquid gate only reads status, F6). Failing the run there is correct fail-fast behavior, not an over-strict false failure. There is also no stale-marker false-fail: $LOG is truncated at nest launch (`> "$LOG"`, runner line 193) and $NEST_LOG lives in a freshly cleaned RUN_DIR (rm -rf of $RUN_DIR/hypr before launch), so a marker in either file belongs to this run. The echo on line 305 ("hook marker absent, profile applied") is the defect: it upgrades "no failure marker seen" into "profile applied" without evidence. The fail branch is right; the pass message is wrong.

## 2. Safety of the fix direction (runner-side profile re-apply after load)

### 2a. What could go wrong for the LIVE session

- (a) Wrong-target reload. This is the single most dangerous failure mode. The launcher shell exports XDG_RUNTIME_DIR=$RUN_DIR and WAYLAND_DISPLAY=/run/user/1000/wayland-1 (the absolute LIVE socket path) at nest launch, with HYPRLAND_INSTANCE_SIGNATURE unset (runner lines 183-185). A BARE `hyprctl reload` executed in the launcher shell therefore addresses the LIVE compositor, not the nest. A live reload re-executes hyprland.lua, which dofiles visuals-login.lua (line 54). That file, with glass not loaded live, registers visuals.py on hyprland.start. Whether hyprland.start fires on a reload is UNVERIFIED in the evidence, but the consequence if it does (or at the next login) is that visuals.py runs the normal activation path (`scripts/visuals.py` -> `_activate` -> `hyprctl plugin load` plus reload), loading hyprglass into the LIVE session: exactly the outcome the nested test exists to avoid. Worst case, a plugin fault then crashes live Hyprland PID 1515 with unsaved work. Mitigation is absolute: the reload goes through nest() only, with explicit nest XDG_RUNTIME_DIR, WAYLAND_DISPLAY=$NEST_DISPLAY, and HYPRLAND_INSTANCE_SIGNATURE=$SIG, and no bare `hyprctl reload` appears anywhere in the fix.
- (b) Config mix-up. The fix touches files under /tmp/y6-nested/conf. If instead it edits the LIVE optics file (native/hyprglass-local-optics.lua, blur 0.0) or the live visuals-login.lua, or points the nested conf at the live optics path, two harms follow: the nest measures the wrong profile (blur 0.0 live file instead of the 0.15 candidate), and live behavior changes at the next login or reload. Mitigation: nest paths only; md5-verify the nest optics.lua (b011ea91c3b831651f55fdd096d54c46) before the run; never write to ~/.config/hypr or ~/computer-use-wayland/native.
- (c) Profile leak into live. The live chain contains guarded hyprglass API refs (visuals-login.lua gates the live optics file on glass_version == "1.1.1-cu.1"; the live optics file is guarded by `if hl.plugin.hyprglass then`). These are inert while the plugin is not loaded (F11), and the reload fix does not load anything live. The leak vector is (a) above, or a live config edit, both closed by the preconditions in section 3. A nested reload cannot leak the profile into live by itself: the nest is a separate process with its own display, socket dir, and config copy (Y6e council 3 runtime section 4).
- (d) Reload re-executes the nest load line. On a nested reload the whole conf re-runs, including line 16 `hl.plugin.load(...)`. What that does to an already-loaded copy is UNVERIFIED (F13). Bounded blast radius: any harm lands on the nest only (a duplicate-paused entry, or nest death), never on live. The load-only trial (AMEND item 4) must prove exactly one active hyprglass after reload before any pill run.
- (e) Failed reload leaves defaults. A reload that fails its syntax check emits config.reloaded WITHOUT resetting config values (diff line 6822), so the nest keeps defaults and the positive marker never appears. This is a measurement hazard, not a live hazard, and G1/G4 catch it (fail, no pill).
- (f) Shared-GPU stall. A GL fault in the nest could stall the shared GPU (accepted residual from Y6e redteam D5; killing the nest is the recovery). A reload does not change this residual.
- (g) Skip-var bypass. If HYPRGLASS_SKIP_VERSION_CHECK were set in the ambient env at nest launch, LoadGuard's version gate would be bypassed (Y6e redteam D4). The load test already asserts env empty; the fix must preserve that assertion. A reload inherits the nest process env, not the launcher shell env, so the reload itself introduces no new skip-var path.
