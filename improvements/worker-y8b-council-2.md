## Q1: Is the shell-quoting mechanism proven as the root cause of both A1 and A2? GO

The mechanism is proven. The evidence chain, each link checked against a primary source:

1. Both executors ran the brief's exact diagnose JS. Brief A step 3 and brief A2 step 3 (worker-y8-executor-a-brief.md line 17, worker-y8-executor-a2-brief.md line 17) mandate the exact JSON containing `document.querySelector('#contacts-count')` with single quotes. Both event streams show the executor issuing exactly that JSON to step.sh single-quoted: events-a.jsonl item_10 and item_12, events-a2.jsonl item_12 and item_13. A2's command matches the trap shape exactly (single-quoted JSON, single quotes around #contacts-count inside it), as the task asked me to verify.
2. Both failed identically and immediately: A1 diagnose eval HTTP 500 in 2 ms, retry HTTP 500 in 4 ms; A2 diagnose eval HTTP 500 in 3 ms, retry HTTP 500 in 3 ms (execution log 19:19:10 and 19:29:45; out.log lines 7-8 for A1, lines 20-21 for A2). No task step ran in either attempt. The 2-4 ms timing is an immediate SyntaxError, not a timeout and not a dead driver.
3. The driver stack was alive at the time. The coordinator's design-required liveness checks at 19:22:40 (driver PID 274644 alive, geckodriver PID 274657 alive, port 4451 listening) rule out driver death, and the coordinator's own diagnosis on A1's tab at 19:23:17 returned the full VISIBLE snapshot with countText "6" (out.log lines 9-11). A dead driver cannot do that.
4. The byte mechanics are confirmed, not assumed. The shell test /tmp/quotetest.sh (this council, VM) passes the exact JSON shape through a plain bash single-quoted argument and prints what step.sh would receive as $1: `{"cmd":"eval","js":"return (function(){var cc=document.querySelector(#contacts-count);return 1;})()"}`. The single quotes around #contacts-count are stripped by the shell, the rest of the JSON survives intact, and it still parses as JSON (verified with json.loads). So the driver receives valid JSON carrying broken JS, forwards it, and Marionette answers HTTP 500. That is exactly the observed symptom.
5. The controlled A/B repro on A2's own live tab closes the loop. /tmp/e1/repro-quote.sh case A (executor's exact quoting, shortened JS) returns HTTP 500 in 3 ms; case B (identical JS, double quotes for the selector) returns "6" in 2 ms. Out.log lines 22-23 show these two results in order, on the same tab, between A2's failures and the cleanup close/delete. Same tab, same session, same driver, same minute: only the quoting differs, only the quoting changes the outcome. A2's tab was therefore healthy and the quoting was the cause.
6. The pre-flight success is explained, not contradictory. preflight.py calls step.sh via subprocess list argv (preflight.py, step function), so no shell ever sees its single quotes. The executors and the coordinator used the shell path. The instrument worked on the argv path and broke on the shell path because the two paths were never the same code path. The coordinator's own diagnosis succeeded because it used double quotes.
7. A2's pipeline difference is not a confound. A2 piped step.sh through sed and tee (`set -o pipefail; ... | sed ... | tee -a`), A1 did not, and both failed identically. The pipeline cannot be the cause.

What would falsify it (none of these obtained): the double-quoted repro returning HTTP 500 on the same tab; the full fixed diagnose JS returning HTTP 500 through the shell path; a quoteless eval (for example `return window.__agyVerify()`) returning HTTP 500 on the same tab at the same time, which would show a tab-wide or driver-wide failure instead; or the driver log showing the JS arriving with its quotes intact and still failing, which would point at Marionette or the JS itself rather than the shell. The first falsifier was directly tested and failed to falsify: the double-quoted repro returned "6".

Two honest gaps, neither of which breaks the verdict: (a) the repro used a shortened JS containing only the querySelector fragment, not the full diagnose JS. The full diagnose JS contains exactly one single-quoted literal (`'#contacts-count'`), so the shortened repro isolates the only suspect token, but the full-JS live proof is still owed before A3 (see Q4 item 1). (b) I did not resolve codex's bash -lc escaping layers byte-for-byte from the event stream alone (the `\'` sequences in the recorded command). That layer is not needed for the mechanism: the plain-bash repro isolates the shell layer and reproduces the exact failure, and the coordinator's double-quote success on the same tab rules out everything downstream of the shell.

## Q2: Is the v2.2 fix correct and complete? AMEND

The direction is correct: fix the instrument once, in the frozen files, with proof. Runtime conversion by the B executor is the wrong call. But the fix as specified is incomplete in three ways, and one of them would break the plan if done naively.

### Q2a: The fix must specify the exact byte form, or it will produce invalid JSON

"Single to double quotes for selectors" is not a complete specification. The JSON the executor types is single-quoted at the shell level, and a literal `"` inside a JSON string value must be backslash-escaped, or the JSON is invalid. The correct typed form is `\"#contacts-count\"` in the JSON text, exactly as repro-quote.sh case B shows it. A brief that shows bare `"#contacts-count"` inside the JSON (without the backslash) hands the executor invalid JSON: json.loads fails, the driver never gets a command, and the failure looks like a new instrument bug. Every amended brief, the reference, and the plan conversion must use the `\"` form in the JSON source text, and the verification must assert it (see Q4 item 3).

### Q2b: A naive single-to-double conversion of the plan BREAKS two commands

This council counted every single quote in the plan file (programmatic census, laptop, md5 a7b5646b2bf081386bb7bcea0563ad5a):

- Total single-quote characters: 160.
- Inside `"js"` values: 158, forming 79 single-quoted JS string literals.
- Outside JSON commands: 2, both in the line-3 usage example `/tmp/e1/step.sh '<json>'`. Those are the shell usage pattern, correct as written, and must NOT be converted.
- JSON commands total: 64. JS-bearing commands: 26 (19 eval, 7 click_js). Of those, 24 contain single quotes; the 2 quoteless ones are the localStorage.clear eval and the `return window.__agyVerify()` eval.
- No single quotes exist in any `text`, `css`, `url`, `el`, or expected-result field. The `find`, `text`, `value`, `type`, and `click` commands are shell-safe as written.
- Correction to the record: the log and the task state "all 21 of its evals". The census says 19 eval + 7 click_js = 26 JS-bearing commands, 24 carrying the trap. Use 26, not 21.

Of the 79 JS literals, 77 convert cleanly (selectors, `'change'`, `'input'`, `'Engineering'`, `'all'`, `'active'`, `'favorite'`, `''`, `'Spam Bot'`). Two do not: the Frank notes reads on plan steps 21 and 55 (commands 25 and 74 in the census) contain the literal `'.meta-line[style*="italic"]'`, a single-quoted JS string that already contains double quotes. Converting its outer quotes to `"` yields the JS `".meta-line[style*="italic"]"`, which is a SyntaxError (the string ends at the second `"`), and yields invalid JSON if the inner quotes are left unescaped. A blanket sed `s/'/"/g` breaks exactly these two commands, which are final-verification-adjacent reads (step 55 is a fixed final read). The correct conversion is JSON-aware: parse each command with json.loads, rewrite the string literals in the decoded JS (inner `"` becomes `\"` in JS), re-serialize with json.dumps so the escaping is mechanical, and diff. The diff proof must call out the two italic lines explicitly, because they change by more than bare quote characters. Every converted command must then pass json.loads and a JS syntax check (see Q4 item 3). "Only quote characters change" is false for those two lines and must not be claimed.

### Q2c: The B executor must not convert at runtime

Converting the plan once, mechanically, with diff proof and a re-freeze is the right call. Runtime conversion by the B executor is wrong for four reasons: it violates the B brief's own rule ("execute ONLY that plan... do not fix the plan"); it puts 26 conversions under executor discretion and time pressure, with no diff proof and no audit trail; the executor would have to perform the conversion through the same quoting trap it is trying to avoid, so a slip reproduces the failure it was meant to prevent; and a mis-converted step would be indistinguishable from a plan defect or an executor error in the judge's reading. The plan is the frozen deliberated artifact; fix it in the open, once, with proof.

### Q2d: Remaining single-quote traps, swept

- Driver reference click_js example: `{"cmd": "click_js", "js": "document.querySelector('...')"}` (driver reference, commands line) carries the trap in the reference itself and must be fixed to the `\"...\"` form. The reference also gives no quoting guidance anywhere; the v2.2 quoting rule must sit next to the eval line and the command list, not buried at the end.
- Briefs A, A2, B diagnose JS: all three carry the trap (brief A line 17, brief A2 line 17, brief B step 4). The A2 brief is historical and needs no live fix, but the A base brief, the B brief, and the NEW A3 brief must all carry the fixed form.
- preflight.py: DIAGNOSE_JS contains `'#contacts-count'` and `' '` (transition join); REMOVE_TZ_JS contains `'tz-hidden'` and `'--zen-logo-path'`. Both are passed via subprocess argv, so both are safe today. Converting them to double quotes is harmless uniformity and removes a footgun for anyone who later copies that JS into a shell command, but it is defense in depth, not a fix for a live failure. If converted, it must be re-verified by a live pre-flight run (Q4 item 7), not assumed safe.
- The A executor's own JS is the residual risk. A writes its own evals for 28 steps, and the fixture it reads uses single-quoted JS idioms throughout (the fixture has 78 single quotes; it uses getElementById 39 times and no querySelector, so no fixture snippet is directly copy-pasteable into a trap, but the executor's natural JS style is single-quoted selectors). The quoting rule in the reference is the only guard. Mitigation is layered: the rule must be prominent and show the correct `\"` form with the HTTP 500 symptom; the fixed diagnose is the executor's first step, so a non-compliant executor fails the gate before any task step, exactly as A1/A2 did; and the coordinator must audit A3's event stream for `'` bytes inside js values after the run (Q4 item 8). After the fix, a quoting slip by the executor is an executor error, not an instrument defect, and two consecutive such 500s are DRIVER DEAD per the brief, not a void.
- Spec values the A executor types contain no apostrophes. The spec has 5 single quotes, all possessives in prose ("Bob Martin's", "David Kim's", "Spam Bot's"). No typed value (Frank Sinatra, +1-555-9999, Vocal Architect, Engineering) contains one. The `type` commands in the plan likewise contain none.
- Plan copies: the repo copy improvements/worker-x-e1-plan-test-05.md has md5 a7b5646b2bf081386bb7bcea0563ad5a, identical to /tmp/e1/plan-test-05.md. Both copies must be converted identically and the new md5 frozen in the design. Converting one and not the other would recreate the drift the design forbids.

## Q3: Are A1/A2 void as instrument artifacts with the retry budget reset and the next A start labelled A3, or is arm A exhausted at 2 starts? GO, with conditions

Void A1/A2 as instrument artifacts, reset the retry budget, label the next A start A3. Conditions: (1) the void is recorded as an explicit v2.2 design amendment with the bounded test below, not as a silent relabel; (2) A1/A2 stay in the log and in every table as VOID (instrument), never deleted or replaced; (3) the replication-pair naming collision is fixed in v2.2 (see below); (4) the voided starts and the fix are disclosed in the final verdict, and the final judge decides the clean-win question with that disclosure in front of it.

Reasons for voiding:

- Zero task steps were attempted in either run. The failure is in the coordinator's own instrument (the brief's mandated exact JS plus a driver reference with no quoting guidance), not in the executor, the task, or the browser. The executors followed the brief exactly; the brief's exact JS was unexecutable through the only permitted invocation path. This is a broken stopwatch, not a slow runner.
- The design's post-start rule was written for genuine run events (crash, DRIVER DEAD, mid-run hidden body), which presuppose a runnable instrument. It does not cover an instrument that was provably broken before step 1 and failed identically on both attempts for the same reason. Applying it here would record two executor FAILs for executors that did nothing wrong and measured nothing, which corrupts the comparison more than voiding does.
- Precedent inside this same run supports it: the 18:55:40 pre-flight failure (the missing `return` bug) consumed no retry budget in the v2.1 re-freeze, because no classification was made and no measurement existed. A1/A2 are the same category one step later: the diagnose gate never returned a value, so no measurement exists.
- Without a reset, arm A would have zero valid observations while arm B runs once, which is the outcome the design forbids in plain words: "Never compare one measured arm against nothing."

Reasons the letter of the design points the other way, and why they do not win: the design says max 2 starts per arm, post-start first run IS the result, and a second crash ends the arm as BLOCKED. A1/A2 were post-start (new_session and new_tab succeeded). But the design also says a re-run is a second observation "reported alongside A1/B1, never a replacement", which assumes the first observation measured something. A1/A2 measured nothing. The amendment is explicit and versioned (v2.2), which is exactly the mechanism the design provides for post-freeze change ("Any change after this freeze requires a new version number and a re-freeze note, never a silent edit").

The precedent hazard is real and must be bounded, not wished away. Voiding two failed attempts could let a coordinator erase any inconvenient result. The bound is a four-part test, written into v2.2, and a void is legitimate ONLY when all four hold: (i) the failure is proven to be an instrument defect that made the task step impossible before any task step was attempted; (ii) the proof is independent of the outcome, a controlled repro, not the executor's say-so; (iii) the defect is fixed and the fix is proven live through the same path that failed; (iv) the voided attempts stay in the record with their labels. All four hold here: zero task steps, the A/B repro on A2's own tab, the fix plus the Q4 live proof, and A1/A2 retained as VOID in the log. Any future void that fails any part of the test is not a void, it is a FAIL.

Naming collision: the design's replication trigger calls the second pair "B2, A2", but A2 is now used (and voided). v2.2 must rename the replication pair explicitly. I recommend B2/A3 if the trigger fires after A3 and B1, with a note that A3 is both the post-fix first observation and, if replication triggers, the second-pair A run. Alternatively rename replication runs R1/R2. Either is fine; leaving the collision in the text is not.

Clean-win question: the design says if either arm needed an infra retry or a recovery-ladder intervention, no clean win or loss is claimed. A1/A2 voiding is an instrument fix before any measurement, not an intervention during a measured run, so I do not hold that the clause auto-triggers. But A3 still runs under the shadow of two voided starts and a mid-experiment fix, and that history must be disclosed in the final verdict. The final judge, not this council, decides whether any win is clean, with the disclosure in front of it.

The A3 brief must be a new file (worker-y8-executor-a3-brief.md), derived from the fixed A brief, with report file run-a3-report.md and an explicit ban on A1 and A2 artifacts (run-a-report.md, run-a2-report.md, events-a.jsonl, events-a2.jsonl, out.log). A3 is a fresh codex process that must not see the previous attempts.
