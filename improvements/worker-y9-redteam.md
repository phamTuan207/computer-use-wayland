## Attack 2 (BLOCK): the claimed Council 3 preflight fixes are absent from the copied code

The plan section 3 says "Preflight (Council 3 F1-F9 all applied)". The working tree copy of run_agyq2.py still has every one of the blocking defects, proven by line:

- C3-F1, lock type: run_agyq2.py line 1189 requires `parts[1] != "POSIX"`, so a flock(2) hold (type FLOCK) is skipped. Council 3 proved live that the POSIX-only filter returns holders [] under a real flock hold. Consequence: preflight raises "no flock holder" on every correctly launched run, including Y9's own documented launch. The plan's claim that the check "accepts POSIX, FLOCK, OFDLCK" is false for the code it copies.
- C3-F3, ppid None kills: run_agyq2.py lines 1152-1154 set ppid None when stat is unreadable, lines 1155-1156 set parent_alive False, and lines 1164-1167 fall through to SIGTERM then SIGKILL. The plan claims ppid None "REFUSES instead of killing". False. In the live slot this can kill another runner's live geckodriver (see attack 4).
- C3-F7, stat parsing and ancestors: run_agyq2.py lines 1152 and 1201 both parse ppid with `.split()[3]`, not after the last ')'. The ancestor set at lines 1197-1204 starts from os.getpid() but immediately replaces it with its parent, so os.getpid() is never in the set. Both halves of the plan's C3-F7 claim are false.
- C3-F8, garbage PID files: run_agyq2.py lines 1140-1146 do `continue` silently on an unreadable PID file. Nothing is unlinked and nothing is logged. The plan's claim is false.
- C3-F9, Hyprland safety gate and idle log: preflight in run_agyq2.py (lines 1097-1213) contains no hyprctl call at all and logs nothing about idle time not being independently verified. The plan's claim of a "labeled SAFETY gate with 10 s timeout" and an idle log line is false.
- Base instability: run_live.py and run_agyq2.py are currently dirty in the working tree (uncommitted Y4d council revision), and the plan contains no md5 values anywhere despite claiming "md5 recorded". Y9 would be copying a moving base with no frozen hash.
- Required fix: apply C3-F1, F2, F3, F4, F5, F6, F7, F8, F9 in the actual files Y9 ships, re-prove F1 with a live flock hold as Council 3 did, and record the md5 of every shipped file in the plan before launch. Do not claim a fix is applied until it is in the shipped bytes.

## Attack 3 (BLOCK): the claimed Council 2 ladder fixes are absent from the copied code

The plan section 3 lists C2-F1 through F9 as applied. The working tree copy of run_agyq2.py still has them, proven by line:

- C2-F1, flag on verified removal: run_agyq2.py lines 251-253 set `r.details["tz_hidden_removed"] = True` immediately after the removal eval, BEFORE the post-remove diagnose at lines 258-261. The post-remove snapshot is never checked for class absence. A no-op eval (extension already removed the class) still flags the test.
- C2-O1, logo property: the removal eval at lines 251-252 clears only the tz-hidden class, not the --zen-logo-path inline property that removeLoadingScreen also clears. The plan claims the eval "also clears the --zen-logo-path inline property". False.
- C2-F2, bootstrap intervention invisible: bootstrap_tab (run_agyq2.py lines 1039-1095) runs ensure_visible on a throwaway Runner("bootstrap") and discards it, and main lines 1230-1234 return 2 with no JSON at all on bootstrap failure. There is no top-level bootstrap_intervention field anywhere in the file (grep finds none). The plan's claim is false.
- C2-F3, headline folds flagged passes: main line 1287 counts `passed` as all passing tests including flagged, and line 1312 returns 0 when `passed == len(results)`. The plan's own threshold (exit 0 iff clean plus flagged == 10) is contradicted by the copied exit test. The session-creation failure path (lines 1248-1265) appends r.summary() with no "flagged" key.
- C2-F4, abort counter: infra_blocked is only touched inside the except branch (lines 1267-1275). A passing test never resets it, and the session-creation-failure `continue` path never resets it. Sequence INFRA-fail, PASS, INFRA-fail aborts a healthy run. The plan's claim that the counter "resets to 0 on any pass and on the session-creation-failure continue path" is false, and its claim of startswith("INFRA:") matching is false: the code uses `"INFRA:" in str(exc)`, a substring test. The plan also lists session-creation failure as INFRA-blocked in section 2, but the copied main counts it under a separate wd_failures counter, not infra_blocked.
- C2-F5, ladder budget: ensure_visible (lines 240-274) has no deadline, no elapsed-time logging, and no 8 s enforcement. The poll is 2.0 s plus rebootstrap, which Council 2 measured at about 6x over budget in the worst case. The plan's claim is false.
- C2-F6, no handle scanning: bootstrap_tab loops `for h in d.handles()` at lines 1055 and 1069, switching to each handle to read its URL, and rebootstrap_tab does the same at line 193. The plan claims the runner "keeps a registry of known test-tab handles and NEVER switches to an unregistered handle" and that "pre-existing fixture tabs from earlier probes are NOT reused". The copied code does the exact opposite: it scans every handle including user tabs and prefers reusing a fixture tab.
- C2-F7, guarded diagnose: diagnose_body is called unguarded inside both scan loops (rebootstrap_tab line 200, bootstrap_tab lines 1060 and 1074). A diagnose raise aborts the scan instead of skipping the tab.
- C2-F9, INFRA classification: rebootstrap_tab line 219 raises a bare RuntimeError ("rebootstrap: no visible test tab after 3 attempts") with no INFRA prefix, and the removal eval at lines 251-252 is unwrapped, so a raise there is a bare error, not INFRA. The plan's claim is false for both paths.
- C2-F8, second half unhandled: in rebootstrap_tab lines 205-211, a new tab is removed from opened_tabs and then diagnose_body is called unguarded. If diagnose raises, that tab is in neither opened_tabs nor any registry: leaked and untracked.
- Required fix: implement every C2 fix in the shipped runner and re-verify each against the cited line numbers. In particular: set the flag only after the post-remove snapshot proves the class is gone, clear --zen-logo-path too, surface bootstrap_intervention on all paths including bootstrap failure, exit 0 only on clean plus flagged == total, add "flagged": False to the session-failure summary, reset infra_blocked on pass and on session-failure continue, enforce a real 8 s ladder deadline with elapsed logging, replace handle scanning with a registry of handles the runner created, guard every diagnose call in a scan loop, and raise INFRA-prefixed errors from rebootstrap and removal-eval failures.

## Attack 4 (BLOCK): the slot-polling marker is ambiguous and the race is real

- Evidence: the plan section 5 defines Y8's completion marker as "a commit on todolist-push recording Y8's E1 execution completion (its final report in improvements/worker-y8-e1-execution-log.md or a completion commit message)". That file already exists and is 16101 bytes of prep log, whose last timeline entry (18:36) says "execution waits for Y4d". Mere existence of the file, or any commit touching it, cannot signal completion. No exact commit-message pattern, no exact log line, and no laptop-side check (Y8 geckodriver gone, Y8 server stopped, lock free) is specified.
- The marker also has no polling mechanism or timeout: "poll todolist-push every few minutes" names no process that polls (Y9 is a subagent session, not a cron), and no deadline if Y8 never completes. The flock -w 1800 in the launch command then waits up to 30 minutes for a lock held by a live Y8, which contradicts the poll-first design and turns a slot violation into a 30 minute silent wait followed by failure.
- The race matters because of attack 2: if Y9 launches while Y8 is still tearing down, preflight's ppid-None kill path (run_agyq2.py lines 1152-1167) can SIGTERM then SIGKILL a live driver whose parentage was never verified.
- Required fix: define the marker exactly (commit message regex plus a specific new log line in the Y8 execution log, for example an "E1 execution complete" entry with both arm results), and add laptop-side pre-launch checks (no foreign geckodriver, Y8 ports 4451 and 8767 free, lock holder is this run's flock only). Replace flock -w 1800 with a short wait (or 0) once the marker is confirmed, so a held lock fails fast and loud instead of waiting silently. Name the polling process and its stop condition.

## Attack 5 (BLOCK): the shared-tab bootstrap contradicts the adopted fix design and Y8's rejection

- Evidence: the plan creates ONE fresh tab via window/new and forbids reusing pre-existing fixture tabs. Fresh window/new tabs are exactly the path that intermittently opened hidden (Y4b root-cause doc: about 6 of 6 new tabs hidden 17:52-17:57). The adopted fix design (worker-y4b-hidden-body-root-cause.md, fix design section) says bootstrap_tab is KEPT and strengthened, with reuse of a verified visible fixture tab preferred, and that its evidence base is n=1 confounded by time, so it is harness defense, not a validated fix. Y8's frozen design (worker-y8-e1-comparison-design.md line 105) explicitly rejects the Y4 bootstrap tab for the same reason ("its evidence is n=1 confounded by time") and uses fresh tabs with no fallback.
- The plan takes the worst of both: a single fresh tab (the hidden-prone path) with no reuse fallback and no specified behavior if that one tab opens hidden and the ladder fails, except suite abort before test 1 with zero tests run.
- Required fix: pick one coherent bootstrap policy and write it down with its failure path. Either keep the Y4b reuse-first bootstrap_tab with a fresh-tab fallback and a per-test re-verify, or adopt Y8's fresh-tab-only policy with an explicit INFRA abort and no silent reuse. Do not present a fresh-tab-only bootstrap as the Y4b design.

## Attack 7: test-09 append is a proven live-vs-simulator divergence, and the plan's rename-branch instruction contradicts the spec

- Evidence: WD.type_text clears first (run_live.py lines 396-400: POST /element/{id}/clear, then POST /element/{id}/value). Puppeteer page.type appends. Simulate.mjs line 343 does `page.type('#note-editor-body', ', Apples')`, which appends to "Milk, Eggs, Bread". A live type_text of ", Apples" would clear the body to just ", Apples", stage that as the Device A buffer, and fail spec step 33 ("Milk, Eggs, Bread, Apples"). The plan correctly identifies this in prose, but the fix (read current value first, then type the full text) exists nowhere in code, and the read must use d.value() on a textarea, which is also unproven in the runner.
- The plan also says "NEVER use the save handler's rename branch". That contradicts the spec: step 7 saves a note titled "Shopping" under a generated id, and the fixture save handler (fixtures/test-09-notes-sync.html, save handler) renames the internal key to 'shopping' exactly when the title is "Shopping" and the active id is not 'shopping'. Without that branch there is no 'shopping' key for keep-both to overwrite later. The bypass Y7 found is narrower: saving with title exactly "Shopping" while the ARCHIVED note is active deletes the archived key. No save happens after the archived note is selected (spec steps 29-34 are click, delete, view, finalize), so the bypass cannot trigger on the spec path.
- Required fix: implement the read-then-type-full step in code for step 10, and correct the instruction to the precise rule: never save with title "Shopping" while the archived note is active. Do not tell the runner to avoid the rename branch outright.

## Attack 8 (BLOCK): test-10 step 15 is impossible as written, and the plan folds a no-op into a pass

- Evidence: fixtures/test-10-ide-debug.html line 114 defines `<input type="text" id="input-edit-watch-total" style="display: none;">`. ## Attack 9: test-01 duplicate ids are handled by luck, not by a selector

- Evidence: the fixture renderPanes loop creates one #pane-terminal-input per pane (fixtures/test-01-tmux-session.html lines 213-216) and one #btn-send-command per pane (lines 218-221). The plan claims "Marionette find returns the first match (the active pane), same as puppeteer". The plan never proves any of that, and it never mentions the duplicate #btn-send-command, whose first match is pane 1's closure. If any later step changed the active pane, first-match typing and first-match sending would silently land in pane 1 while the active output shows pane 2.
- Required fix: scope the selectors to the active pane (for example select inside the pane whose content has id pane-active-output, or assert activePaneIndex via eval before typing), instead of relying on bare duplicate ids and first-match luck. Record the proof in the runner, not in the plan.

## Attack 10: a hidden body mid-test is misclassified as a fixture failure, and the INFRA abort never triggers

- Evidence: diagnose_body runs only in goto (run_live.py goto) and in open_fixture's ensure_visible (run_agyq2.py lines 292-311). WD.refresh (run_live.py lines 351-360) does wait_ready plus a 1 s settle with no diagnose at all, even though open_fixture does clear-storage plus refresh before ensure_visible, so the refresh itself is undiagnosed. If the body goes hidden mid-test (after open_fixture passed), subsequent clicks fail with generic WebDriver errors that contain no "INFRA:" prefix, so main's except branch (run_agyq2.py lines 1267-1275) takes the else path and resets infra_blocked to 0. The suite then keeps driving a hidden tab test after test, each recorded as a fixture failure, and the two-consecutive-INFRA abort the plan relies on never fires.
- Required fix: diagnose after every refresh and on any step failure before classifying it; classify a hidden body found mid-test as INFRA, not as a step failure. State the mid-test hidden-body rule in the plan.

## Attack 11: the re-run rule is unenforceable and the log cannot tell attempts apart

- Evidence: the plan section 2 allows a re-run "ONLY for a test proven infra-blocked, logged as a re-run, never as a first pass". The copied main loop has no re-run path at all: each test runs once, and two INFRA-blocked tests abort the suite. There is no attempt field in the log schema (run_live.py log_step records test, step, op, elapsed_ms, ok, detail, error; Runner.summary records test, pass, failures, details, started_at, finished_at, elapsed_ms). A re-run would write identical test ids into the same JSONL, indistinguishable from the first attempt except by timestamp. The JSONL is also append-only (log_step opens LOG_PATH with "a") with no truncation or rotation step at launch, so a second launch appends to the first run's log.
- Required fix: add an explicit attempt field to log_step and to the per-test summary, implement the re-run path in main (which tests, how many attempts, whether the shared tab is re-bootstrapped), and truncate or rotate LIVE_LOG at launch with the rotation recorded.
