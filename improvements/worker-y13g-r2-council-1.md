### F2 (Medium-Low) Launcher -m guard runs after _derive_ship_dir and cleans the derived dir, not the file's dir
- File: tests/realistic/launch_y13.py:185 (SHIP_DIR = _derive_ship_dir()), 190-213 (_entry_pyc_paths uses _SHIP_DIR), 227-236 (__spec__ guard). The runner has no such ordering issue (its _SHIP_DIR is the file dir, guard first).
- Evidence, two proven sub-cases:
  - (a) Repo-tree -m bypasses the guard entirely. Probe P4a: a copy of launch_y13.py under a dir with a .git (repotree/) run as `python3 -m launch_y13` exits 2 with the C3-1 repo-tree message, and the .pyc written by -m stays behind (pyc-left=['launch_y13.cpython-312.pyc']). The new round-2 repo-tree refusal inside _derive_ship_dir (87eec47) exits before the guard runs, so the guard's cleanup never happens. Control P4b (-m from a staged ship, no .git): guard message + .pyc deleted. This contradicts the B4 re-test assertion "-m exits 2 with the 'use script form' message, no .pyc is left behind" for the repo-tree invocation, which is the most natural place to probe the file.
  - (b) --ship-dir elsewhere cleans the wrong dir. Probe P4c: `python3 -m launch_y13 --ship-dir <other ship>` from a staged ship prints the script-form message but the .pyc stays in the file's own dir (pyc-left-in-file-dir=['launch_y13.cpython-312.pyc']), because _entry_pyc_paths walks the derived SHIP_DIR while -m writes the .pyc next to the source file (__file__ dir).
  - In both cases the leftover .pyc bricks later direct runs from that dir (runner module-top scan refuses kind pyc) until re-stage or regen cleanup (regen deletes tests/realistic/__pycache__ only for the repo dir).
- Proposed fix: run the __spec__ guard BEFORE _derive_ship_dir, against a provisional _SHIP_DIR = dirname(abspath(__file__)); derive the real SHIP_DIR after the guard (and keep the safe_path check after the guard, as now). The guard's cleanup target is then always the file's own __pycache__, which is where -m writes. Re-run the B4 -m re-test from both a repo-tree path and with --ship-dir pointing elsewhere.
