## Confirmed hole (BLOCK)

### B1. Manifest count pin counts entries, not unique files: a duplicate entry masks a dropped file

- Files: `tests/realistic/run_agy_y2.py` lines 296-320 (`_verify_manifest`) and lines 323-350 (`_verify_served_files`).
- Scenario, verified mechanically: take the real manifest, delete the `agy-y2/fixtures/test-08-devtools.html` entry, append a second copy of the `agy-y2/fixtures/test-07-file-manager.html` entry. Entry count stays 26, so the pinned-count check at line 299 passes. Every listed entry's md5 matches disk, so the loop passes. Result from the real function: `ok=True, checked=26, bad=[]`. Then tamper test-08 on disk (appended one line, md5 changed to b584355e8b6f0a6ee3e95f51a8e386dd) and serve it over HTTP: `_verify_manifest` still returns ok=True, `_verify_served_files` still returns ok=True checked=26. The tampered file is never fetched by either check because neither function ever sees its path. The run would proceed and drive run_08 against stale fixture bytes.
- Why this is in scope, not a forger scenario: no manifest generator script exists in the repo (grep finds only SHIPPED.md references), so the manifest is hand built or regenerated by hand, and the working-tree copy is uncommitted and regenerated. A copy-paste or regeneration slip that duplicates one entry and drops another is an ordinary assembly error, exactly the class the F2 count pin was added to catch ("a manifest listing fewer files would silently skip checks", line 146-148). The pin catches a deleted entry only when nothing else fills the count. A malicious forger with ship-dir write access could edit the runner instead, but this hole needs no malice, only a slip.
- Second facet, same root cause, also verified: path-escape entries pass both checks. Rewriting the run_live.py entry path to `agy-y2/../run_live.py` (disk) and to `../run_agy_y2.py` (runner entry) both return ok=True from `_verify_manifest` (Path resolves `..`) and from `_verify_served_files` (http.server normpaths the URL before serving, so the resolved file is served with a matching md5). Alone an escape is not a bypass, since the target file IS verified under an aliased spelling, but it is a second way to disguise a dropped entry in combination with a duplicate. Both facets close with one fix.
- Fix: in `_verify_manifest`, resolve each entry path (`(base_dir / rel).resolve()`) and require the set of resolved paths to have exactly EXPECTED_MANIFEST_FILES members, and require every resolved path to stay inside base_dir. Apply the same uniqueness rule in `_verify_served_files`, or have it reuse the validated entry list instead of re-reading the manifest. A set-equality check against the expected 26 paths is strongest; a uniqueness check alone closes the demonstrated hole.

## Non-blocking findings (fix with B1, or record)

- N1. `_verify_manifest` crashes instead of refusing when `files` is null or a non-sized value. Line 296-299: `files = manifest.get("files", [])` followed by `len(files)` sits outside any try. Verified: files null raises `TypeError: object of type 'NoneType' has no len()`, files int raises the same for int. main() calls it unwrapped (line 2600), and the `--verify-manifest` path (line 2614) likewise, so the process dies with a traceback and no suite JSON. Fail-closed (no tests run, nonzero exit via uncaught exception) but unstructured. Hardening: guard `isinstance(files, list)` before the length check and return `(False, 0, ["manifest files is not a list"], ...)` like an unreadable manifest. Same shape in `_verify_served_files` line 335: `for entry in manifest.get("files", [])` raises TypeError on files null, unwrapped in main at line 2649.
- N2. `_verify_served_files` re-reads and re-parses the manifest instead of reusing the validated entries, and enforces neither the count, the hex rule, nor (after the B1 fix) uniqueness. It is safe today only because `_verify_manifest` already refused malformed entries on the same bytes seconds earlier. A mid-run manifest edit between the two reads (TOCTOU) could make them disagree. Also `rel = entry.get("path")` sits outside the try in the served loop (lines 336-337), so a non-dict entry raises AttributeError out of the function instead of refusing cleanly; reachable only through the same TOCTOU window, since the disk check already refused such entries. Hardening: pass the validated entry list from `_verify_manifest` into the served check, or replicate the guards there.
- N3. Bootstrap ladder time is undercounted, not double counted, when ensure_visible raises. `bootstrap_tab` lines 2316-2320: the accumulation line runs only after a successful `ensure_visible` return; on a raise the attempt's ladder time stays in the discarded runner and never reaches `info["stall_ms"]`. Metric only, direction is undercount. Hardening: move the accumulation into a finally around the ensure_visible call, or accumulate `getattr(r, "stall_ms", 0)` in the except path too.
- N4. Path-escape entries pass both checks (verified, see B1 second facet). Alone they verify the target file under an aliased spelling, so they are not a standalone bypass, but they let a dropped entry hide behind a different spelling in combination with a duplicate. Closed by the same resolved-path uniqueness fix as B1, plus a containment check (resolved path must stay under base_dir).
- N5. Park fallback can close the shared test tab. The shared tab handle is registered in `_TEST_TABS` (bootstrap line 2337, rebootstrap line 655), so if sacrificial creation fails, the fallback loop may park on it and DELETE /session closes it. Recoverable by design (open_fixture re bootstraps), no verdict change, no user tab involved. No fix required; keep the behavior documented.
- N6. Skipped-DELETE residual, pre-existing base behavior. In the session-dropped path, cleanup unlinks the pid file before the next run's preflight sweep could ever see it. If proc terminate plus wait plus kill somehow left the geckodriver alive (all three steps are exception-proof in the base, so this needs a wedged proc), the next run's sweep works from the pid file and would not find it. Extremely unlikely, and outside this diff (base `_cleanup` unchanged). No action.
