## Design principles (derived, not new rules by themselves)

1. Keep the coordinator. The evidence for our shape is the strongest in the crawl (Anthropic B1, swarm-tax B2, Stackness B5). Peer-to-peer worker chat is the failure mode. Workers never negotiate with each other. All contact goes through the coordinator or through the repo (coord files, BOARD.md, PR comments).
2. The coordinator's scarce resource is context and review time, not agent count. Stackness: human review is the bottleneck, 60% of the busiest window idle waiting on the human. Tokenade: re-sent context is most of the bill. Every structural change must reduce coordinator re-reads, review minutes, or loop iterations, or it is not a performance change.
3. Fewer steps beats faster steps. Reliability collapses within 16 steps (Mittal). Our t01 took 12 tool calls. A structure that adds a review hop, a handoff hop, or a coordination hop per task must pay for that hop in steps saved elsewhere, or it makes tasks slower AND less reliable.
4. A rule that lives only in a brief is a reminder. A rule that lives in a lint, a test, a template, a script, or a checklist the runner enforces is a rule. Lauren Tan's test: if the same mistake can come back, it is not yet a rule.

## Proposals

Each proposal has the same four parts: what changes, why it helps performance or quality, what it costs, how to verify it works.

### P1. Original-brief-only spawning: every worker reads the original brief file, never a coordinator summary

- What changes: every spawn brief must name one original brief file path (repo file or coord file) and require the worker to read that file in full before acting. The coordinator may add a short routing note (which files to touch, which to avoid, time budget), but the routing note must never restate the task, the acceptance criteria, or the numbers. If the task has no written original brief, the coordinator writes one first (one page max, with acceptance tests) and then spawns. Summary-only briefs are banned. This applies to Muse subagents, laptop agents via SSH, and clones via coord files alike.
- Why it helps: the swarm-tax experiment measured the cost of summary briefs directly: team pass rate 25.7% with planner summaries vs 54.1% when every member read the task file, a 28.5 point recovery, level with one agent. Hand-offs lose field names, status codes, and edge cases. In our setup the same loss shows up as workers re-asking, re-doing, or shipping work that fails the acceptance test the coordinator already wrote down. Reading the original also removes one coordinator re-write per spawn, which is coordinator context saved.
- What it costs: the coordinator writes a one-page brief before spawning instead of a paragraph in chat. About 5-10 min of coordinator time per new task type, near zero per repeat (template reuse, see P9). Workers read more tokens at start, but the experiment shows the net is still cheaper than a failed team run at 1.6x-3.7x cost.
- How to verify: sample 10 spawns per week. Check each spawn message names a brief file path and the worker's first action log shows it read that file. Metric: share of spawns with a named original brief (target 10/10), and share of worker outputs that fail an acceptance criterion already stated in the original brief (target falling week on week; baseline to be measured on the next 10 tasks, since no baseline exists yet, UNVERIFIED until measured).

### P2. Handoffs rewritten from full history, never from the previous summary

- What changes: whenever a task passes from one agent to another (worker to worker, worker to coordinator, coordinator to clone via coord file, clone back via PR comment), the handoff note is rewritten from the FULL record (brief, logs, test outputs, diffs), not by compressing the previous handoff note. The handoff template is fixed: (a) original brief path, (b) what was done, with file paths and commit hashes, (c) test evidence, with commands and outputs, (d) what failed and the exact error text, (e) what is still open, (f) what NOT to redo. Max one page. The coordinator owns the rewrite for clone handoffs; the outgoing worker owns it for subagent handoffs. A handoff that only says "see previous message" is rejected.
- Why it helps: the handoff-loss experiment found repeated compression is the largest loss mechanism, and rewriting from the full record recovers 70-82% of lost learning at the same note budget. Changing the agent itself caused little or no loss. Our clone2 70+ min stall and the coordinator #2 stall (flagged 04:14, killed 04:36, 50 min after silence) are both consistent with state lost across handoffs: the next agent did not know what the last one had already tried. Full-history rewrites also cut the coordinator's re-read tax, because the coordinator reads one complete note instead of reconstructing state from a chain of summaries.
- What it costs: 5-10 min per handoff to rewrite from the record, vs 1 min to compress the last note. This is the most expensive proposal per instance, so it applies only at real handoffs (agent change, day boundary, clone batch boundary), not at every status update.
- How to verify: sample handoffs. Check each one names the original brief, lists exact error text for failures, and lists open items. Metric: share of handoffs that let a fresh agent resume without re-asking the coordinator a question already answered in the record (target 8/10 or better; measure on the next 10 handoffs).

### P3. Verification evidence contract: "done" is not proof, and reviewer approval is not evidence

- What changes: no worker report counts as done without runnable verification evidence attached. The evidence contract, per task type: (a) code change: the exact test command, its full output or a file path to the log, pass/fail counts, and the commit hash; (b) computer-use task on the machine: a timed run log (wall-clock Asia/Ho_Chi_Minh plus elapsed), step count, and a screenshot or video of the end state; (c) research or crawl: source URLs plus access date per claim, UNVERIFIED where unknown. A bare "done", "fixed", "10/10", or "looks good" with no attached evidence is returned unread. Separately, an agent reviewer's approval is explicitly NOT evidence: per the swarm-tax result (24 of 24 approvals went to code that failed hidden tests), approval only means "I read it", never "it passes". Only an independent acceptance run counts.
- Why it helps: this is Lauren Tan rule 1 applied to our loop, and it attacks the 87.8% directly in the other direction: a false "done" costs a full re-run plus a coordinator investigation, which is more loop iterations than a real verification run. Our own history supports it: clone1 batch 2+3 finished in about 20 min but quality was questioned and now needs a batch 4 council plus redteam re-verification, which is a second full verification cycle bought by accepting a weak first one. METR shows the perception trap: people feel 20% faster while measuring 19% slower, so feeling done is not evidence of being done.
- What it costs: every worker spends the verification run time (our full suite is 119.9 s for 1,523 tests, so this is cheap for code; for machine tasks the timed run is the task itself, so the cost is the log discipline, not extra minutes). The coordinator spends review time reading evidence instead of prose, which is slower per report but far cheaper than a re-run.
- How to verify: audit 10 "done" reports. Count how many carry runnable evidence (target 10/10) and how many later fail an independent re-run (target 0; clone1 batch 2+3 is the current counterexample to beat). Also track VCR (AWS Builder framing): coordinator review minutes divided by worker production minutes per task. If VCR is at or above 1.0, review is theater and the evidence format, not the reviewer, must change.

### P4. Generator-runner separation, enforced by file scope, not by trust

- What changes: keep the existing rule (generators never run their own tests) and enforce it mechanically: the generator's brief names the files it may write; the runner's brief names the test command and the files it may read but not write. The generator's report must not contain test results for its own code (it may contain the command it expects the runner to run). The runner is a different agent (different subagent, or a different laptop agent, or the other clone) and its report is the only test evidence that counts under P3. The coordinator never accepts a generator's self-test as the verification artifact.
- Why it helps: self-verification is the cheapest way to produce a false "done". The swarm-tax reviewer result (24/24 approvals failed hidden tests) is the same failure in review form. Separation also matches Anthropic's successful multi-agent research pattern in its transferable part: workers write outputs to a shared filesystem and return lightweight references, while a different party checks them. It costs one extra spawn per task, but it removes the most expensive failure mode we have: a shipped "done" that is not done.
- What it costs: one extra agent spawn and one extra handoff per task. Against Stackness (effective parallelism only 1.21-1.82x), this is a real cost, so apply it to every code or machine change, but NOT to pure read/research tasks, where Nosov shows sub-agents already cost 74-221% extra for no recall gain.
- How to verify: audit task logs. Metric: share of landed changes whose test evidence came from a different agent than the generator (target 10/10 for code and machine changes). Count reverts or re-verification cycles per landed change (target falling; clone1 batch 4 re-verification is the current baseline case).

### P5. Spawn cap: two lanes by default, spawn only when the parts are truly independent and disjoint

- What changes: default cap is TWO concurrent workers (lanes) per task, including clones. A third lane needs all three conditions: (a) its files are disjoint from both other lanes (no shared file, no shared test slot), (b) it has its own test slot or database, (c) the coordinator can name what it delivers that neither other lane delivers. Spawn is banned for read/search work (Nosov: 0 recall gain, 74-221% extra cost), for tasks under depth 10 in the handoff-tax sense (Anchan and Sen: crossover at depth 10 on one task; below that, one agent thinking longer wins), and for any task where the parts share a file. Sequential is the default. Parallelize only when the parts are truly independent.
- Why it helps: the measured return on parallelism is 1.21-1.82x effective, not Nx (Stackness, 364 runs), while the cost is 1.41-3.31x tokens and a solve-rate drop from 83% to 59% when sub-agents are enabled (2,124-run benchmark). Unbounded fan-out is a named failure mode in that benchmark, alongside orphaned children and delivery races. Our own numbers agree in shape: clone1 batch 2+3 in about 20 min looked fast and produced questioned quality, which is exactly what a too-wide fan-out buys. Two lanes also keeps the coordinator's re-sent context tax bounded (A7: every background transcript is re-sent to the coordinator model).
- What it costs: wall time on tasks that look parallel but are not. The honest trade is stated in the brief: two lanes at 1.5x beats four lanes at 1.8x with a quality re-verification cycle attached.
- How to verify: log lane count, file overlap, and wall time per task for two weeks. Metric: effective parallelism (agent-hours divided by busy hours, Stackness definition) and re-verification rate per lane count. If three-lane tasks do not beat two-lane tasks on wall time including re-verification, the cap stays at two.

### P6. Kill rules: kill on no PROGRESS, not on silence, with a hard wall-clock timeout per task

- What changes: replace the current liveness-based watch with a progress-based watch, and write the thresholds into every spawn brief so the worker knows them before starting. (a) Every worker must emit a progress marker at least every 15 min: a step completed, an artifact written, a test run finished, or a decision logged, with wall-clock time. A heartbeat alone ("still running") is not a progress marker. (b) Watchdog polls every 5 min (unchanged) but judges PROGRESS, not liveness: no progress marker for 15 min is a stall flag, and the coordinator kills on the first stall flag (existing standing rule, kept). (c) Every spawn carries a hard wall-clock timeout in the brief: p95 completion time for that task type plus margin, default 60 min for machine tasks, 30 min for code tasks, 20 min for research tasks, unless the coordinator sets another number with a reason. At timeout the worker is killed even if it is still emitting heartbeats. (d) The watchdog runs as a separate process and reports to the coordinator (Muse), never to the worker or to a sub-coordinator, so a stuck coordinator cannot silence its own stall flag. (e) After a kill, the coordinator writes a one-line kill record (who, when, last progress marker, what was tried) into the task log before respawning, so the next worker does not repeat the dead path.
- Why it helps: the stall sources agree that liveness is not progress. A walking-dead agent passes every liveness check while producing nothing (walking-dead guide, citing 68 confirmed infinite-loop failures across 47 projects). Our own record shows the gap: coordinator #2 was flagged at 04:14 and killed at 04:36, 50 min after silence, and clone2 stalled 70+ min once. A 15-min progress rule with a 5-min poll would have cut both. The hard timeout also caps the worst case we have already seen twice: fcc K2 died twice with zero output (no progress marker at all), and agy Q2 first run timed out at 10 min at 4/10 tests (progress visible, but the timeout was the run's own limit, not a structural kill rule).
- What it costs: watchdog work is unchanged in cadence (5-min poll, 15-min action, matching neuramesh). The new cost is the progress-marker discipline on workers (one line per 15 min) and the kill record (one line per kill). The risk is a false kill on a legitimately slow step; the margin in (c) and the progress-marker definition (a decision logged counts) are the mitigation.
- How to verify: metric 1, time from last progress marker to kill, target under 20 min (5-min poll plus 15-min action). Metric 2, count of kills where the killed agent had emitted only heartbeats and no progress marker in the 15 min before the kill (target: every kill is of this form, meaning no productive work was cut). Metric 3, repeat-kill rate: same task killed twice for the same cause (target 0; a repeat means the kill record in (e) failed or the task needs a redesign, not another spawn).

### P7. Clone management: one batch at a time, acceptance gate between batches, no parallel clone batches

- What changes: (a) only ONE clone batch runs at a time across both clones. Clone1 and clone2 never run parallel batches on the same workstream. (b) Batch size is capped: one batch is one coherent deliverable (one test batch, one fix set), not "batch 2+3" combined. (c) No next batch is assigned until the previous batch passes its acceptance gate: an independent runner (not the clone, per P4) runs the acceptance tests, and the coordinator reads the evidence (per P3) before writing the next coord file. (d) Every coord file carries the original brief path (P1), the acceptance command, the file scope, the wall-clock timeout (P6), and the report format (short structured report plus file paths, no full transcript pasted). (e) If a clone stalls (no progress marker for 15 min by its own log, or no coord-file update for 60 min), the coordinator does NOT send a second nudge into the same coord file. It writes a kill/stop note in the coord file, waits for the clone to acknowledge or for the timeout, then reassigns the batch to the other clone or to a laptop agent, with a fresh handoff rewritten from full history (P2).
- Why it helps: clone1 batch 2+3 in about 20 min is the case study. Fast plus questioned quality means the batch boundary, not the clone, failed: two batches were combined, and the next work started before the previous work was verified. The acceptance gate in (c) is the fix, and it is cheap because the runner is already a separate role (P4). The one-batch rule also respects the evidence that human (coordinator) review is the bottleneck: two clones producing in parallel only queue up review work the coordinator cannot do, and Stackness measured 60% of the busiest window idle waiting on the human. Repo-only contact stays, because it is the structure the crawl supports (coordinator-mediated, no worker-to-worker chat).
- What it costs: clone throughput drops on paper (no parallel batches), and the coordinator pays one acceptance read per batch. The expected net is positive because it removes the batch 4 re-verification cycle we are paying now.
- How to verify: metric 1, batches passing the acceptance gate on first run (target rising; batch 2+3 is the baseline failure). Metric 2, time from batch delivery to acceptance decision (target under 60 min; if the coordinator is the bottleneck, the cap, not the clone, is the problem). Metric 3, count of batches reassigned after a stall (target: every reassignment carries a fresh full-history handoff, P2, with zero repeated dead paths).

### P8. Coordinator guard: read before landing, and join every worker before concluding

- What changes: two guards, both stolen from the crawl. (a) Unread-message guard (Anthropic B1): no worker and no coordinator lands a change (commit, merge, coord-file update, PR comment) until it has read all incoming messages since its last read (repo state, PR comments, coord files, watchdog flags). The guard is a checklist line in the landing step, not a feeling. (b) Join guard (sub-agent benchmark failure mode: orphaned child processes): the coordinator never concludes a task while any spawned worker is still running. Every spawn is joined (report received, or kill record written under P6) before the task is marked done. A task with an unjoined worker is not done, even if its main deliverable looks finished.
- Why it helps: the Anthropic guard recovered failed team episodes to 73% (Opus 5) and 62% (Sonnet 5) on reruns. Orphaned workers are a named failure mode in the 2,124-run benchmark, and our own fcc K2 case (died twice with zero output) is what an unjoined worker looks like from the coordinator side: no report, no evidence, no join. Both guards cost seconds and prevent the most expensive coordinator failure: landing work that a concurrent message already invalidated.
- What it costs: a checklist line per landing, and the coordinator waits for slow workers instead of concluding early. The wait is bounded by the P6 timeout, so it cannot stall the coordinator indefinitely.
- How to verify: audit landings. Metric: share of landings where the landing agent's log shows a repo-state read in the same session (target 10/10), and share of concluded tasks with zero unjoined workers (target 10/10; check by listing spawned workers per task and confirming each has a report or a kill record).

The register has three columns: the repeated item, the conversion (tool, skill, or deterministic rule), and the evidence that it worked (before/after wall time or error count). The coordinator reviews the register weekly and converts the top repeated item. Conversions already implied by our standing rules are written down explicitly instead of living in memory. - Why it helps: this is the compounding mechanism. Without it, every new worker re-learns the same lesson by failing the same way, which is the 87.8% loop paid again for nothing. With it, the system gets stronger the longer it runs, which is the whole point of the clip.

## What this paper deliberately does NOT propose

- No peer-to-peer worker chat. The crawl's strongest result (Anthropic B1, 4 of 4 environments) is against it, and the Madani field study (12 of 14 rollbacks) warns that more handoff structure without coordinator mediation makes it worse, not better.
- No more lanes as the default fix for slowness. Parallelism returns 1.21-1.82x (Stackness) at 1.41-3.31x token cost with a solve-rate drop (2,124-run benchmark). The performance lever is fewer loop iterations and cheaper observations (Council A), not more agents.
- No heavier handoff schemas (JSON schemas, validations) as the fix for lost state. The Madani study found they increased total token spend 1.4x-2.8x over the single-thread baseline. The fix proposed here is rewriting from full history in plain text (P2), which the handoff-loss experiment measured at 70-82% recovery.
- No change to the coordinator role itself. One coordinator, repo-mediated contact, generators separated from runners, watchdog separate from the coordinator. The structure is supported by the crawl; the failures are in its enforcement, not its shape.
- No implementation. Per the task, this paper proposes only. Each proposal names its verification metric so a later worker can implement and measure it.

## Top 3 proposals (summary for Worker W)

1. P1 plus P2, original-brief-only spawning with full-history handoffs. Expected effect: the largest quality recovery available from structure alone. The swarm-tax experiment measured a 28.5 point pass-rate recovery from original briefs, and the handoff-loss experiment measured 70-82% recovery of lost learning from full-history rewrites. In our terms: fewer re-asks, fewer failed acceptance runs, fewer re-verification cycles like clone1 batch 4.
2. P3 plus P4, verification evidence contract with generator-runner separation. Expected effect: false "done" reports stop reaching the coordinator. The cost is one extra runner spawn per code or machine change; the saving is the full re-run plus investigation cycle that a false done currently buys, as clone1 batch 2+3 showed.
3. P6 plus P5, progress-based kill rules with a two-lane spawn cap. Expected effect: stalls end in under 20 min from the last progress marker instead of 50-70+ min, and fan-out stops buying questioned quality at 1.5x wall-time gain. The cap also bounds the coordinator's re-sent context tax.
