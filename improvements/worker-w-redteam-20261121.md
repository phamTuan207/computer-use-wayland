## 1. Council A: performance proposals

### A1. Batch actions per observation inside code-exec programs

- Verdict: WEAKEN. The narrow Pick 1 pattern survives. The generalization to "every multi-step task" dies.
- Strongest attack: the proof is one task shape at small n, and the proposal quietly changes what batching means. Pick 1 measured code-exec batching on one rerun set (4/4, minus 53% wall). Council A then proposes generalizing it to every multi-step task, but the verification experiment it designs uses the Pick 4 fixture at `file:///tmp/speed-pick4-20261118/pick4-fixture.html`, a /tmp path, which is ephemeral scratch, not a committed fixture. A /tmp fixture may not exist on the runner's machine, may differ between runs, and cannot be frozen in a commit. The experiment's foundation is a path that does not survive a reboot. Second, program-composition think grows with program length, and Council A admits it: P3/P4 think-before-code-exec was about 18s vs P2 8.59s (A1 design, 2026-11-19). On longer programs the composition think can eat the whole saving, and the proposal has no cap on program length, no rule for when a program is too long to write. Third, the atomicity guard is a design claim, not a measurement: the A1 design section 7 states the adapter preflights the whole batch, but Council A admits "if that preflight guarantee is wrong for some action type, a partial batch could leave the app in a half-done state." No test of preflight behavior across action types exists in the cited sources. Fourth, the code-exec budgets cap the mechanism: API-call budget 32, wall-clock budget default 30s, max 60s (A1 design). A long task such as f01 with 70 scripted steps cannot fit in one program call; it needs multiple program calls, which reintroduces the loop the proposal claims to remove. Fifth, a batched program written by the model does more damage per mistake than one action: a wrong program can type, click, and submit before any observation catches it, and model-written retry logic can mask errors by retrying a wrong action until it "succeeds" against the wrong state. Sixth, Council A conflates two different batchings: code-exec batching (one program does many actions) and model-turn batching (one turn emits many tool calls). Council C's Experiment 1 tests the second; Council A's proposal is the first. A pass for one does not prove the other.
- Evidence for the attack: A1 design file lines 5-6 and 229-230 (Pick 1 numbers plus the n=1 warning); Council A section 1 (admits think-before-code-exec growth and the preflight conditional); Council C section 2.2 (f01 has 70 scripted steps, which exceeds a 32-call, 60s program budget by construction).
- What would change WEAKEN to SURVIVES: freeze the Pick 4 fixture into the repo (not /tmp) before any run; cap program length and state the cap in the brief; test the preflight guarantee deliberately with a bad ref mid-list across every action type used, and publish which types are preflight-safe; run the held-out realistic task by an independent runner before any default change; and state the expected effect as "Pick 1 shape on deterministic short tasks" instead of "every multi-step task."

### A2. DOM/ARIA-first observation, screenshot only for verification and recovery

- Verdict: WEAKEN. Direction right, default flip premature.
- Strongest attack: the headline numbers do not move wall time the way the proposal implies. DOM read 3-5ms vs screenshot-plus-vision in seconds is a 100x gap in reading state, but reading state is not the loop: think is 87.8% of task time by the councils' own baseline, and a 3ms read saves milliseconds per iteration while each iteration costs about 35s of think (t01: 7 min over 12 calls, task brief, 2026-11-21). The proposal attacks the smallest slice of the loop and presents it as the second-biggest lever. Second, the strongest crawled support actually argues against the necessity of tree-first: PureTensor (2026-09-26, MEASURED, 39 live tasks, bottlenecks crawl A1) found the same model 3.0x slower in a heavy harness vs a lean loop, but the lean loop was screenshot-only, not tree-based. The 3.0x gap came from harness weight, not from tree vs screenshot. A lean screenshot loop already captures most of the win. Third, MobiBench (2026-10-21, MEASURED, 508 tasks, bottlenecks crawl A3) is Android mobile, not desktop Zen; tree 27.17% vs screenshot 4.72% vs hybrid 31.50% measures which input helps a mobile agent choose its next action, not whether a desktop loop should default to tree. Transfer to our Zen desktop loop is assumed, not shown. Fourth, the failure modes are severe and the guards are new infrastructure, not existing pieces: the tree can report correct rects while the viewport is 0x0 (Zen windowed Marionette quirk, zen doc section 3); a BiDi click can report ok while the counter stays 0 (971ms, zen doc section 4); live Zen allows ONE remote session total, so a tree-first loop needs single-session ownership via `scripts/zen_dom.py` file lock plus hung-client watchdog, which does not exist yet as a tested component. Council A says "the pieces exist" while listing a guard that must be built. Fifth, the proposal is browser-only in practice (DOM/ARIA) but framed as a loop default; desktop tasks have no DOM, and the paper gives no desktop observation plan beyond "accessibility tree where available."
- Evidence for the attack: zen doc sections 3, 4, 7 (viewport trap, false-ok click, single session); bottlenecks crawl A1 Source 9 (lean screenshot loop, not tree, produced the 3.0x gap); bottlenecks crawl A3 (MobiBench is mobile); Council A section 2 (admits the Polygon hover case, canvas, and pill have no tree).
- What would change WEAKEN to SURVIVES: build and test single-session ownership first, with a test that proves a second session cannot be opened by accident; run the A/B (DOM loop vs screenshot loop, n=3, same realistic task) and require a wall-time win, not a read-time win; keep tree-first as opt-in per task type (form fill, navigation, state reads) with screenshot-first retained for hover-dependent, canvas, and animated-glass tasks; and stop quoting the 100x read gap as if it were a task-speed gap.

### A3. Code-exec and CLI replace GUI steps wherever the step is deterministic

- Verdict: WEAKEN. Mechanism real, the gate is the problem, and the incremental gain over A1 is small.
- Strongest attack: Council A admits the 157x ratio overlaps proposal 1 almost entirely ("most of the 157x IS the loop that proposal 1 attacks") and that the incremental gain of proposal 3 over proposal 1 is only "the steps that become zero-model-call code instead of one-program-call code." That increment is small and unmeasured. Yet the proposal adds a gate: "before any task runs as a vision loop, the brief must name the deterministic steps and say why each one cannot be code or CLI." A gate is a planning step added to every task, and OSWorld-Human (arXiv 2506.16042v2, June 2026, structures crawl A1) measured planning alone at more than half, sometimes close to 75%, of total task latency. Adding a planning gate to every task taxes the most expensive part of the loop to save a small increment. Second, the "repeated ops become tools" leg leans on the Lauren Tan clip, whose own crawl file (clip crawl, 2026-11-21) states the headline output depended on free Grok tokens at SpaceX and a very strong orchestrator model, and is not reproducible without that budget. Council A admits this and still uses the mechanism as support, but the mechanism without the budget is just "write more tooling," which costs builder time that is never budgeted in the proposal. Third, the substitutability boundary is policed by nothing: a step is substitutable only when the fixture exposes the same operation the user performs, and reaching into fixture internals to set the end state directly is fabrication of a pass (Council C section 4.3 admits this). No reviewer, lint, or test in proposal 3 enforces that boundary; it relies on the worker's judgment, which is exactly what the evidence contract in Council B is for, and proposal 3 does not reference it. Fourth, the code-exec allowlist (no imports, no dunders, no eval/exec/open) caps what is substitutable, and the paper explicitly does not propose widening it, so the scope of proposal 3 is bounded by an allowlist it refuses to touch.
- Evidence for the attack: Council A section 3 (admits overlap with proposal 1 and the small increment); structures crawl A1 (planning share); clip crawl caveats (free Grok tokens, SpaceX); Council C section 4.3 (fabrication boundary).
- What would change WEAKEN to SURVIVES: drop the gate to a guideline ("prefer code/CLI, note the GUI steps you kept and why, in one line"); measure the increment over A1 on one realistic task instead of asserting it; name the enforcement for the substitution boundary (runner checks the program does not touch fixture internals); and budget the tool-building cost per conversion instead of treating it as free.

### A4. Faster coordinate grounding: DOM rects plus a coordinate cache

- Verdict: KILL the cache. The DOM-rect half survives, but only as part of A2, not as its own proposal.
- Strongest attack: the proposal's own cited evidence says grounding is not the bottleneck. PureTensor (2026-09-26, MEASURED, bottlenecks crawl A3) found click accuracy separated the top three vision models by only 3 targets out of 72, yet the most accurate model finished last on live tasks, because most failures were judgment and recovery, not missed pixels. Council A quotes this and then proposes a grounding optimization anyway. The expected effect is small by its own evidence. The cache half is worse than small, it is circular: the invalidation rule is "re-ground on any refusal or any diff touching the target rect," but diffs come from observations, and the cache exists to skip observations. A layout shift that happens between skipped observations produces no diff, so the cache looks valid while the button has moved, and the result is a confident wrong click, which Council A admits is "worse than slow right ones." The cache lifetime is bounded by the 90s snapshot expiry already in `scripts/cdp.mjs`, but realistic tasks run minutes (f01 about 40 min hand-driven, Council C section 1), so the cache expires mid-task anyway and the benefit window is short. The desktop half has no mechanism at all: coordinates are to be cached "keyed by element identity" for non-browser windows, but no definition of element identity without vision is given, and no desktop source for rects is named. Finally, the viewport trap (headless Chrome 1280x800 reports a 1280x713 page, clicks about 12% too low, PureTensor) means DOM rects are in page coordinates while the click driver needs the same frame; the proposed guard is "assert the coordinate frame," which is a test, not a fix, and the test itself is not written.
- Evidence for the attack: bottlenecks crawl A3 (grounding accuracy does not decide live-task success); Council A section 4 (admits stale-cache confident wrong clicks and the 90s expiry); Council C section 1 (f01 about 40 min); PureTensor viewport finding in bottlenecks crawl A1 Source 9.
- What would change KILL to SURVIVES: delete the cache entirely; keep only "use DOM rects where they exist," folded into A2 with no separate proposal, no cache, no desktop identity key; and write the coordinate-frame assertion test before any rect is trusted on a new window size.

### A5. Cut tool calls per task: compact observations, no full history, short reports

- Verdict: WEAKEN. The cheap parts survive. The token claims and the compaction advice do not.
- Strongest attack: the token numbers are the weakest in the package. The 25:1 input/output ratio, the 1M input tokens per 50-turn session, and the 62% re-sent-context figure all come from tokenade.net (about 2026-10-16, bottlenecks crawl B4), which the crawl itself labels mixed verification with the 62% and Uber figures secondhand and UNVERIFIED. Council A repeats them with caveats but still uses them to justify the proposal. The 98% re-sent-context run (claude-code issue 106025, 2026-10-29) is one measured run of a multi-agent Claude Code session, not our loop. Second, the proposal contradicts its own cited reliability evidence: Mittal ("How Fast Do Agents Rot?", about 2026-09, MEASURED, n=10,664 trajectories, bottlenecks crawl A4) found that bounding the context window steepened reliability decay (logit slope minus 0.69 vs minus 0.44). Cutting context aggressively can make the agent dumber, not faster, and Council A admits this in "what breaks" while still recommending compaction. Third, the fixed-schema short report is itself a handoff structure, and the Madani field study (14 deployments, bottlenecks crawl B3) found adding handoff structure increased total token spend 1.4x-2.8x over the single-thread baseline. Council A cites Madani in section 6 to argue against handoff structure, then proposes a fixed report schema in section 5. Fourth, the re-send tax is overstated because prompt caching exists: tokenade itself notes prompt-cache reads cost 5% of fresh input on Opus 5.5 and 10% on Sonnet/Haiku (bottlenecks crawl B4). A re-sent cached context is not a full-price re-send. Fifth, "never send full image history" and "persist the plan outside context" are already standing practice (coord files, BOARD.md), so part of the proposal restates what we do.
- Evidence for the attack: bottlenecks crawl B4 (tokenade caveats, cache pricing); bottlenecks crawl A4 (compaction steepens decay); bottlenecks crawl B3 (Madani structure cost); Council A sections 5 and 6 (the internal contradiction).
- What would change WEAKEN to SURVIVES: keep only the three cheap parts (diff-only observations, short structured reports, file-referenced plans) as hygiene inside proposals 1-4, which Council A already says in its priority order; drop the token-multiplier claims until measured on our own sessions; replace blind compaction with structure-based cuts only (diffs, file references), never truncation; and reconcile the fixed-schema recommendation with the Madani finding explicitly.

## 2. Council B: structure proposals

### B P1. Original-brief-only spawning

- Verdict: WEAKEN. Good hygiene, near-zero marginal gain, wrongly sold as a performance lever.
- Strongest attack: Council B admits in its own synthesis that "our repo-based briefs (coord files, BOARD.md) already implement rule 1." The proposal codifies existing practice, then claims the swarm-tax recovery (25.7% to 54.1%, plus 28.5 points, programmingtheloop.com, 2026-10-26, 144 runs, structures crawl B2) as its expected effect. That recovery was measured on coding tasks with Codex CLI and gpt-5.6-luna, comparing a team given planner summaries vs a team given the task file. Our setup already gives workers the file. The marginal gain of banning summary-only briefs, when summary-only briefs are already not our practice, is unmeasured and plausibly near zero. Second, the cost is coordinator time, which Council B's own design principle 2 calls the scarce resource ("the coordinator's scarce resource is context and review time, not agent count"). Writing a one-page brief before spawning costs 5-10 min of coordinator time per new task type. The proposal spends the scarce resource to save a cost we are not currently paying. Third, the ban is unenforceable in the clone case: clones are contacted only via coord files, and the coord file IS the coordinator's writing. If the coordinator writes a bad coord file, no rule about "reading the original" helps, because the coord file is the original as far as the clone can see. Fourth, "if the task has no written original brief, the coordinator writes one first" adds a serial step before every ad-hoc task, which slows the fast tasks the owner cares about.
- Evidence for the attack: Council B P1 and its design principle 2 (cost vs scarce resource); structures crawl B2 (swarm-tax is coding tasks, Codex CLI); Council B synthesis (repo briefs already implement rule 1).
- What would change WEAKEN to SURVIVES: reframe as template hygiene, not a performance lever; drop the 28.5-point claim for our setup and measure the actual baseline (share of spawns that already name a brief file) before claiming any effect; exempt ad-hoc tasks under a size threshold from the write-a-brief-first rule.

### B P2. Handoffs rewritten from full history, never from the previous summary

- Verdict: WEAKEN. The template is good. The "rewrite from full history at every handoff" rule is too expensive for its evidence.
- Strongest attack: the cost is the highest per instance in the paper (5-10 min per handoff vs 1 min to compress the last note, Council B's own numbers), and the benefit number (70-82% recovery of lost learning) comes from a paper read via summary only (zicq.com summary, about 2026-11-17, bottlenecks crawl B3), with the underlying paper not read in full by the crawler. Council B marks it reported, not independently verified, then builds its second-ranked proposal on it. Second, the rule applies "whenever a task passes from one agent to another," which in our setup is frequent (worker to worker, worker to coordinator, coordinator to clone, clone back via PR comment). At 5-10 min each, handoff rewrites become a standing tax on every transfer, paid in coordinator time, the scarce resource. Third, the proposal contradicts itself on authorship: "the coordinator owns the rewrite for clone handoffs," so the clone's handoff is still a coordinator summary, just a longer one written from the record. P1 bans coordinator summaries; P2 requires the coordinator to write the handoff. Both cannot be the rule. Fourth, the two stall cases cited as evidence (clone2 70+ min, coordinator #2 flagged 04:14 killed 04:36) are consistent with many causes, including a stuck agent, a bad task, or a dead session, not only lost handoff state. "Consistent with" is not "caused by."
- Evidence for the attack: bottlenecks crawl B3 (summary-only caveat on 70-82%); Council B P2 (cost numbers, coordinator ownership); task brief 2026-11-21 (stall cases).
- What would change WEAKEN to SURVIVES: restrict full-history rewrites to real boundaries (day boundary, clone batch boundary, agent replacement after a kill), not every transfer; keep the six-part template for all handoffs; cap the rewrite at one page and time-box it; and measure the resume-without-re-asking rate on the next 10 handoffs before making it a standing rule.

### B P3. Verification evidence contract

- Verdict: SURVIVES. This is the strongest structural proposal in the package, and it survives its best attack.
- Strongest attack: the cost is real and the enforcement is vague. Every worker spends verification-run time, and the coordinator spends review time reading evidence instead of prose, which Council B admits is "slower per report." For machine tasks the timed run is the task itself, so the cost is log discipline, but for research and crawl tasks the evidence (source URLs plus access date per claim) must be assembled by hand, and no time budget is given. "A bare done is returned unread" needs a fast reject path; if the coordinator must read a report to decide it has no evidence, the rejection itself costs review time, and a slow reject loop becomes a new bottleneck. The VCR framing (AWS Builder, 2026-05-29, bottlenecks crawl B1) cuts both ways: if verification costs as much as production, review is theater by Council B's own cited threshold, and P3 plus P4 together (evidence plus a separate runner) can push verification cost above production cost on small tasks. A 2-minute fix with a 5-minute evidence pack and a separate runner spawn is VCR above 1.0.
- Evidence for the attack: Council B P3 (admits slower per-report review); bottlenecks crawl B1 (VCR thresholds are anecdotal, three deployments, not theory); Council B P4 (extra runner spawn adds verification cost).
- Why it survives anyway: the failure it attacks is documented in our own record, not imported: clone1 batch 2+3 finished in about 20 min, quality questioned, now needs a batch 4 council plus redteam re-verification, a second full verification cycle bought by accepting a weak first one (task brief, 2026-11-21). The cost of a false done (full re-run plus investigation) exceeds the cost of attaching evidence (our full suite is 119.9s for 1,523 tests). The Lauren Tan rule it implements (done means nothing without runnable verification evidence, clip crawl, 2026-11-21) is the most transferable rule in the clip because it does not depend on token budget. The attack only narrows the scope, it does not kill the idea.
- What would strengthen it further: a light evidence format per task type (command plus output path plus counts, not a prose essay); a fast reject (coordinator checks for the evidence attachment first, before reading the report); and a VCR check per task size, with small tasks exempt from the separate-runner leg of P4.

### B P4. Generator-runner separation, enforced by file scope

- Verdict: WEAKEN. Right for landed changes, wrong as a universal rule, and unenforceable as specified.
- Strongest attack: the cost is one extra agent spawn and one extra handoff per task, which is exactly the sub-agent cost the councils cite against parallelism (1.41x-3.31x tokens, solve rate 83% to 59%, 2,124-run benchmark, structures crawl B3; Nosov 74-221% extra for read/search work, structures crawl B4). P4 spends that cost on every code or machine change, including small ones, while P5 caps the system at two lanes. A generator plus a runner is already two lanes, which leaves no lane for any second real worker. The proposals collide: P4 consumes the P5 budget. Second, "enforced by file scope, not by trust" does not enforce anything: file scope names which files the generator may write and which the runner may read, but nothing in file scope prevents the generator from running the test command anyway and pasting the result, or prevents the runner from editing a file. Enforcement would need a mechanism (separate checkout, permissions, or a log audit), and none is proposed. Third, the exemption ("NOT to pure read/research tasks") is a judgment call the coordinator must make per task, which adds a classification step to every spawn. Fourth, the swarm-tax reviewer result (24 of 24 approvals failed hidden tests) is about code review, not about self-testing; the paper treats them as the same failure, but a generator running its own tests and a reviewer approving code are different mechanisms with different fixes.
- Evidence for the attack: Council B P4 and P5 (spawn cost vs lane cap); structures crawl B3 and B4 (sub-agent costs); Council B P4 (no enforcement mechanism named).
- What would change WEAKEN to SURVIVES: apply separation to landed changes only (code merged, machine state changed, contest-affecting work), not every task; let the runner be an already-running agent (the other clone, a laptop agent) instead of a fresh spawn wherever possible; add a real enforcement check (audit the generator's log for test commands, or run the runner in a separate checkout); and count the runner spawn against the P5 lane cap explicitly so the collision is visible.

### B P5. Spawn cap: two lanes by default

- Verdict: SURVIVES. The evidence is the strongest multi-source case in either council paper.
- Strongest attack: the "depth 10" crossover (Anchan and Sen, arXiv:2610.06069, Oct 2026, bottlenecks crawl B3) comes from one ledger-reconciliation task, and Council B admits the number is task-specific, not universal, then uses it as a ban ("spawn is banned for tasks under depth 10"). A task-specific number cannot support a universal ban. The three conditions for a third lane are also uneven: (a) disjoint files and (b) own test slot are checkable, but (c) "the coordinator can name what it delivers that neither other lane delivers" is subjective and will be satisfied by any articulate coordinator. The cap is therefore enforced by two real conditions and one rhetorical one. The Stackness evidence (364 runs, 2026-11-11, structures crawl B5) is single repo, single developer, single harness, by the author's own caveat. The 2,124-run benchmark was read via news summary, not the underlying study (structures crawl B3). The clone1 batch 2+3 case (about 20 min, quality questioned) is cited as proof that fan-out buys questioned quality, but the batch boundary, not the lane count, may be the fault: two batches were combined and the next work started before verification, which is a P7 failure, not a P5 failure.
- Evidence for the attack: bottlenecks crawl B3 (depth-10 task-specific); structures crawl B5 (single repo/developer caveat); structures crawl B3 (news-summary caveat); Council B P7 (batch boundary as the alternative explanation).
- Why it survives anyway: three independent sources point the same way (Stackness effective parallelism 1.21-1.82x, the 2,124-run solve-rate drop, Nosov cost with no recall gain), and the cost of the cap is zero to implement (it is a refusal to spawn, not a build). Even if the exact numbers are soft, the direction is consistent and the downside of the cap is bounded: a task that truly needs three lanes can still get one by meeting conditions (a) and (b). The attack narrows the justification, it does not overturn the rule.
- What would strengthen it: drop the depth-10 ban to a guideline ("below depth 10, prefer one agent thinking longer"); make condition (c) checkable (name the deliverable file, not a sentence); and log lane count, file overlap, and wall time per task as proposed, so the cap earns its keep with our own numbers within two weeks.

### B P6. Kill rules: progress-based watch with hard wall-clock timeouts

- Verdict: WEAKEN. The progress watch is right. The hard timeouts with invented numbers are not.
- Strongest attack: the timeout defaults (60 min machine, 30 min code, 20 min research) are invented. Council B admits no baseline exists for time-from-last-progress-to-kill and that three of four paper-wide metrics are UNVERIFIED until measured. A timeout set without p95 data is a guess, and a wrong guess false-kills legitimate slow work: Council C states f01 hand-driven is about 40 min per run, which already exceeds the 30-min code-task default, and a long Zen load, a compile, or a 70-step task can legitimately emit no progress marker for more than 15 min. The progress-marker definition ("a decision logged counts") is loose enough that a stuck agent can emit decisions forever and never be killed, while a productive agent doing one long step gets killed. Both failure modes exist in the same rule. The "kill on the first stall flag" standing rule, combined with a 5-min poll and a 15-min action, means a worker can be killed 20 min after its last marker even when the marker gap is caused by the task, not the worker. The kill record (one line per kill) is good, but the repeat-kill target of 0 is unrealistic: a task killed twice for the same cause may mean the task is hard, not that the kill record failed. Finally, the watchdog reporting line ("reports to the coordinator, never to a sub-coordinator") assumes the coordinator is always available to receive it; if the coordinator is the stuck part, the flag still waits on the coordinator, which is the exact failure the standing rule was written to prevent (watchdog reports to Muse, not to the coordinator, per the task brief).
- Evidence for the attack: Council B P6 (invented defaults, loose marker definition); Council C section 1 (f01 about 40 min); task brief 2026-11-21 (coordinator #2 stall, clone2 stall); bottlenecks crawl B5 (stall sources agree on progress markers, but none prescribes 60/30/20 defaults).
- What would change WEAKEN to SURVIVES: measure p95 completion time per task type on the next 10 tasks first, then set timeouts from those numbers with margin; until then, timeouts are a coordinator judgment call, not a number in the brief; tighten the marker definition (a decision counts only if it names the next concrete step and its evidence); and clarify the watchdog reporting line so a flag about the coordinator goes to Muse directly, not to the coordinator being flagged.

### B P7. Clone management: one batch at a time, acceptance gate between batches

- Verdict: WEAKEN. The acceptance gate is right. The blanket one-batch ban is not.
- Strongest attack: the proposal kills the one parallelism that demonstrably worked. Clone1 batch 2+3 finished in about 20 min; the quality was questioned, but Council B attributes the quality failure to the batch boundary ("two batches were combined, and the next work started before the previous work was verified"). If the fault is the missing acceptance gate, the fix is the gate, not banning parallel batches. Banning parallel batches on disjoint workstreams throws away throughput to fix a gate problem. Second, the gate adds coordinator review per batch, and Council B's own cited evidence (Stackness, structures crawl B5) says coordinator/human review is the bottleneck, with 60% of the busiest window idle waiting on the human. Adding a review gate per batch while the coordinator is the bottleneck queues more work behind the slowest resource. The metric "time from batch delivery to acceptance decision, target under 60 min" admits the coordinator may be the bottleneck, but the proposal has no remedy if the target is missed. Third, the stall handling has two different clocks: no progress marker for 15 min by the clone's own log, or no coord-file update for 60 min. A clone can be stalled for 59 min by the second clock while the first clock says 15 min. The proposal does not say which clock governs. Fourth, "do NOT send a second nudge, write a kill/stop note, wait for ack or timeout, then reassign" can strand a batch for up to the timeout while the other clone sits idle.
- Evidence for the attack: Council B P7 (gate vs ban conflation, two clocks); structures crawl B5 (coordinator review is the bottleneck); task brief 2026-11-21 (clone1 batch 2+3 in about 20 min).
- What would change WEAKEN to SURVIVES: keep the acceptance gate (no next batch on the same workstream until the previous batch passes); drop the blanket one-batch ban and allow parallel batches on disjoint workstreams with separate runners; pick one stall clock (15-min progress marker) and use it everywhere; and add a remedy for the coordinator bottleneck (if acceptance decisions exceed 60 min twice, the cap, not the clone, is the problem, and batches queue instead of spawning).

### B P8. Coordinator guard: read before landing, join every worker before concluding

- Verdict: WEAKEN. Cheap checklist lines, overstated evidence, one real delay cost.
- Strongest attack: the unread-message guard's headline (recovered failed episodes to 73% Opus 5 and 62% Sonnet 5 on reruns, Anthropic "Worse Together," 2026-11-11, structures crawl B1) comes from simulated environments with per-user peer agents and competing goals, not from a manager directing specialists. Council B notes the caveat and still uses the numbers as if they transfer. Our setup already has repo-mediated contact; the guard's marginal effect here is unmeasured. "Read all incoming messages since its last read" is unbounded: repo state, PR comments, coord files, watchdog flags. On a busy day that read can be large, and the guard has no scope limit. The join guard has a real cost: the coordinator waits for slow workers instead of concluding early, bounded by the P6 timeout, which defaults to 60 min for machine tasks. A task whose main deliverable is done can sit unconcluded for up to an hour because one worker is slow. The fcc K2 case (died twice with zero output) is cited as what an unjoined worker looks like, but a dead worker with zero output is a P6 kill case, not a join-guard case; the join guard does not resurrect it, it only delays the conclusion while the kill is processed.
- Evidence for the attack: structures crawl B1 (simulated environments caveat); Council B P8 (unbounded read, wait bounded by 60-min timeout); task brief 2026-11-21 (fcc K2 zero output).
- What would change WEAKEN to SURVIVES: keep both guards as checklist lines, not blocking gates; scope the unread-message read to the task's own files (its coord files, its PR, its watchdog flags), not the whole repo; cap the join wait (if a worker has not reported by its P6 timeout, write the kill record and conclude without it); and stop quoting the 73%/62% simulated recovery as expected effect for our setup.

### B P9. Register, plus P9a rules, P9b tools, P9c skills

- Verdict: KILL the apparatus. The underlying principle survives, but only as a habit inside P1-P8, not as a program.
- Strongest attack: P9a is a restatement, not a proposal. Its thirteen rows duplicate P1-P8, Council A's observation rule, and the step-budget and report rules. Counting it as a separate proposal double-counts work already proposed elsewhere. P9b proposes four tools (overlap-audit enforcement, watchdog as a separate process with kill-record writer, handoff-template filler, evidence packager) with no build cost, no owner, and no time estimate; the handoff-template filler and evidence packager are new moving parts that themselves need testing, and the Madani finding Council B cites (adding handoff structure increased tokens 1.4x-2.8x) warns that exactly this kind of apparatus makes things worse. P9c proposes three skills with the same problem: a spawn-brief skill, a machine-verification skill, and a clone-coordination skill, none written, none budgeted. The register itself (one file, weekly 15-min review, convert the top repeated item) has no owner and no budget, and "conversions are only built when the item has repeated at least twice" is a rule about when to build, not a plan to build. The Lauren Tan clip rule ("a repeated mistake becomes a deterministic rule, never a reminder") is about turning a mistake into a lint, a test, or an architecture constraint, not about maintaining a register. The register is process about process. Finally, the geometry rule in P9a ("viewport constants live in one file, verified by a test") is a code change owned by Council A, and Council B admits Council A owns the technical form, so accountability is split across two papers for a single rule.
- Evidence for the attack: Council B P9 (duplication visible in the table, no owner or budget named); bottlenecks crawl B3 (Madani structure cost); clip crawl (the rule is lint/test/architecture, not a register).
- What would change KILL to SURVIVES: delete the register and the weekly review; delete P9b and P9c as a program and propose at most one tool (the evidence packager, which directly serves P3) with a named builder and a time budget; keep the one-line principle ("twice means a rule, and the rule lives in a lint, a test, or a template") as a sentence inside the spawn-brief template; and assign the geometry rule to one owner.

## 3. Council C: measurement proposals

### C Exp1. Batching experiment, 44 runs, 30% bar, four go conditions

- Verdict: WEAKEN. The experiment is needed. As designed it is too expensive, too fragile, and it tests the wrong batching.
- Strongest attack: cost first. 44 runs, with 6 f01 runs at about 40 min hand-driven each (Council C section 1, extrapolation from RUN-REPORT-20261121.md), is about 4 hours of agent time for f01 alone, plus 38 other runs, plus coordinator review, plus the unscoped precondition (fix fcc-k fixtures and replace `__fcckVerify()` self-simulation with DOM assertions). The precondition is itself generator work that needs a runner and evidence under B P3/P4, so the experiment triggers the whole apparatus before any measurement happens. No time budget for the precondition is given. Second, the design is fragile: n=3 per method per case, and a median of 3 is flipped by a single flake, a Zen restart, or an SSH drop. Alternating A/B/A/B does not cancel learning effects: the runner learns the task across runs, so later runs are faster regardless of method, and there is no blinding (the runner knows which method it is running). Expectation bias is uncontrolled. Third, the primary set is a selected subset: 4 of 10 fcc-k cases, excluding f06, f07, f08, f10 (BLOCKED) and f02, f05 (fixture gaps). The experiment measures the loop on the cases that survived selection, not on the loop generally. Fourth, and most important, Experiment 1 tests model-turn batching (one turn emits a batch of independent actions), while Council A's proposal 1 is code-exec batching (one program does many actions). A GO for one does not prove the other, and a NO-GO for one does not kill the other. The two papers' "single first experiment" claims therefore cannot both be true: Council A says the first experiment is the Pick 4 fixture, n=3, code-exec program vs step-by-step loop; Council C says the first experiment is 44 runs on fcc-k. They test different levers on different fixtures with different bars (Council A: fewer calls AND lower wall; Council C: 30% median wall plus pass rate plus recovery plus 2.5 actions per observation). Fifth, the fourth go condition (actions per observation at least 2.5 mean) conflates mechanism with outcome: a batching method could win wall time via fewer observations without reaching 2.5 if batches are small, and the experiment would call that inconclusive instead of a win.
- Evidence for the attack: Council C sections 1, 2.2, 2.5, 2.6 (cost, exclusions, n=3, four conditions); Council A section 1 (different fixture, different bar); RUN-REPORT-20261121.md lines 88-93, 177 (fixture defects, f01 70 steps, 40-min extrapolation).
- What would change WEAKEN to SURVIVES: run a pilot first (f01 plus one more primary case, n=3 per method, alternating, checker blinded to method) before committing to 44 runs; time-box the fixture fix with a named budget and freeze the fixed fixtures in one commit; drop or soften the 2.5 actions-per-observation condition to a diagnostic (report it, do not gate on it); and reconcile with Council A in writing: either Experiment 1 tests code-exec batching (A1) or model-turn batching, not both, and the other gets its own named experiment.

### C Exp2. Tree-first observation experiment, 20% bar

- Verdict: WEAKEN. Same cost problem as Exp1, plus confounding by Exp1's outcome.
- Strongest attack: another 44 runs on the same frozen set, after the runner has already practiced those cases in Exp1. Learning effects contaminate Exp2: the runner knows f01, f03, f04, f09, t03, and t10 by then, so the baseline is no longer a fresh baseline. The design tries to control confounding by holding batching fixed at the Exp1 outcome ("if Exp1 went GO, B includes batching; if NO-GO, B uses one action per turn"), but that means the treatment in Exp2 differs depending on Exp1's result, so Exp2's result cannot be compared across the two branches and cannot be replicated without re-running Exp1. The 20% bar is arbitrary: no power analysis, no justification for why 20% is the right threshold vs 10% or 30%, and Council C admits the published multipliers behind it are weak (SyndiPath vendor blog UNVERIFIED, olliebot secondhand, PureTensor 3.0x harness gap that was screenshot-only). The go rule is asymmetric in the wrong direction: any pass-rate drop is an automatic NO-GO even if wall time falls sharply, so a tree-first loop that is 40% faster with a small accuracy cost on one case type is discarded, while a 21% win with equal accuracy is adopted. The value tradeoff is decided by the rule, not by the owner. Finally, MobiBench (the best cited evidence) supports hybrid input (31.50%) over tree-only (27.17%), and Exp2's treatment (tree every iteration, screenshot only at verification and recovery) is close to hybrid, so the experiment may pass while proving less than claimed: it proves hybrid works, which was already the MobiBench finding.
- Evidence for the attack: Council C section 4.2 (batching held at Exp1 outcome, 20% bar, auto NO-GO on pass-rate drop); bottlenecks crawl A3 (MobiBench hybrid beats tree-only); Council C section 2.6 (same case set reused).
- What would change WEAKEN to SURVIVES: run Exp2 only if Exp1 goes GO, on a smaller set (two primary cases plus one control, n=3), with a fresh runner who did not run Exp1; justify the 20% bar or replace it with "faster with equal pass rate, and the size reported plainly"; and let a small pass-rate drop trigger a scoped follow-up (which case types lose accuracy) instead of an automatic NO-GO.

### C Exp3. Code-exec and CLI substitution experiment, 25% bar, 30% substitutable share

- Verdict: KILL as designed. The question is worth asking, but this experiment is not the way to ask it.
- Strongest attack: four simultaneous go conditions (25% median wall reduction, pass rate equal or better, recovery steps not rising, substitutable-step share at least 30%) make the joint probability of a GO low even for a real effect. If each condition has an 80% chance of passing on a true effect, all four pass about 41% of the time; the experiment is designed to fail. Second, the qualifying cases are the wrong cases: f01 has a spec bug (uppercase formulas, RUN-REPORT-20261121.md line 99) that must be fixed first; t03 and t10 are clone1 control-set short cases, and Council C's own section 1 states clone1 tests are 5-7 steps each and "too short to show think-time differences." The experiment uses cases its own author says cannot show the effect. Third, the boundary rule (no reaching into fixture internals to set the end state directly) is unenforceable by a runner alone: it requires code review of every program the agent writes, and no reviewer role is assigned to Exp3. A run that fabricates a pass by setting fixture state directly looks identical to a legitimate substitution in the run log unless someone reads the program. Fourth, the answer is already largely known: scripted code is faster than GUI driving (157x on t01, INTERNAL; 16x-50x per-step gap, UI-TARS writeup secondhand, bottlenecks crawl A1). The open question is not whether code is faster but how much of the 157x gap the agent loop closes, and that can be answered by comparing the Exp1 treatment arms against the scripted floor, with no separate 44-run experiment. Exp3 spends a full experiment to re-measure a known direction.
- Evidence for the attack: Council C sections 1, 4.3 (short control cases, spec bug, four conditions, fabrication boundary); RUN-REPORT-20261121.md lines 41, 99 (f01 spec bug); bottlenecks crawl A1 Source 10 (per-step gap, secondhand).
- What would change KILL to SURVIVES: fold the question into Exp1/Exp2 reporting (report substitutable-step share and wall time vs the scripted floor for the cases already run, no new runs); if a standalone experiment is still wanted, use one long case with many substitutable steps (f01 after its fix), n=3, a single go condition (wall time down with pass rate equal or better), and a named code reviewer who reads every program for fixture-internal writes.

### C Six metrics plus run-log schema (sections 3.1-3.7)

- Verdict: SURVIVES, with two downgrades.
- Strongest attack: metric 3.3 (tokens per task, input and output separately) is often unmeasurable by Council C's own admission: "if the session does not expose a per-task token count, report tokens as UNMEASURED for that run and use tool calls as the cost proxy." A metric that is UNMEASURED on many runs cannot be a required field, and the schema's tokens_in/tokens_out-or-null design means medians will have holes that are never explained. Metric 3.4 (observation cost per observation by type) requires logging every observation with type and timestamps, which is new harness work, unbuilt and unestimated; until the harness logs it, the metric is aspirational. Metric 3.5 (verification cost, VCR) imports thresholds (under 0.5 fine, 0.5-1.0 edge, at or above 1.0 theater) from AWS Builder (2026-05-29, bottlenecks crawl B1), which the crawl labels anecdotal field observation from three deployments, "not a survey" and "not theory." Treating VCR at or above 1.0 as theater is a pragmatic cutoff, not a finding, and for safety-critical verification (a contest upload with a deadline, a package error that blocks a contest) verification should cost as much as production. Metric 3.6 (stall minutes as wall time minus time covered by progress markers) is ill-defined when markers are sparse: a 40-min f01 run with markers every 15 min can show large stall minutes spuriously.
- Evidence for the attack: Council C sections 3.3, 3.4, 3.5, 3.6 (caveats in the author's own words); bottlenecks crawl B1 (VCR anecdotal).
- Why it survives anyway: wall time (3.1), tool calls (3.2), pass/fail by DOM checker, recovery steps, and the JSONL schema are the right spine, and "a run report missing a metric says UNMEASURED, never a guessed number" is the single most important sentence in the paper. The attack only downgrades tokens to best-effort and VCR to a flag, not a rule.
- What would strengthen it: mark tokens as best-effort (report when available, never block a run report on it); build the observation logger before requiring metric 3.4; use VCR as a flag ("verification cost exceeded production cost, explain why") rather than an automatic theater verdict; and define stall minutes with a worked example so two runners compute the same number.

### C Pre-registration, frozen cases, and anti-self-deception rules (sections 5.1-5.5)

- Verdict: SURVIVES. The strongest part of Council C, and the hardest to kill.
- Strongest attack: the honest costs. "No threshold moves after seeing results; if a threshold was wrong, the experiment is re-run as a new pre-registered experiment" doubles the cost of any misspecification, and with n=3 medians and arbitrary bars (30%, 20%, 25%), misspecification is likely. Frozen cases plus an independent runner plus a second checker is three roles per experiment, which is coordinator overhead that Council B's P5 cap and P4 runner cost already strain. The METR lesson (felt speed vs measured speed, 19% longer with AI while developers felt 20% faster, 16 developers, 246 issues, July 2025, re-analysis Oct 2026, bottlenecks crawl B2) is from early-2025 tools and experienced maintainers in their own large codebases; Council C notes the scope limit, but the paper still uses it as the justification for wall-time-only claims, which discards legitimate secondary signals (fewer errors, less coordinator re-reading) that wall time alone does not capture.
- Evidence for the attack: Council C sections 5.1, 5.4 (re-run cost, three roles); bottlenecks crawl B2 (METR scope limits).
- Why it survives anyway: pre-registration, frozen cases, reporting all runs including failures and invalidations, and independent verification are the only defenses against the failure mode this team has already shown (a fast batch with questioned quality, a 20-min batch that needed a full re-verification). The re-run cost is the price of honesty, and it is cheaper than shipping a false speedup. The METR scope limit narrows the lesson, it does not remove it: felt speed is not evidence in any scope.
- What would strengthen it: allow a pilot phase with movable thresholds (pilot results set the bar, then the bar freezes for the confirmatory runs), so misspecification is caught cheaply; and record one secondary metric per experiment (coordinator review minutes) so wall-time-only claims do not discard the coordinator cost.

### C Order of work (section 6): fixtures first, then Exp1, Exp2, Exp3 sequentially

- Verdict: WEAKEN. Fixtures-first is right. Strict sequential gating is too slow.
- Strongest attack: "no experiment starts until the previous one's go/no-go is recorded, unless the parent explicitly orders parallel runs" (Council C section 4, intro) plus the six-step order in section 6 means the team waits weeks: fixture fix (unbudgeted), then 44 runs for Exp1, then 44 for Exp2, then Exp3. At 40 min per f01 run and a 15-min watchdog cadence, the calendar cost is measured in weeks, while the owner priority is performance now. The sequential rule also contradicts Council B's own evidence that review, not agent count, is the bottleneck: sequential experiments do not reduce review load, they serialize it. The fixture fix and the Exp1 pilot can run in parallel on disjoint cases (fix f06-f10 while piloting f01/f03), and the Exp2 design (not runs) can be written during Exp1. Strict sequencing buys cleanliness at the price of speed, and cleanliness is not the owner's priority; performance is.
- Evidence for the attack: Council C sections 4 and 6 (sequential gating, six steps); Council C section 1 (f01 about 40 min per run); structures crawl B5 (review is the bottleneck).
- What would change WEAKEN to SURVIVES: keep fixtures-first for the cases in the experiment, but allow the fixture fix and the Exp1 pilot to proceed in parallel on disjoint cases; allow Exp2 design work during Exp1 runs; and replace "no experiment starts until the previous go/no-go" with "no experiment's runs start until the previous experiment's cases and thresholds are frozen," which preserves the anti-confounding intent without serializing the calendar.

## 4. Contradictions between the councils (and with standing rules)

These are not nitpicks. Each one means two papers tell the implementer opposite things, and the implementer will guess.

1. Two "single first experiments." Council A section 7: the first experiment is proposal 1's verification on the Pick 4 fixture, n=3 per arm, code-exec program vs step-by-step loop. Council C section 2 and 4.1: the first experiment is 44 runs on fcc-k cases, model-turn batching. Different lever, different fixture, different bar. Both claim to be first. One of them must yield, or the team runs two "first" experiments and learns less from each.
2. Handoff structure: yes or no. Council A section 6: "Do NOT add handoff structure to fix handoff loss," citing Madani (structure added 1.4x-2.8x tokens). Council B P2 (fixed six-part template), P3 (fixed evidence schema), P9 (templates, register, skills): add handoff structure. Direct contradiction, unacknowledged in either paper.
3. The runner consumes the lane cap. Council B P4 adds one runner spawn per code or machine change. Council B P5 caps the system at two lanes. Generator plus runner is two lanes, leaving no lane for a second real worker. Neither proposal counts the runner against the cap.
4. Verification cost vs the theater threshold. Council B P3 plus P4 (evidence on every report, plus a separate runner) can push verification cost above production cost on small tasks. Council B's own cited VCR rule (AWS Builder, bottlenecks crawl B1) calls verification at or above 1.0 theater. The paper cites the threshold to justify P3 and then proposes a combination that can breach it.
5. Context: cut it or read it all. Council A A5: cut context (diffs, short reports, no full history). Council B P2 and Council C section 5.5: handoffs rewritten from the full record, coordinator reads the full log. These can be reconciled (cut worker context, keep coordinator handoffs full), but neither paper draws the line, so an implementer cutting context will cut the handoff record too.
6. Kill on first flag vs quality over speed. Standing rule: quality over speed; kill stuck agents on first stall flag. Council B P6 combines them with invented timeouts (60/30/20 min) and a loose progress-marker definition. A productive agent on a legitimate 40-min step (f01) can be killed under the rule while a stuck agent emitting decisions survives it. The standing rule and P6 as written are in tension, and P6 does not resolve it.
7. Who owns the observation rule. Council B P9a states the observation rule (tree/DOM/AX first, batch actions per observation) as a structural requirement but says "Council A owns the technical form of this rule." If DOM-first fails, neither council owns the failure. Split accountability is no accountability.
8. Selection bias in the measurement set. Council C Exp1 excludes 6 of 10 fcc-k cases (f02, f05, f06, f07, f08, f10) and measures 4. Council A Exp1 uses one synthetic Pick 4 fixture. Both claim to measure "the loop." Neither measures the loop on the cases that were excluded, which are the hard cases (blocked buttons, missing UI, fixture gaps) where the loop actually spends its time.
9. The coordinator summary ban vs coordinator-authored handoffs. Council B P1 bans coordinator summaries as a task source. Council B P2 requires the coordinator to own the rewrite for clone handoffs. The clone's only source is therefore a coordinator summary, just a longer one. The ban is unenforceable where it matters most (clones, who have no other channel).
10. Sequential experiments vs the user's priority. Council C section 4: no experiment starts until the previous go/no-go is recorded. Owner priority: performance when Muses control the user's machine, first. Strict sequencing is the slowest way to get performance answers, and the paper gives no calendar estimate for the full sequence.
