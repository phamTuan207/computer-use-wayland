## The 3 sharpest attacks (with proof)

### Attack 1 (sharpest): the Wayland-nested design repeats the exact failure it claims to escape

The design's launcher, run-nested-wayland.sh, is specified to set XDG_RUNTIME_DIR=/tmp/y6-nested/run and WAYLAND_DISPLAY=wayland-1, then start the nested Hyprland so it connects to the live compositor as its Wayland parent.

That cannot work as written. The live compositor socket is at /run/user/1000/wayland-1 (verified: srwxr-xr-x, Nov 21 15:17). A relative Wayland display name is resolved under XDG_RUNTIME_DIR by libwayland-client, so with XDG_RUNTIME_DIR=/tmp/y6-nested/run the nest looks for /tmp/y6-nested/run/wayland-1, a path that does not exist and that nothing creates. The result is the same wl_display_connect failure already in all five crash reports, for the same reason: a display name pointed at a socket that is not there.

This is not a new failure mode. It is attempt 3's failure mode, copied into the fix. Attempt 3's run-nested.sh did exactly this pattern (isolated runtime dir plus a relative display name), and its tail shows Wayland backend cannot start: wl_display_connect failed. The design changes the display name from wayland-y6 to wayland-1 but keeps the runtime-dir override that makes the name unresolvable.

The fix is one line and the design does not contain it: either set WAYLAND_DISPLAY=/run/user/1000/wayland-1 (absolute path, so XDG_RUNTIME_DIR is irrelevant for the parent connection) while keeping the isolated runtime dir for the nest's own socket, or keep XDG_RUNTIME_DIR=/run/user/1000 for the parent connection and give the nest a distinct display name. Until one of those is in the script, Council A's instruction to run the design verbatim is an instruction to reproduce a known failure. The two design files do not exist yet (re-verified: no run-nested-wayland.sh, no hyprland-wayland.conf, no optics.lua under /tmp/y6-nested/), so nothing stops the author from fixing this before the files are created, but as written the design is dead on arrival.

Consequence: Path C's proof bar (nested starts, plugin loads) has never been attempted even once in a form that could pass its first step. Any schedule or GO/NO-GO that assumes the design is ready is built on a file that does not exist and a command that cannot connect.

### Attack 2: five crashes are one experiment, and the verdict claims five experiments

Y6's headline rests on counting: 5 launches, 5 identical crashes, therefore HEADLESS DOES NOT WORK. The count is true as launches and false as experiments.

What the artifacts actually distinguish:

- Attempts 1, 2, and 4 are observationally identical. Their stdout logs are byte-identical apart from run-dir suffix and PID, and all five logs (including attempt 4) print Disabling stdout logs (debug.enable_stdout_logs = 0). Attempt 4's claimed distinguishing condition never took effect: the config on disk now contains enable_stdout_logs = true with mtime 18:23, but the log line proves the running process read it as 0. Attempts 1 and 2 differ only in Y6's word (WLR only vs WLR plus AQ), with no launch artifact for either; the env vars in question do not exist in the binary anyway (see below), so the claimed difference could not have changed the outcome even if it happened.
- Attempt 3 is the only genuinely distinct run: it has a saved launcher (run-nested.sh), it ran as a live-session child, and it is the only tail with the logind.c:309 Device or resource busy line.
- Attempt 5 is distinct only by one line: seatd.c:66 Permission denied instead of seatd.c:64 No such file or directory, proving a seatd socket existed at that time.

So the evidence collapses to three observable experiments (SSH baseline, live child, seatd-EACCES), all sharing the same broken seat, the same nonexistent WAYLAND_DISPLAY=wayland-y6, and the same config. None of them selected headless (AQ_BACKENDS does not exist in libaquamarine.so.0.16.0, confirmed by strings plus grep; WLR_BACKENDS does not exist either), none supplied a DRM fd, and none pointed the Wayland backend at a real socket. The deterministic repeat proves the failure is stable, not that the space is exhausted.

What it would take to earn the stronger verdict: either (a) a seat actually opens (seatd -u or seatd-launch-as-root, with SEATD_SOCK set and the open logged) and the run still dies at the allocator with a DRM fd supplied, or (b) a direct demonstration from the shipped binary or a run with AQ_TRACE=1 that the headless backend is requested, starts, and returns drmFD -1. Y6 did neither. Until one of those exists, the honest verdict is HEADLESS-AS-RUN DEAD, HEADLESS UNTESTED for the untried paths. Council A and Council B agree with each other on this point and both are right against Y6's headline.

A secondary count error rides on the same collapse: the report says attempt 4/5 contain the Aquamarine tail and attempt 5 is the most complete. All five contain the tail (verified by grep across all five reports), and attempt 3 is the most complete (extra logind line, verified in 217712.txt, absent from 219789.txt).

### Attack 3: Council A's Path A is broken as written in two independent ways

Council A is the strongest paper of the three on mechanism, and its Path A still fails its own evidence standard twice.

First, AQ_NO_KMS_REQUIREMENT is not in the shipped binary. I ran grep -a -c for the full literal against /usr/lib/libaquamarine.so.0.16.0: count 0. The only match for the AQ_NO_KMS prefix is a truncated fragment, AQ_NO_KMS_REQUIR, once. By Council B's own method (strings proves no literal env name in the binary), the variable Council A prescribes as half of Path A fails the same test Council B used to kill AQ_BACKENDS. AQ_DRM_DEVICES is present (confirmed, with the hint string about disambiguating render nodes), so the render-node half of Path A survives, but the KMS half is wiki-sourced, not binary-verified for Aquamarine 0.16.0 as shipped. If the variable does not exist in this build, Path A as specified silently drops its KMS waiver and the render-node attempt runs without it, which changes what a failure would mean. Council A never greps for the variable it prescribes.

Second, seatd-launch cannot do what Path A asks unprivileged. /usr/bin/seatd-launch is -rwxr-xr-x root root: no setuid bit (verified). Its own man page says seatd requires root privileges, achieved through SUID of seatd-launch or by running seatd-launch as root. Neither condition holds for a run as user. Council A never mentions this. The only way to run it is sudo, and then the man page's next sentence bites: seatd-launch drops privileges from the effective user to the real user before running the command, and if the real user is root, that is a noop. Under sudo, the nested Hyprland itself runs as root. A root nested compositor is a different experiment from every Y6 attempt: root can open /dev/dri/card1 and card2 directly (root:video 660, user not in video), root-owned runtime dirs and crash reports, and a root seatd socket. A success under sudo would not prove an unprivileged seatd seat works, and a failure would be ambiguous between seat, DRM, and root-environment causes. The clean seatd fix is the one Council A mentions in passing and never elevates: seatd -u user (the -u flag exists, verified in seatd -h), which chowns the socket to the user while the nested process stays unprivileged, plus SEATD_SOCK if the socket path differs. Path A should be rewritten around that, with seatd-launch-as-root as a separate, explicitly-root variant, not presented as a one-command unprivileged fix.

A third, smaller break in the same path: the AQ variables address the DRM and allocator stage, which in every observed log is downstream of the seat failure (Failed to open a session, then DRM Backend failed, then no allocator). AQ_DRM_DEVICES cannot fix a DRM failure caused by a missing seat. Council A pairs the vars with a seat fix, so the combination is coherent, but the paper's section framing (the render-node path addresses the allocator wall instead of only the seat wall) invites reading the vars as an independent fix. They are necessary-but-not-sufficient, and they fix a failure Y6 never isolated. Any Path A run must log the seat open first; if the seat step fails, the DRM result that day proves nothing about render nodes.

## More attacks on the reproduction design (silent wrong answers)

The design can fail loudly (nested crash), but the dangerous outcomes are the quiet ones. Each of these produces an answer that looks like a result and is not.

1. No animated backdrop is defined inside the nest. The 20/11 incident is LIQUID plus an animated backdrop. The nest's default background is static. The design says to capture the foot window over the backdrop and to count 32 frames 1 s apart, but it never says what produces motion inside the nest (no wallpaper client, no video, no animation source is named or launched). With a static backdrop, 32/32 identical frames and 0 callbacks is a vacuous pass: it proves a static scene does not flicker, which nobody disputed. NOT reproduced would be meaningless, and REPRODUCED would be impossible. The independent variable is missing from the design.
2. The wrong plugin version silently gates everything. The GO criterion requires version 1.1.1-cu.1, but backup 1 is an Oct 9 build (backup dir epoch 1791544423 converts to 2026-10-09 18:13:43 +07) against a Hyprland built Nov 9 (0.57.2). No check was ever made of which Hyprland version backup 1 targets, and backup 2 (30,622,520 bytes, different hash) was dismissed as different build, not used, without a compat check against 0.57.2's plugin API. If backup 1 is stale for 0.57.2, the plugin refuses to load, the design hits NO-GO on version grounds, and the nest itself is never judged. The version gate conflates nest success with plugin-build identity. Identify the load-compatible .so first (by loading it, not by matching the vendor hash), or demote the version check to a recorded observation.
3. The optics profile may be applied to the wrong thing or not at all, with no detection. The live setup applies the profile through a setup.py hook when exactly one hyprglass of the right version is loaded. The design instead sources a copy of the lua file after the plugin line and reloads the nest, with no check that the reload succeeded (nested hyprctl still responds, nest PID alive) before proceeding. The lua file itself sets global layers mask_mode region (line 26) and separately calls layer() with mask_mode contour for namespace computer-use-indicator (line 37). The pill inside the nest gets contour only if it uses that exact namespace. The design never states the nested pill's namespace or how layers.active=true is verified per layer. A status check that reads only global flags can pass while the pill itself is unprofiled.
4. The pill may run against the live env instead of the nest. indicator.py's _status honors a passed env dict (HYPRLAND_INSTANCE_SIGNATURE plus WAYLAND_DISPLAY, verified in the source), but the design names no launch command, no entry point, and no state dir for the nested pill run. The indicator's session state (session.json, indicator-<token>.sock) lives in a state dir the design never separates from the live session's. If the nested pill shares the live state dir, its socket and token collide with the live indicator, or the nested run silently talks to the live pill and measures the live compositor. Council B flagged this as pre-verify; I add that the code path that would collide (endpoint plus session.json) is real and the design gives it no answer.
5. grim can capture the wrong output. Step 4 is written under the checks env header (nested runtime dir plus wayland-y6), which is correct, but the step's own text says only use grim with the nested WAYLAND_DISPLAY. Run without the matching XDG_RUNTIME_DIR, grim looks for wayland-y6 under the live runtime dir, fails, or (if WAYLAND_DISPLAY is left at the live value) captures the live screen, including Zen, and the frames get counted as nest evidence. The command must pin both variables every time. The same two-variable discipline applies to every hyprctl call inside the nest.
6. The nested window is not a 960x540 window, and it is not harmless to a concurrent runner. monitor=WAYLAND-1,960x540 sets the nest's virtual output size. The live window that appears is sized by the live Hyprland tiler, which will tile it and resize Zen, not float it at 960x540. There is no live windowrule in the design to float it. The focus steal is therefore also a layout shift: Zen geometry changes, hasFocus and visibility observations of any concurrent runner are polluted even if nobody clicks. Precondition 1 guards only run start, and there is no mid-run abort rule if a runner starts or the nest grabs focus mid-run (Council B gap 1, endorsed). The design's do not click it instruction does not prevent any of this.
7. The Wayland parent protocols are assumed, not checked. The shipped binary's strings show the Wayland backend failing on Missing protocols and initDmabuf: failed to get default feedback. The design assumes the live compositor supplies everything Aquamarine's Wayland backend needs (dmabuf plus shell plus seat). No step lists the required protocols or checks them before launching foot. If the backend rejects the parent on protocols, the nest dies at the same place as attempts 1 to 5 and the design records it as a nest failure rather than a parent-protocol failure.
8. The handover precondition is stale on arrival. Owner away, handover confirmed 18:24, still in force is asserted as a standing fact. A handover is time-bound and the owner has since been active in the window (runners Y4d and Y8 started after 18:24). Any later run must re-confirm handover at run time (Council B, endorsed). The design also borrows live activation needed ~8 s for first-use shader compile from the live session; the plugin was never loaded anywhere in this probe, so the 30 s shader budget is a borrowed number, not an evidenced one.

## Safety record attack

Y6's safety section says the live session was untouched and verified unaffected at 18:23:33. The outcome half is true and I re-verified its durable parts: live PID 1515 started Nov 21 15:17:25 and is still the only Hyprland process; with the explicit live env, hyprctl version responds 0.57.2 and plugin list shows only hyprbars 1.0; no seatd process survives; /run/seatd.sock is gone; all five per-instance hyprland.log files are 0 bytes; all five crash reports exist with matching PIDs and times in coredumpctl (18:20:16, 18:22:00, 18:22:35, 18:23:03, 18:24:52).

The action half is not untouched, and the report downplays three touches:

- Attempt 3 executed code inside the live compositor process. hyprctl dispatch with Lua os.execute runs the Lua chunk in-process in live Hyprland, and the dispatched script launched a child that crashed 13 seconds later. The dispatch form is precedented in repo history (worker-m-agy-auth-log.md:82 uses the same function() os.execute form), and the mechanism worked, but it is execution inside the live session by definition, not isolation from it. The report calls attempt 3 a Hyprland child via dispatch and separately claims the live session was untouched; those two sentences contradict each other unless untouched is narrowed to undamaged.
- seatd ran as root for 107 seconds (seatd.log: started, then stopped after 00:01:47) and created a VT-bound seat seat0 while logind session 2 holds the same VT. Council A already flags seatd/logind coexistence as unverified. The report records the start and the kill but never names the coexistence risk it created, and its socket-mode and PID details have no surviving record (see verdicts table).
- Five SIGABRT coredumps of /usr/bin/Hyprland produced a desktop crash notification the owner saw at ~18:23, attributed in the report to all five attempts when only four dumps predate the notification. A crash notification naming Hyprland is indistinguishable to the owner from a live-session crash at first sight. That is a real user-visible touch, and the standing rule it produced (Muses watch crash notifications themselves) exists because the touch happened.

None of this proves harm. It proves the safety claim must be reworded from untouched to survived undamaged, with the three touches disclosed. Council B's CONFIRMED on safety is outcome-scoped and survives; Y6's wording does not.
