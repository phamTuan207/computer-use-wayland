# Council Member B (fix design): deterministic runner fix for the hidden-body incident

Verdict: the runner can be made deterministic without removing the cause, but only if it stops treating "body hidden" as one undifferentiated failure. The fix is a diagnose-first ladder in `run_live.py`, with the bootstrap tab as the fallback, not the fix. Y4's `bootstrap_tab` is kept and strengthened. Y4's `ensure_visible` recovery is replaced, because its own evidence shows it does not work. Class removal via eval is allowed only as a logged, bounded, last step before fallback, never as a silent pass. The non-code blacklist is worth trialling in parallel, but it is not the primary fix.

Scope: design only. No implementation in this paper. No driving of the owner's Zen was done for this paper. All claims cite the evidence pack (`improvements/worker-y4b-evidence-pack.md`), `tests/realistic/run_live.py` lines 80-300, and `tests/realistic/run_agyq2.py` commit 03307cd.

## 1. Fix design, numbered steps, in run_live.py terms

Add three functions to `run_live.py`, and change two call sites in `run_agyq2.py`. No other test file changes.

1. Add `diagnose_body(d)` to `WD` in `run_live.py`. One `eval` call, one dict returned. It reads, in this order, `documentElement` classList, body computed style, body inline style, transition state, and corroborating state. Full spec in section 2. It never clicks, never types, never navigates, never switches tab.
2. Add `classify_hidden(diag)` in `run_live.py`. Pure function, no browser call. Returns one of `VISIBLE`, `TZ_STUCK_V1`, `TRANSITION_FROZEN_V2`, `OTHER_HIDDEN`, `FIXTURE_FAILURE`. Classification rules in section 2. `OTHER_HIDDEN` and `FIXTURE_FAILURE` never enter the Transparent Zen recovery ladder.
3. Add `ensure_visible(d, r, label)` to `run_live.py` as the replacement for Y4's version in `run_agyq2.py`. Same name and call sites, new internals. It calls `diagnose_body`, then runs the recovery ladder in section 3, with a hard total budget of 8 seconds per tab opening. It returns `(ok, diag, intervention)` where `intervention` is `None` or a short string such as `"waited-class-cleared"`, `"removed-tz-hidden"`, `"repaint-recovered"`, or `"fallback-bootstrap-tab"`. Every call logs the full `diag` dict and the `intervention` to the JSONL log. If `ok` is False, it raises nothing itself; the caller decides.
4. Change `WD.goto` in `run_live.py`. After the existing 1.0 s settle, call `diagnose_body` once. If `VISIBLE`, return as today. If hidden, call `ensure_visible` immediately, before any `click`, `type_text`, or `find`. `goto` must not return a hidden page as if it were ready. This is the single choke point, so every runner that uses `goto` gets the fix, not only `run_agyq2.py`.
5. Change `WD.new_tab` in `run_live.py`. After the existing switch verification, call `goto`, which now includes step 4. If `ensure_visible` fails inside `goto`, `new_tab` must not append the handle to a "visible" list and must not let the caller proceed. It records the failure in `r` if a runner is attached, or raises `RuntimeError` with the `diag` dict in the message. It must not close the tab here; the caller owns fallback.
6. Change `WD.__enter__` in `run_live.py` to fix the known orphan bug. Wrap the session POST in try/except. On any raise, call `self._cleanup()` before re-raising, so a 30 s session timeout never leaves a geckodriver with no parent. Also write the geckodriver PID to `/tmp/wd-<WD_PORT>.pid` on start and remove it in `_cleanup`. Also stop sending geckodriver stdout/stderr to DEVNULL. Send them to a per-run log file, for example `/tmp/wd-<WD_PORT>.log`, so a future timeout has evidence. This is a precondition for section 4.
7. Add `preflight()` in `run_live.py`, called once at the start of `main` in every runner, before `start_server` opens any tab and before `bootstrap_tab` runs. Spec in section 4. If any preflight check fails, the runner exits with code 2 and prints the failing check. It never opens a tab after a failed preflight.
8. Change `open_fixture` in `run_agyq2.py`. Keep the shared-tab structure, but replace its current `ensure_visible` call with the new `run_live.py` version, and handle the return value. If the shared tab is `TZ_STUCK_V1` or `TRANSITION_FROZEN_V2` and recovery fails, call `rebootstrap_tab` once (step 9) and retry `open_fixture` once on the new tab. If the second tab also fails, raise `RuntimeError` with prefix `INFRA: hidden-body` plus the `diag` dict, and set `r.details["infra_blocked"] = True`. Do not record this as a fixture failure.
9. Add `rebootstrap_tab(base, old_tab)` in `run_agyq2.py`. It does not close `old_tab`. It finds a fresh `about:blank` tab, or creates one with `window/new` and runs the full diagnose and recovery ladder on it. If no usable tab exists after one creation attempt, it raises `INFRA: hidden-body` and the suite aborts. It returns the new handle and logs both handles.
10. Change `Runner.summary` handling in `run_agyq2.py` only by addition, not by changing the pass rule silently. Keep `pass` as `len(self.failures) == 0`. Add `r.details["tz_intervention"]` whenever step 3 returns a non-None intervention, and `r.details["infra_blocked"]` whenever step 8 sets it. A test that passed only after `removed-tz-hidden` is still a pass, but it is a flagged pass, visible in the JSON summary. A test that was blocked is a fail with an `INFRA:` failure string, never a pass, never silently skipped. The suite abort rule stays as Y4 fixed it: only session-creation failures count toward the abort threshold, plus a new rule, two consecutive `INFRA: hidden-body` blocked tests abort the suite. One blocked test does not abort the suite.
11. Change `WD.visible(css)` in `run_live.py` only by adding a body guard, not by changing its contract. Before checking the target element, if `diagnose_body` shows the body hidden, return False immediately. This stops a misleading "element not visible" from being read as a fixture failure when the whole body is hidden. Do not change the rect, display, and visibility checks for the target element itself.

## 2. Detection: the exact check

### 2.1 What to read, and in what order

One eval, one snapshot, no separate evals that can race each other. The eval returns a dict with these fields, in this order:

1. `readyState`: `document.readyState`. If not `complete`, the page is not ready. Do not classify as hidden-body yet. Wait for `wait_ready` first, as `goto` already does.
2. `htmlClass`: `document.documentElement.className` as a string, plus `tzHidden`: `document.documentElement.classList.contains("tz-hidden")` and `tzInitialized`: `classList.contains("tz-initialized")`. Class first, because it decides V1 vs V2. The pack shows `initLoadingScreen` adds `tz-hidden` synchronously at `document_start`, and `removeLoadingScreen` removes it 500 ms after being called. If the class is present, the extension loading screen is still on by its own mechanism.
3. `bodyExists`: `!!document.body`. If false, this is not a hidden-body case. It is a load failure.
4. `bodyVis`: `getComputedStyle(document.body).visibility`. `bodyOpacity`: `getComputedStyle(document.body).opacity` as a float. `bodyDisplay`: `getComputedStyle(document.body).display`. `htmlVis`: `getComputedStyle(document.documentElement).visibility`. The pack symptom is body hidden, opacity 0, html visible, rect non-zero, display block. All four must be read together.
5. `bodyInlineVis` and `bodyInlineOpacity`: `document.body.style.visibility` and `document.body.style.opacity`. The pack rules out inline style in both incidents. If inline style is set, the cause is not the extension stylesheet, and the case leaves the Transparent Zen ladder.
6. `bodyTransition`: `getComputedStyle(document.body).transitionProperty`, `transitionDuration`, and `transitionDelay`. This is the V1 vs V2 tiebreaker after class. Under `:root.tz-hidden body` the CSS sets `transition: none`. Under the normal rule it sets `transition: visibility .25s, opacity .25s, background-color .25s`. So a present class plus `transition: none` is consistent with V1. An absent class plus `visibility .25s` is consistent with V2, where the class was removed but the transition never advanced.
7. `bodyRect`: `document.body.getBoundingClientRect().width` and `.height`. The pack symptom has non-zero rect. A zero rect points elsewhere.
8. `innerTextLen`: `document.body.innerText.length`. Corroboration only, never a gate. Hidden body gives empty innerText. A visible fixture with genuinely empty text is possible in principle, so this field is logged but never used alone to declare hidden or visible.
9. `hasFocus`: `document.hasFocus()`. `visibilityState`: `document.visibilityState`. The pack shows both are normal during the incident, so they are logged to rule out a background-tab explanation, not used to declare visible.
10. `url`: `document.URL`. Logged so a diagnosis can never be attributed to the wrong tab later.

Sample the dict twice, 300 ms apart, only when the first sample is hidden. The second sample distinguishes a transition in flight (opacity rising, class just cleared) from a stuck state (identical values twice). Do not sample more than twice in detection. Polling belongs to recovery, not detection.

### 2.2 Classification rules

- `VISIBLE`: `bodyVis == "visible"` and `bodyOpacity >= 0.99` and `bodyDisplay != "none"` and `bodyRect` non-zero. `tzHidden` may be true or false here only in the first 500 ms after load, before `removeLoadingScreen` fires. After the 1.0 s settle in `goto`, a visible body with `tzHidden` still true is logged as a warning but still counts as `VISIBLE`, because Marionette can interact with it. Do not treat a stale class as hidden when computed style says visible.
- `TZ_STUCK_V1`: `tzHidden == true` and `bodyVis == "hidden"` and `bodyOpacity == 0`. This matches the extension mechanism exactly: the class is on, the `:root.tz-hidden body` rule applies, transition is `none`. This is an extension loading screen stuck, not a fixture failure. Note the evidence caveat: R's probe_q05e reported "no class" in incident 1, but the probe output was not saved to disk, so the exact htmlClass value is unverified. V1 is therefore the leading mechanism for the class-present case, not a proven fact for incident 1.
- `TRANSITION_FROZEN_V2`: `tzHidden == false` and `bodyVis == "hidden"` and `bodyOpacity == 0` and `bodyInlineVis == ""` and `bodyInlineOpacity == ""` and `bodyRect` non-zero and `bodyExists == true`. This matches the pack V2 prediction: class gone, no rule matches, computed style still hidden. The pack notes V2 needs refresh ticks to have stopped entirely, not just throttled, because a 250 ms transition would complete within about 1 s even at 1 Hz. Whether a visible-window tab can have a fully stopped refresh driver is an open question for the council. V2 is therefore a hypothesis to test by the recovery ladder, not a proven fact.
- `OTHER_HIDDEN`: body hidden but neither V1 nor V2 fits. Examples: `bodyInlineVis == "hidden"`, or `bodyDisplay == "none"`, or `htmlVis == "hidden"`, or body rect zero. This leaves the Transparent Zen ladder. Log the full dict and treat as infra-blocked, not as a fixture failure, until a separate investigation explains it.
- `FIXTURE_FAILURE`: body `VISIBLE` by the rule above, but the target element is missing, has zero rect, has `display: none`, or has computed `visibility: hidden` on its own. This is the only class that is a real fixture or test failure. The body-visible check is what separates it from the extension case. A fixture that hides its own body deliberately would be misclassified here, but no fixture in this suite does that, and the fixture source contains zero occurrences of "visibility" per R's grep.

### 2.3 What detection must never do

Detection must never click, type, scroll, switch tab, or remove a class. It is read-only. It must never infer hidden from a single Marionette error string such as "element not interactable" or "could not be scrolled into view". Those errors also occur for a genuinely missing element. It must never use `visible("body")` alone as the diagnosis, because `visible` in `run_live.py` checks only rect, display, and visibility, not class, opacity, or transition, so it cannot distinguish V1 from V2 from a fixture failure. It must never run a stylesheet rule scan in the hot path. R's per-sheet scan was a diagnostic probe, not a runner check, and it is slow and can throw on cross-origin sheets. Class plus computed style is sufficient for the runner.

## 3. Recovery: exact steps, in order, with timeouts

Total budget: 8 seconds per tab opening, counted from the end of the 1.0 s settle in `goto`. Every step logs its start time, end time, and the `diag` dict after it. If any step returns `VISIBLE`, stop immediately and proceed with the test. Do not run later steps after success.

1. Wait and re-poll for the extension's own removal. Poll `diagnose_body` every 250 ms for up to 2.0 s. This covers the normal chain: `removeLoadingScreen` is 500 ms after being called, and the pack chain normally completes 0.5 to 1.5 s after load. If the class clears and the body becomes visible in this window, return `("waited-class-cleared", diag)`. This step applies to V1 and to V2 in flight. Do not remove the class during this window. The extension may still be about to remove it itself.
2. If V1 persists after step 1, remove the class exactly as the extension itself does. One eval: `document.documentElement.classList.remove("tz-hidden"); document.documentElement.style.removeProperty("--zen-logo-path"); return "removed";`. This is the only eval removal allowed, and only on the current test tab, only when `tzHidden == true` and the URL is a test origin. Log the intervention string `"removed-tz-hidden"` in `r.details`. Then wait 500 ms for the `visibility .25s, opacity .25s` transition to complete, and re-diagnose. If visible, return. If the class is gone but the body is still hidden, reclassify as V2 and go to step 3. If the class reappears, that means the extension re-added it. Do not remove it a second time. Go to step 4. Rationale: this mimics `removeLoadingScreen`, it does not touch fixture DOM, and it does not fake content. It is still an intervention, so it must be flagged, not hidden.
3. If V2, or if step 2 left the class gone but the body hidden, force a repaint. One eval, in this order: read `document.body.offsetHeight` to force reflow, then `requestAnimationFrame` twice, then `window.scrollTo(0, 1)` and back to `window.scrollTo(0, 0)`, then `document.body.scrollIntoView({block: "center"})` if body exists. Then wait 500 ms and re-diagnose. Repeat this step at most twice, total 2.0 s including waits. This step is a hypothesis, not a proven fix. The evidence against it is strong: switch away and back did not fix it in probe d, `window.focus()` plus 2 s did not fix it in probe_y4b, and the pack notes V2 needs refresh ticks to have stopped entirely. So step 3 is a bounded try, not a loop. If it fails twice, stop trying repaint tricks.
4. Fall back to the bootstrap tab. Do not open another `window/new` tab, because the incident affects `window/new` tabs specifically and a second new tab has the same risk. Switch to the shared bootstrap tab established by `bootstrap_tab`, `goto` the fixture URL there, and run `diagnose_body` plus steps 1 to 3 on that tab with a fresh 8 s budget. If the bootstrap tab is visible, return `("fallback-bootstrap-tab", diag)` and continue the test on that tab. If the bootstrap tab is also hidden after its own ladder, go to step 5.
5. Declare the test infra-blocked. Raise `RuntimeError("INFRA: hidden-body " + json.dumps(diag))`, set `r.details["infra_blocked"] = True`, and record the failure with the `INFRA:` prefix. Do not attempt a third tab. Do not retry the same fixture in the same test. The suite continues to the next test, which gets its own fresh session and its own ladder. If two consecutive tests are infra-blocked, abort the suite. The abort threshold is two, matching Y4's session-failure threshold, so a single incident does not kill a suite but a persistent incident does.
6. Never, at any step, use a real click on a fixture element as a recovery probe. Y4's log says the state "cleared by itself ~17:59, right after a real click in the reused tab". That click was in a tab that was already visible. A click on a hidden tab will fail Marionette's interactability check anyway, and a click that lands in the wrong tab is a user-tab risk. Recovery is eval, wait, repaint, and fallback only.

## 4. Preconditions that must hold before ANY tab is opened

`preflight()` runs once per runner invocation, before `start_server` and before `bootstrap_tab`. It fails closed: any check that cannot be verified is a failure, not a pass. It prints each check with ok or fail and the evidence.

1. Stale geckodriver sweep by PID, not by port alone. Read the pidfile `/tmp/wd-<WD_PORT>.pid` if present. List geckodriver processes with `pgrep -a geckodriver` and note each PID, its `--port` argument, its parent PID, and its start time. For the runner's `WD_PORT`, if a geckodriver is listening and its parent python process is alive, abort with "live runner holds port <WD_PORT>, pid <pid>". Do not kill it, do not steal the port, do not pick another port silently. If the parent python is gone, or the parent PID is 1, or the pidfile owner is dead, that geckodriver is an orphan. Log its PID, port, parent PID, and start time, kill it by PID with SIGTERM, wait up to 5 s, then SIGKILL if still alive, and verify with a second `pgrep` that it is gone. This is the incident 1 lesson: R found orphan PID 113280 on port 4446 with parent python long gone, killed it by PID, and the next new tab was visible. The pack stresses this is correlation, not proven causation, so the sweep is a hygiene precondition, not a claimed cure. Never kill by port number alone without checking the PID and parent first.
2. Lock state: Marionette single session. Check that port 2828 answers and that no other WebDriver session is active. The practical check is: `pgrep -f "geckodriver.*--port"` shows no live geckodriver other than the one this run is about to start, and the pidfile for this port is absent or stale. Also check that no other runner python process is running the same suite, by `pgrep -f run_agyq2.py` and `pgrep -f run_live.py` excluding this process. If another runner is live, abort. Do not share a Marionette session between runners. The pack notes BiDi and Marionette share a single session slot, and a leak blocks all remote control until Zen restarts.
3. Zen liveness: check Zen PID is alive, Marionette port 2828 accepts a TCP connection within 2 s, and the geckodriver status endpoint answers after start. If Zen is not alive, abort. Never start a run against a dead browser and interpret the failures as fixture failures.
4. Hyprland IPC responsiveness: run `hyprctl version` with a 5 s timeout. If it hangs or times out, abort before any tab is opened. The pack records Hyprland IPC unresponsive for the whole probe window in incident 2, and the owner input freeze followed at 17:59. Whether the IPC wedge caused incident 2 is unverified, but an unresponsive compositor is not a safe state to drive tabs in. A timeout here is a preflight failure, not a warning to ignore.
5. Owner-away check: do not drive tabs while the owner is at the keyboard. The check is two parts. First, require explicit authorisation for the run: the operator sets `LIVE_OWNER_AWAY=1` only after confirming the owner has handed the machine over, or the run is launched from a scheduled job the owner approved for an away window. Second, check for recent input if a reliable idle source is available on the machine, and abort if input was seen in the last 60 s. If no reliable idle source is available, the explicit flag in the first part is the check, and the log must record that idle time was not independently verified. Never infer "owner away" from silence alone, and never infer it from the absence of a Hyprland error. The 17:59 freeze, where the owner's physical keyboard and mouse stopped responding for about 1 min during probe tab navigation, is the reason this is a precondition, not a courtesy.
6. Fixture server and test origin: verify the fixture server root answers on its port, and that the base URL is a loopback origin (`http://127.0.0.1`). Do not run live tests against a non-loopback origin without an explicit override. This also bounds the blacklist discussion in section 7 to one origin.
7. Extension state snapshot, read-only: record the installed Transparent Zen version from the XPI filename, and record whether `about:blank` tabs are currently visible, by listing handles and reading `document.URL` only. Do not navigate, do not evaluate on user tabs. This snapshot is for the log, so a later incident can be compared to a known-good baseline. Do not read extension storage, do not change settings in preflight. Settings changes belong to section 7 and need a separate decision.

If any preflight check fails, exit code 2, print the failing check, and open no tab. A failed preflight is not a test failure and is not counted in the suite summary.

## 5. What the fix must NEVER do

- Never navigate, type into, click, evaluate on, switch to as a target, or close a user tab. The only tabs the runner may act on are handles in `WD.opened_tabs` and the single bootstrap handle that was verified as `about:blank` or a test-origin fixture URL. The existing `new_tab` comment in `run_live.py` already states this rule, because `geckodriver --connect-existing` does not switch to the new tab and an unswitched `goto` lands in the previously current tab. The fix must preserve that switch verification and extend it: every `switch` must verify the current handle equals the intended handle before any further action.
- Never dismiss the open alert on tab [4], and never touch that tab at all. The pack records an open alert on a user tab, "unexpected alert open" on eval. Any eval on that tab raises. The runner must catch that error, skip the tab, and never call `alert_accept`, `alert_dismiss`, or `alert_text` on it. The alert is the owner's, not the runner's.
- Never close a tab it did not open. `_cleanup` in `run_live.py` already closes only `opened_tabs`. The bootstrap tab must stay out of `opened_tabs`, as Y4 already does, and must be returned to `about:blank` at the end, not closed. `rebootstrap_tab` must not close the old tab either, even if the old tab is hidden. A hidden test tab is left for the owner or for a later manual check, not closed by the runner.
- Never fake a PASS. No step may mark a test pass when the body was hidden and no interaction occurred. No step may skip the body-visible check, or replace it with a weaker check such as readyState alone. No step may use `window.__agyVerify()` or `__fcckVerify()` as an oracle; the `run_live.py` header already forbids this because those hooks self-simulate and always pass. Any `removed-tz-hidden` intervention must appear in `r.details` and in the JSON summary. Any infra-blocked test must appear as a failure with an `INFRA:` prefix.
- Never remove `tz-hidden` on a user tab, on a tab whose URL is not a test origin, or on a tab that was not just diagnosed as `TZ_STUCK_V1`. Class removal is scoped to the current test tab only.
- Never kill Zen, never kill a live runner's geckodriver, never kill by port alone. Section 4 step 1 is the only kill allowed, and only for an orphan verified by PID and parent.
- Never retry without a bound. The 8 s ladder budget, the at-most-twice repaint, the once-only class removal, and the once-only fallback are hard limits. An unbounded retry loop is how a stuck runner becomes a stuck suite.
- Never drive while the owner is at the keyboard. See section 4 step 5.

## 6. Honest judgment of Y4's already-landed workarounds (commit 03307cd)

### bootstrap_tab: KEEP, and strengthen

Keep. This is the only workaround with direct positive evidence. Probe_y4c showed a pre-existing `about:blank` tab navigated to the q01 fixture gives a visible body, click OK, type OK, while new `window/new` tabs to the same fixture and to example.com were hidden at the same time. The mechanism is also consistent: a reused tab is not a fresh `window/new` document, so the extension's `document_start` loading screen path does not run again on it in the same way. The shared tab plus fresh session per test plus storage clear plus reload is a sound isolation model.

Strengthen in four ways. First, verify the reused tab before returning it: run `diagnose_body` on it after switching to it, and only return it if `VISIBLE`. Y4's version checks visibility only on the newly created fallback path, not on the reused path. Second, narrow the reuse match. The current order is `about:blank` first, then any tab whose URL starts with the test base. The second branch is too broad: a leftover probe tab is fine, but a tab that happens to be on the test origin for another reason is not proven to be a test tab. Restrict the second branch to URLs that are known fixture paths under the test base, and log the matched URL. Third, record the bootstrap handle and URL in the log at creation, and re-verify the handle still exists in `d.handles()` before each test. If the owner closed it, re-bootstrap instead of failing the test. Fourth, add the `rebootstrap_tab` path from section 1 step 9, so a bootstrap tab that goes hidden mid-suite does not end the suite. Without these, `bootstrap_tab` is a good workaround with an unverified reuse path and no recovery if the shared tab itself fails.

### ensure_visible: REPLACE the internals, keep the name and call sites

Replace. The current recovery is switch away to another tab and back, `window.focus()`, wait 2 s, re-check. The evidence shows this does not work. Probe d, switch away and back, did not fix it. Probe_y4b, `window.focus()` plus 2 s, did not fix it. Y4's own docstring admits the state cleared by itself around 17:59 after a real click in a reused tab, not because of `ensure_visible`. Keeping the current body as the recovery would be keeping a placebo that costs 2 s and, worse, switches to a user tab as the "away" tab. The current code picks the first handle that is not the test tab and switches to it. That is a user tab by definition in a live Zen with 22 pre-existing tabs. That switch is a focus steal, and the owner input freeze at 17:59 followed probe tab navigation in the same window. The switch-away step must be removed entirely.

What to keep from `ensure_visible`: the call sites, the name, the contract that it returns False when the body is still hidden, and the caller behaviour in `open_fixture` that raises instead of proceeding to click. The new version in section 3 keeps all of that, but its internals are diagnose, wait, class removal, repaint, and fallback, with logging. The 2 s unconditional sleep is replaced by the 8 s bounded ladder with per-step logging. The function must also stop using `getattr(r, "tab", None)` as an implicit contract. The tab handle must be an explicit argument, so a missing handle is a programming error, not a silent skip.

### Abort heuristic fix: KEEP

Keep. The first Y4 run aborted 0/2 because any error containing "session" counted toward the abort threshold, including step failures whose WebDriver URL contains `/session/<id>/`. The fix, only session-creation failures count, is correct and must stay. The new infra-abort rule in section 1 step 10 is an addition to it, not a change to it. Do not reintroduce substring matching on error text.

### Server-reuse fix: KEEP

Keep. Probing the runner's own fixture before starting a server avoids a double bind on the port. It is a minor correctness fix with no hidden-body relevance, and it does not change test behaviour.

## 7. Non-code options

### Blacklist the test origin in Transparent Zen settings: RECOMMEND as a parallel trial, not as the primary fix

The extension code supports a per-domain branch. `initDynamicTransparency` checks whether the domain is allowed, and `browser.storage.local.get("transparentZenSettings")` carries the settings. What the evidence does not show is whether the settings UI exposes a per-site disable, whether `127.0.0.1` can be added to it, and whether `enableTransparency` or `lightweightTransparency` is currently on. Those settings live in extension storage and were not read.

Recommendation: trial it as a diagnostic and as a scoped mitigation, in parallel with the code fix. Steps: read the settings schema from the installed extension storage, read-only, find the per-site list if one exists, add `127.0.0.1` to it if the UI or storage format supports it, run one probe tab, and record whether new tabs stay visible. If it works, keep the blacklist for live runs, because it removes the cause for test tabs without touching any other tab. If no per-site list exists, stop. Do not invent a settings field. The blacklist is scoped, reversible, and does not change the runner's ability to survive other extensions. Its weakness is that it depends on an unverified UI, and it does nothing for the next content script that hides the body at `document_start`. That is why it is parallel, not primary.

### Disable the extension during runs: RECOMMEND AGAINST as a standing procedure, allow only as a one-off diagnostic

Disabling Transparent Zen would remove the cause entirely for the run, and it is the fastest way to confirm causation: disable, open a `window/new` tab, check the body. As a diagnostic, with immediate re-enable and a log entry, it is legitimate. As a standing run procedure, it is not recommended. It changes the owner's browser environment for every run, it risks being left disabled if a run crashes, it requires driving the owner's Zen to toggle it, and it hides the bug instead of making the runner robust. The runner must survive any extension that injects a loading screen at `document_start`, not only this one. If the blacklist trial in the previous paragraph works, there is no need to disable the whole extension. If the blacklist does not exist, the code fix in sections 1 to 3 is still the standing procedure, and disable remains a diagnostic only.

### Run fixtures in a separate Firefox profile without the extension: REJECT for live runs

A clean profile would be deterministic, but it is not the live Zen. The live runs exist to measure the real environment the owner uses, including its extensions, and Marionette 2828 belongs to the live Zen. A clean profile run would prove the fixture works, which is already known, and would prove nothing about the live runner. Keep this option only for offline fixture validation, never as a substitute for a live run.

### Recommendation, in order

First, land the code fix in sections 1 to 3, because it is the only option that makes the runner deterministic in the real environment and survives the next extension. Second, trial the blacklist in parallel, because if it works it removes the cause for test tabs with a scoped, reversible change. Third, use disable only as a one-off diagnostic to confirm causation, then re-enable immediately. Do not adopt disable as the run procedure.

## 8. What the evidence does not show, and what would change this design

- Whether `documentElement` classList contained `tz-hidden` during either incident. R's probe_q05e collected htmlClass but the output was not saved. If a future incident shows the class absent while the body is hidden, V1 is weakened for that incident and the design must lean harder on the V2 repaint and fallback steps, not on class removal. If a future incident shows the class present, V1 is confirmed and step 2 becomes the primary recovery.
- Whether the stale-geckodriver kill caused incident 1 to clear. The clear was verified only on a new tab under a new session. The sweep in section 4 is hygiene, not a claimed cure. If a future incident clears without any geckodriver kill, the sweep stays but the causal claim stays unmade.
- Whether the Hyprland IPC wedge caused incident 2, or was coincidence, or was an effect. The journal shows no Hyprland errors 17:50 to 18:02. The preflight IPC check in section 4 is fail-closed because an unresponsive compositor is unsafe to drive in, not because causation is proven.
- Whether the open alert on tab [4] plays any role. Tab-modal alerts block JS in that tab only, and there is no evidence it affects other tabs. The fix never touches that tab, so this question does not change the design unless future evidence shows a cross-tab effect.
- Whether the extension's `enableTransparency` and `lightweightTransparency` settings are on. If they are off, the V1 chain should have called `removeLoadingScreen` immediately, which would weaken V1 and point toward V2 or another cause. Reading the settings is the first step of the blacklist trial.
- Whether the repaint in section 3 step 3 ever works. The evidence against it is strong, and the step is bounded to two tries for that reason. If it never works in practice, remove it and go straight from class removal to fallback. If it works once, log the exact `diag` before and after so the council can tell V2 from a coincidental clear.
- Whether the old hidden tabs stayed hidden after the incidents cleared. Both incidents verified the clear only on a new tab. The fix does not need this answer, because it never reuses a hidden tab, but a future probe that re-checks an old hidden tab would settle whether the state is per-tab sticky or global.
