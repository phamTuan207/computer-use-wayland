## 0. The measured baseline every rank in this plan is anchored to

- W-PROF, 4 held-out tasks, all SUCCESS, combined 289.9s. Clean tasks P2, P3, P4: mean wall 36.4s, mean model think 34.2s (94 percent), mean broker service 1.4s (4 percent).
- Think split on clean tasks, scaled to a 100s task: think before act 14.9s mean (41 percent, so about 41s per 100s), think before first observe 7.7s (21 percent), think before verify observe 6.7s (18 percent), think before windows 4.9s (13 percent).
- Scripted zero-thinking harness floor: 2.116s start to verified end state (floor-probe2.sh, same loop shape). A perfect harness saves at most about 2s per task, about 2 percent of a 100s task. This matches the Track 1 verdict (stay Python, Rust rewrite not worth it).
- 10x review anchor: best tc02 about 100s vs 10s target; think-observe-think loop 87 to 95 percent of task time; local broker transactions about 13s of a 100s task, so making them free gives at most 1.15x.
- Consequence: any idea that only cuts local milliseconds is capped at about 2s per task on the profile floor, or about 1 to 2.5s per 100s on the W-HOT reference mix. Any idea that cuts model think calls can be worth tens of seconds. Ranking below follows that order, not novelty.

## How to read the savings

- MEASURED means the number comes from a cited source on that source's benchmark, or from a laptop or VM timing in the source report. It is not a tc02 number unless it says so.
- ESTIMATE means a calculation from the baseline above, with the reasoning shown in the source report. Estimates are labelled as such in every row.
- NOT ADDITIVE: M1, M2, M3, M5, M6, M10, M12, and M17 all attack the same think calls. Stacking them does not stack their savings. Prototype and measure each one alone first, on the same held-out tasks, before any combined claim.
- A saving stated in seconds per 100s task is the ranking unit for the savings column, but the ROW ORDER is by expected MODEL THINK-TIME reduction (re-ranked 2026-11-18), not by end-to-end saving and not by harness time. A saving stated in local ms is a local saving only, and is labelled local.

## 2. Conflicts resolved

### Local grounding model size, W-PLAN vs W-OBS

- Verdict per size, on the RTX 4050 laptop GPU with 6GB VRAM, 32GB RAM. RE-RANKED 2026-11-18 by the merged prior-art survey (grounding angle): Ferret-UI Lite 3B is FIRST, UI-TARS-1.5-2B is SECOND. The original plan had them the other way round; the grounding survey reverses it on Pro accuracy per parameter.
  - Ferret-UI Lite 3B: FITS, FIRST candidate for M10. ScreenSpot-V2 91.6 percent, ScreenSpot-Pro 53.3 percent, OSWorld-G 61.2 (abstract) vs 55.3 (body table), an internal inconsistency in the paper, quote the range and re-check. On Pro it beats UI-TARS-1.5-7B (49.6 percent) by over 15 points despite being 3B. Grounds well and plans poorly (GUI navigation only 19.8 percent on OSWorld), which is exactly the split the cascade wants: ground local, plan with Luna, never let the small model plan. Prototype workers must load it on the laptop and report actual VRAM and per-call latency before building around it; no survey in this track loaded any local model, so the fit is a size judgment, not a measured load test.
  - UI-TARS-1.5-2B: FITS, SECOND candidate for M10. About 2.5GB VRAM at int4, TTFT about 120ms on a 4090 at int4, warm p50 91ms in the Utter measurement on an RTX 3090 Ti. Ahead of Ferret-UI Lite on ecosystem maturity and Qwen2.5-VL tooling, behind it on Pro accuracy. Accuracy on ScreenSpot-Pro is UNMEASURED for the 2B in the sources found; the 7B scores 49.6 percent on ScreenSpot-Pro and the largest size scores 61.6 percent, so cite per size, not per family. A 20-sample local grounding test on his apps, including Vietnamese dialog text and small menu rows, is the cheapest way to get a number before building the cascade around it.
  - UI-TARS-1.5-7B: BORDERLINE, rejected as the default. About 6GB VRAM at int4, TTFT about 250ms on a 4090. W-OBS rejects 7B VLMs on this laptop: 7B needs about 17GB at BF16 and about 4.8GB at Q4_K_M for weights alone, before the vision tower and KV cache, so it does not fit comfortably and would be slower than the API call it replaces. W-PLAN lists it as borderline, not as the pick. Resolution: do not prototype the 7B as the grounder. If Ferret-UI Lite 3B fails the accuracy test, try UI-TARS-1.5-2B next, not the 7B.
  - Mage-VL-Cowork 4B: DOES NOT FIT unquantized, 9.48GB in bf16. Needs Q4 or GPTQ before it can run locally at all. Do not prototype until quantized.
  - Detection plus OCR as a pre-grounding pass (W-OBS R12): YOLO icon_detect v3 is MIT licensed (v1 is AGPL-3.0, do not use v1), about 50MB, ESTIMATE 50 to 150ms per frame on the RTX 4050, plus Tesseract or RapidOCR for text. This is the only local-model work worth measuring if the 2B grounder fails, and it is a candidate inside M10, not a separate prototype.
  - OmniParser v2: parse-all-elements is a different question from ground-by-query (about 1.4s per element in one synthetic benchmark vs about 6.9s for UI-TARS there, 99.3 percent detection vs 70.6 percent). Do not swap them blindly.

### Batching, blind vs validated

- All three reports agree: blind execution is REJECTED (10x review, W-OBS section 4, W-WEB idea 3). The adopted form is always prediction plus live validation plus early exit, M3. A batch that cannot be validated per action before execution is not a prototype, it is the rejected idea under a new name.

### Prompt caching, provider vs Codex route

- W-PLAN R3 numbers (up to 85 percent latency and 90 percent cost reduction on the cached prefix, break-even at the 2nd reuse) are provider-level MEASURED numbers. Whether they apply to the owner depends on the Codex CLI subscription route, which W-PLAN could not verify from public sources. ### Screenshot format, JPEG vs PNG

- W-OBS measured on this VM: JPEG q85 is LARGER than PNG level 1 on a text screenshot (309,828B vs 239,095B) and adds halos on glyphs. W-WEB idea 9 agrees: JPEG only helps upload time, disk, and the 10MB per-image API cap, never token count. Resolution: PNG level 1 stays the default for text UI. ## 3. Top 5 prototype picks

Rules for all five picks: prototype on the speed-swarm branch, never on main; measure alone first, never stacked; fresh held-out tasks only for the success claim (the sealed held-out cases, not tc02 variants the implementer has seen); a prototype that raises the misclick rate, the refusal rate, or the session-death rate fails even if it is faster; no prototype touches ownership, cancellation, verification, or brokered keyboard input (see the invariants under each pick).

Measurement method for all five picks, identical to W-PROF:

- Tasks: the same 4 held-out tasks W-PROF ran (P1 C-03, P2 E-04, P3 B-01, P4 A-01), plus at least 2 fresh held-out tasks from the sealed set for any success claim. Run each task once per arm (baseline arm, then prototype arm), same model (Codex gpt-6-luna, max reasoning, full access, on the laptop), same optimized discipline (one observation, ground all controls, batch actions in one act request, re-observe only to verify).
- Records: same shape as `~/workspace/speed-profile-20261118/records.jsonl` (87 lines in W-PROF): one JSONL record per request with submit and result timestamps, think-before timestamps from a decisions log, request service time, images and bytes, refusals, and the verify observation. Write new records to a fresh directory in the same style, for example `/tmp/speed-profile-20261118/` style JSONL under a new dated directory, never by overwriting the W-PROF records. Report wall time session start submit to verified end state, think total, service total, think-before-act, think-before-first-observe, think-before-verify, think-before-windows, request count, image count and bytes, refusals, misclicks, session deaths.
- Floor probe: re-run the scripted zero-thinking floor probe (floor-probe2.sh shape: start, windows, observe screen, observe window, act with one harmless empty command, observe window, finish, back to back, no model calls) on each prototype arm, so a harness change reports its floor separately from a think change.
- Decision rule per pick: ship only if the prototype arm beats the baseline arm on wall time AND does not worsen refusals, misclicks, or session deaths. Report the per-arm table, not a single number.

### Pick 1. Code execution as the action (M1)

- Why first: the single biggest lever in the crawl. CONSERVATIVE BOUND (re-ranked 2026-11-18): OpenGCUA code execution ALONE vs GUI plus CLI baseline is plus 6.1 points and minus 14.8 percent steps (arXiv 2610.22200, 82 offline tasks, 8 frontier models). The 53.0 percent fewer steps figure is the FULL configuration, which mixes batching and code, and must NOT be used as the planning number. CoAct-1: 10.15 vs 15.22 steps (OSWorld). CLI beats GUI on steps independently: Gu et al. (arXiv 2606.19388) CLI oracle 10.7 steps vs 18.6 for GUI agents on AndroidWorld, and Claude Code on Opus 4.7 reaches 71.8 percent with shell access and no mobile training. It removes whole think cycles rather than shaving them, and it is distinct from the adopted checked plans: the model writes the program at runtime, with loops and branches that react to intermediate results inside one call, while a checked plan cannot loop over an unknown number of rows.
- Exact files to change:
  - New controller module, for example `scripts/code_exec.py` (new file, do not edit `scripts/cu.py` for the interpreter itself), plus a thin executor-side prompt and schema change in the controller that calls it (the executor lives outside the repo in Codex, so the repo change is the interpreter plus its tool definition, not the model prompt file).
  - `scripts/cu.py`: only the narrow seam that lets the interpreter call the existing brokered primitives (observe, act, windows, browser, a11y) through the same code paths `desktop_act` and `observe` already use. No new input path.
  - `scripts/plans/tc02.schema.json`: extend the schema only if a program step needs a new field, otherwise leave it alone.
- Exact change:
  - A persistent local Python interpreter on the laptop, state carried across turns, that runs one short program per model call. The program may call only an allowlisted API: `observe()`, `act([...])`, `windows()`, `read_file()`, `assert_state()`, plus loops, conditions, and asserts in plain Python. Element IDs are bound to delivered observations and invalidated on reset. Every program must end with an executable verification: an assert that checks the postcondition (for example the file now reads Saved, the expected bytes and SHA match), and a GUI fallback when code cannot do it.
  - The model emits the program plus a one-line intent, not a free-form action list. The interpreter runs it, stops at the first failed assert or failed live validation, and returns the partial result plus the observation at the failure point, so the supervisor replans from there.
  - Sandbox guard: no unbounded programs (wall-clock budget per program, step budget per program, both enforced by the interpreter, not by the model), no shell commands outside the allowlist (no `os.system`, no `subprocess`, no network, no file writes outside the task target path), no destructive commands. A program that tries any of these fails closed with no side effect.
- What NOT to change:
  - Ownership, lease, generation, cancellation (cancel latch, `check_cancel`, idle timeout), and explicit finish stay exactly as they are. The interpreter never bypasses them.
  - Verification stays: the final state is verified from an exact source (file bytes and SHA, DOM text, a11y flags) plus a final observation image, never from the program asserting its own success.
  - Brokered keyboard input stays: typing goes through the existing `wtype` path in `desktop_act`, never through a direct write, AT-SPI setter, clipboard injection, or browser fill that skips the broker.
  - The pointer miss check (over 3px refuses the click) and the screen-changed refusal stay. A program may not disable them.
- Expected saving: ESTIMATE, conservative, from the code-alone ablation: on code-able subtasks, think calls fall by about one third to one half, which is roughly 10 to 17s of the 34.2s think budget (planning survey section 7, using the minus 14.8 percent steps bound). The earlier 35 to 50s per 100s estimate was derived from the 53 percent full-config number and is now the full-config ceiling only, not the planning number. MEASURED precedent is step count, not wall time, so the prototype must report wall time, not steps.
- How to measure: baseline arm vs code-execution arm on the same held-out tasks per the method above. Report model calls per task, steps per task, output tokens per task, wall time, think total, and misclicks. Success is fewer model calls AND lower wall time with no rise in misclicks or refusals. If wall time does not fall even though steps fall, report that plainly: the saving is in steps, not in time.

### Pick 2. Subgoal-only verification: drop per-step judge and reflection, with the reasoning dial (M2 plus M12)

- Why second: MEASURED planning is 50 to 75 percent of latency, judging 22.5 percent, reflection 33.6 percent (OSWorld-Human, 39 tasks, Agent S2 and GTA-1). The merged survey strengthens this with the full OSWorld-Human finding: planning plus reflection together account for 75 to 94 percent of total task latency, and each successive step can take up to 3x longer than steps at the beginning as context grows. Screenshot-only history does NOT improve performance; only text-based action history helps, so this pick also adopts text history over image history: keep only the last 1 to 3 screenshots in full, carry the rest as compact text. ESTIMATE 20 to 35s on a 100s task. This is a prompt and harness rule change, no new model, no new dependency. It is the cheapest think cut after pick 1, and it is not additive with pick 1, so measure it alone.
- Exact files to change:
  - Executor prompt and controller config (outside the repo in the Codex invocation, plus the repo-side controller that enforces the rule, `scripts/tc02_controller.py` and `scripts/plans/tc02-v1.json` as the example procedure): add a call-budget rule, no judge or reflect call inside a subgoal, one verification per subgoal at its postcondition, which the checked plans already define.
  - Reasoning dial: a config flag per supervisor level in the controller invocation. Level 1 (deterministic procedure): no model call. Level 2 (bounded routine decision): Luna at low effort, strict JSON schema output (action plus target plus confidence), max output tokens capped. Level 3 (genuine ambiguity, recovery, new procedure): Luna at max effort, as today. Structured outputs make the answer machine-checkable, so a malformed decision fails closed instead of becoming a misclick.
- Exact change:
  - Delete the per-step judge and reflect calls from the loop. After each action batch inside a subgoal, run only the local deterministic checks (postcondition, file bytes and SHA, window and dialog class, AT-SPI validation from M3). Call the supervisor only when a subgoal postcondition fails, when the state is genuinely ambiguous, or when a new procedure must be created.
  - Low effort only for level 2 decisions with a deterministic postcondition check behind them. Any check failure escalates to level 3 at max effort. Never let low effort decide an irreversible action.
  - First answer the two open questions before building: does Codex CLI accept a per-call effort override, or only a session-level config (if session-level only, run level 2 and level 3 as separate Codex invocations with different flags), and does the Codex path honor a strict JSON schema (verify before relying on it).
- What NOT to change:
  - The subgoal postcondition checks themselves, the checkpoint fail-closed escalation, and the quarantine rule (a procedure whose checkpoint fails twice in a row is quarantined, next run re-derives layout from a fresh full-frame observation). Longer unsupervised runs make these more important, not less.
  - Cancellation and finish stay. A bad action running longer before detection is the known risk of this pick; mitigate it with the M3 live validation and the subgoal postcondition check, never by re-adding a per-step judge silently.
- Expected saving: ESTIMATE 20 to 35s on a 100s task from dropping judge and reflect, plus ESTIMATE 30 to 60 percent off supervisor latency and output-credit cost on the level 2 calls the dial touches. On the tc02 happy path the supervisor is called 0 to 1 times, so the dial alone saves near 0s there; the pick pays on cold tasks, recovery, and procedure creation.
- How to measure: baseline arm vs subgoal-only arm on the same held-out tasks, plus at least one cold task shape with no procedure, so the dial has something to act on. Report supervisor calls per task, output tokens per task, wall time, think total, and the number of actions that ran before a bad action was detected (the detection lag). Success is fewer supervisor calls AND lower wall time with no rise in detection lag cost (a bad action caught one subgoal later is acceptable, a bad action that completes a destructive step is a failure).

### Pick 3. Multi-candidate grounding in one vision call, verified by tiny crops (M5)

- Why third: the largest task-scale saving available to observation work, because each avoided re-observe removes a whole vision turn and a recovery loop. - Exact files to change:

- Exact change:
  - One full-frame vision call returns up to 3 candidate points with confidences. Verify candidates in order with a fresh native 90x90 to 200x200 crop (MEASURED 53 to 58ms local, 2.4 to 8KB per crop) instead of issuing a new full-frame observe per miss. Apply the crop context rule M34 on every crop: include column headings plus at least one full row on each side of the target, and at least one adjacent control for disambiguation. - Expected saving: ESTIMATE 5 to 20s per task on clean tasks, far more when it prevents a recovery loop. MEASURED crop cost is 53 to 58ms local per verification, so the saving is the avoided vision turn (seconds of model time) minus that.
- How to measure: A/B on held-out small-target cases, single-candidate vs top-3 with tiny-crop verification. Report attempts per control, misclicks per task, vision turns per task, wall time, and think total. Success is fewer attempts per control and fewer vision turns with no rise in misclicks. ### 4A.2 Do-not-redo list (consolidated from all three prior-art surveys)

1. Faster screenshots without a redraw guard make the agent slower (cua-speedrun: env time down 8.72s, agent time up 18.20s).
2. Standalone prompt compression on short prompts loses to its own overhead (Kummer et al.: up to 18 percent only above about 5k tokens).
3. Speculative decoding can run slower than baseline (EAGLE-3 at 0.44x on Qwen3-8B); through the Codex API it is not available at all.
4. More thinking eventually hurts accuracy, not just latency (past about 7,000 reasoning tokens, flips go wrong over right; 64.3 percent of thinking tokens come after accuracy peaked).
5. LLM summarization of history is no better than simple observation masking, and it costs an extra model call.
6. Cascades pay the sum of both models on escalation; drop the cascade if escalation exceeds about 30 percent.
7. Constrained decoding over the whole generation degrades reasoning by up to 10 points; constrain only the final action JSON.
8. Long context costs more per generated token even with perfect KV-cache reuse (16K to 256K context drives cost per token up 3.6x to 7x).
9. Over-reasoning degrades the model's own confidence signal; use external checks, never self-confidence, for routing or acceptance.
10. Parallel and async function calling save little when tool calls are fast (broker service 0.16s to 1.09s per request).
11. Full a11y-tree dumps as observation (5,000 to 15,000 tokens, worse than a screenshot; adding a11y trees increases per-task latency).
12. A11y-only grounding, no images (a11y.py has no coordinate path; GTK popups not exposed; VisualWebArena text-only 7.3 percent vs 15.1 with a screenshot).
13. Fully blind execution: predict coordinates, click, no fresh image (tc01 4/4 misclick history is the local proof).
14. Observation and pixel caching: reuse delivered images as ground truth (diff-based WHERE-to-look is fine; reused pixels as ground truth is not).
15. Token merging or pooling of visual tokens before grounding (ShowUI ablation 70.8 to 42.3 percent); token selection is almost lossless, never pool.
16. CogAgent on this laptop (29GB VRAM minimum at BF16; INT4 loses significant accuracy).
17. 7B grounders as the default local model (borderline on 6GB VRAM, beaten on Pro by 3B Ferret-UI Lite).
18. Higher resolution is not always better (FastFocus "semantic fragmentation"); do not raise max-width as a grounding fix without an A/B on misclicks.
19. More steps is not a free accuracy lever (OSWorld-Verified: one model swings 9.1 to 23.0 percent on step budget alone; report steps and think time together).
20. Rust rewrite of the harness (Track 1 verdict 2026-11-18, STAY PYTHON; the Rust observation-store port is measurably SLOWER than Python).
21. Downscaling as a think-time fix, unmeasured (byte saving proven locally; think-time saving not, until the gap split is instrumented).
22. Tree of Thoughts per step (5x to 100x tokens; CoT plus self-consistency frequently wins at equal budget).
23. Online MCTS / Agent Q search (live desktop actions are irreversible; R-MCTS costs 7.3x to 10.1x tokens).
24. GTA1 K-way sampling per step (token cost scales linearly with K; buys success, not speed).
25. Parallel rollouts, BJudge style (891s average per task, 24x his clean-task mean before judging).
26. Per-step judge / agentic verification (VeriCUA 10x tokens, 97s per episode, worse OSWorld recall).
27. Per-step reflection (Reflexion worst case about 7x a single attempt; reflection without a grounded test scores worse than nothing).
28. Semantic cache as a correctness mechanism (similarity is not proof; exact-match memo only, inside M4, always behind a postcondition check).
29. AWM gains on newer models (ReasoningBank re-run: minus 0.9 points on Claude 3.7 Sonnet).
30. More retrieved memories (ReasoningBank k=4, 44.4 percent vs k=1, 49.7 percent).
31. Wholescale small-model swap (small model as planner fails and retries; small by default with big-model escalation is the shape, small INSTEAD of big is not).
32. Fine-tune a planner (needs a GPU cluster and API credit; shape only, not training).
33. Speculative writes on the live seat (no sandbox, no undo; only speculative READS are safe).

## 5. The UNVERIFIED remote SSH caller question

- The question, from code-hotspots section 0.1 and W-HOT section 19, unchanged: no file in the repo defines how the remote side issues `request` and polls `result` over SSH (how many SSH invocations per driver command, poll interval, whether `request` and `result` are separate SSH calls). `session_remote.py` only defines the broker side: `_exchange()` opens a new Unix socket per call, `_client_with_lease()` does a `status` exchange before every `request`, `result`, and `finish` call, `_client_finish()` polls `status` every 0.1s. Each logical driver command therefore costs at minimum 1 status exchange plus 1 request exchange plus N status plus result exchanges on the broker side. The SSH-side count is UNVERIFIED.
- Why it matters: W-HOT measured on the VM that `import cu` in a subprocess took 412ms mean and `session_remote.py status` with no broker took 700ms mean (VM numbers inflated 3x to 5x, laptop figure ESTIMATE 100 to 250ms per CLI invocation). At 3 CLI invocations per logical command that would be 0.3 to 0.75s per command, which would dwarf every finding in W-HOT. W-PROF, by contrast, measured the real loop on the laptop: request service 1.4s per clean task across all requests, windows 0.109 to 0.114s, observe 0.159 to 0.206s, act 0.221 to 1.086s driven by execution time. The profile numbers bound the real per-command cost from above and do not show a 0.3 to 0.75s per-command SSH tax on the path W-PROF actually used. The two pictures are consistent only if the W-PROF caller (timed.py, laptop, `~/workspace/speed-profile-20261118/timed.py`) is not spawning a fresh CLI per poll, or if the laptop CLI cost is at the low end of the estimate. Neither is proven from the repo alone.
- What it would take to resolve it: read the actual remote caller, not the broker. The files to read are the caller-side wrappers: the executor's `timed.py` in `~/workspace/speed-profile-20261118/` (the W-PROF caller, already on disk), any SSH wrapper the parent agent uses to issue `session_remote.py` commands, and the Codex skill invocation path that reaches the broker. For each, record: SSH invocations per logical command, whether `request` and `result` are separate SSH calls, poll interval, and whether the CLI process is persistent or fresh per call. Then measure on the laptop: time 20x `session_remote.py status` with a broker running, time 20x a trivial SSH command, and time one full logical command end to end with the caller timestamps, so the SSH and CLI share is separated from broker service. One hour of reading and timing settles it; no code change is needed to answer it.
- Does it block any prototype: NO. None of the five picks depends on the caller shape. Picks 1 to 4 cut model think calls, which dominate at 94 percent whether the caller tax is 0s or 0.75s per command. Pick 5 measures the harness floor with the scripted probe, which uses the same caller as the baseline arm, so a caller tax cancels out in the comparison. If the caller question resolves to a large tax, the fix is a persistent local client process (or one long-lived SSH command) that multiplexes status, request, and result over one broker connection, and it becomes a new prototype of its own, ranked by the measured tax. Until then, do not cost any prototype against an assumed caller tax, and do not build the persistent client on an unverified assumption.

## 6. Recommended sequence

1. Do M11 and M44 first, in parallel with nothing else: run the 50-sample S2 menu-open probe, apply expected-transition handling to every window-closing step, enforce the desktop-hygiene and dialog-class preconditions, and run the gap-split measurement (image receipt vs vision consumption vs decision) on a cold task. Both are cheap, local, and unblock the two biggest estimates in this plan. M11 is the most certain saving because its failure frequencies are MEASURED.
2. Prototype pick 2 (subgoal-only verification) first in code time, because it is a prompt and harness rule change with no new dependency, then pick 3 (multi-candidate grounding), then pick 1 (code execution), then pick 4 (grounding fast path). Pick 5 (hotspot bundle) is SECOND PRIORITY, harness-only, and runs after picks 1 to 4, never interleaved ahead of a think-time prototype. Measure each alone on the same held-out tasks before stacking any two.
3. Build M4 (procedure library) after picks 1 to 3 prove on fresh tasks, not before: the library is the multiplier that makes a 0-turn path apply to the second task shape, the tenth, and the fiftieth, instead of only tc02. Extraction cost is one supervisor session per new shape, amortized over all later runs. Never silently replay a stale procedure: checkpoint fail-closed escalation plus quarantine after 2 consecutive checkpoint failures.
4. Build M10 (local grounder cascade) only after the gap-split measurement exists and the 20-sample local accuracy test passes for Ferret-UI Lite 3B first, then UI-TARS-1.5-2B. Never let the small model plan, never let it act without a deterministic postcondition check. Load each candidate on the laptop and report actual VRAM and per-call latency before building around it.
5. Re-profile after each pick lands, with the same W-PROF method and the same held-out tasks, and report the per-arm table. A claim of fixed without a passing live task test is worth 0 points, per the standing testing standard.
