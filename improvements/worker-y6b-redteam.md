## Verdict: KILL

The plan as written must not run. The measurement function cannot execute: capture() fails on every call for two independent reasons (wrong geometry format, and -g plus -o are mutually exclusive in grim). The run would pass its positive control, start the nest and the pill, tile the nest window over the live screen, and then abort at armA frame 01 with zero arm data. That is not a weak run, it is a run that cannot produce its verdict. ## Kill finding H1: capture() is broken two ways, proven live

The runner, run-nested-wayland.sh line 166:

```
capture() { nest grim -g "$3" -o WAYLAND-1 "$NEST/frames/$1-$2.png" || fail "grim $1-$2 failed"; }
```

PILL_GEOM is built at lines 147 to 158 as "x,y,w,h" (comma separated). BACKDROP_GEOM is set at line 162 as "0,0,200,200" or "760,0,200,200".

Defect 1, geometry format. grim -h on the laptop says: `-g "<x>,<y> <width>x<height>"`. Proven 18:58 +07 against the live session:

```
$ env XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-1 grim -g "0,0,200,200" /tmp/y6b-grim-comma.png
invalid geometry
exit=1, no file written
```

Defect 2, -g and -o are mutually exclusive. Proven 18:59 +07:

```
$ env XDG_RUNTIME_DIR=/run/user/1000 WAYLAND_DISPLAY=wayland-1 grim -g "0,0 200x200" -o eDP-2 /tmp/y6b-g2.png
-o and -g are mutually exclusive
exit=1, no file written
```

Either defect alone kills every capture() call. The first capture is armA frame 01 at line 183, so the run dies there via `fail "grim armA-01 failed"`, then teardown. The positive control (lines 128 to 133) uses `grim -o WAYLAND-1` with no -g, so it passes, which makes this worse: the run looks healthy until the first arm frame, after the nest and pill are already up and the live screen is already disturbed.

Side note, resolved, not a defect: two further grim probes with the space format and no -o reported "supplied geometry did not intersect with any outputs". That is explained, not a grim bug: the live monitor eDP-2 sits at layout position (2464, 902), verified 19:01 +07 via `hyprctl -j monitors`, so regions near (0,0) genuinely do not intersect it. In the nest, WAYLAND-1 is at 0,0 per the config, so a corrected -g region inside 960x540 would intersect. This does show the grim invocation was never dry-run, which is how H1 shipped.

Fix: format the geometry as "X,Y WxH" and drop -o from capture() (a -g region in layout coordinates already selects the output it intersects), or capture the full output and crop afterwards. Then dry-run the fixed invocation before the window.

## Other holes the council briefs did not name

H2. Arm A has no backdrop control, so it is false-positive prone. Arm A (lines 179 to 187) kills mpv, then treats any pill-region change as REPRODUCED. But the backdrop in arm A is whatever the tiler shows behind the pill after mpv dies: the foot terminal window, or empty output. That is not a controlled static image, and arm A captures no backdrop sample, unlike arm B. Any change behind the pill (foot cursor blink, terminal content change, a notification) reads as pill flicker. The decisive arm is the one with no control.

H3. Arm B's pill-only criterion is nearly unreachable, so arm B is false-negative prone. Arm B (lines 199 to 208) counts a pair as flicker evidence only when the pill differs while the 200x200 backdrop sample is byte-identical. The backdrop is testsrc2, a continuously moving video, so the corner sample will differ on essentially every 1s-apart pair (B_BG_DIFF near 31/31, B_PILL_ONLY near 0). A real pill flicker during arm B shows up as pill-diff AND backdrop-diff and is filed under "expected motion". Arm B can therefore almost never yield its REPRODUCED branch, and a flicker in the animated arm is systematically misread. The two arms fail in opposite directions: A over-calls, B under-calls.

H4. Sampling cadence versus flicker frequency is never addressed. The incident flickered at about 10 Hz. The arms sample 1s apart: 60 frames at 60fps is exactly 10 flicker cycles, so a periodic flicker phase-locked to the frame clock lands on the same phase every sample and hides. In practice the loop period is 1s plus grim time, so phase drifts and detection is likely, but the drift is uncontrolled and unmeasured. The design never considers it. Fix with randomized inter-frame delays (for example 0.6 to 1.4s) or burst sampling.

H5. The plugin-load NO-GO conflates nest-specific and real incompatibility. The script fails on "hyprglass not in nested plugin list" (line 94) without inspecting why. A refusal caused by version or API mismatch is real evidence against live loading (same binary, same .so). A refusal caused by the nest renderer (software GL, a missing EGL feature, the Wayland backend lacking something the plugin needs at load) is nest-specific and must not kill option C by exhaustion. The script does not distinguish, and the report's "if Wayland-nested fails (plugin refusal), option C is dead by exhaustion" inherits the conflation. Fix: on load failure, grep the nested log for the load error and classify it before declaring option C dead.

H6. The optics hook races the plugin load. hyprland-wayland.lua line 8 calls hl.plugin.load, line 12 immediately dofiles the hook, which checks glass_count right then. If plugin.load is asynchronous, the hook sees count 0, prints its marker, and the profile is never applied; no later step applies it (the liquid gate only reads status). The run then NO-GOs after 60s for a spurious reason. Whether hl.plugin.load is synchronous in 0.57.2 is UNVERIFIED from the files. Fix: retry the glass check in the hook, or re-apply the profile from the launcher after the first successful status read.

H7. Teardown orphans the nest and leaks the indicator child. NESTED_PID (line 80) is the PID of `timeout 300 Hyprland`, not of Hyprland itself. Teardown (line 46) does `kill NESTED_PID; sleep 2; kill -9 NESTED_PID`. Proven on this VM 18:58 +07: `kill -9` on a timeout process leaves its child alive and reparented to PID 1 (test: timeout pid 25029, child sleep 25031 survived, PPID 1). A plain TERM is forwarded by timeout and usually kills Hyprland, so the hole bites only when Hyprland does not die on TERM within 2s, but that is exactly the failure case teardown exists for. The orphaned nest keeps running with its runtime dir deleted (line 48) and its window on the live screen. Separately, the pill script spawns the indicator binary with start_new_session=True (indicator.py Native.__init__), so killing PILL_PID (line 45) never kills the indicator child, which keeps the pill surface alive until the nest dies; if the nest is orphaned, the pill survives with it. And line 47 `pkill -x mpv` kills every mpv on the machine, including any the owner or another agent runs, instead of only the one the run started. Fix: kill the nest process group (setsid gives it its own group), track and kill the indicator child, track the mpv PID instead of pkill -x.

H8. The nest renderer is never recorded. The asymmetry clause says the nest renders "possibly with software GL", but the script never greps the nested log for renderer or GLES lines. A positive or a negative therefore cannot be attributed to a known rendering path, and the clause stays an unmeasured unknown. Fix: record the renderer lines in the report.

H9. No owner-return detection and no overall deadline. Y6_HANDOVER_CONFIRMED=1 is a point-in-time assertion; nothing re-checks it. If the owner returns mid-run, the nest window is tiled over the user's Zen (the report admits the nest resizes Zen), the script keeps capturing, and nothing aborts. There is also no overall script timeout: the 30 minute window is asserted, not enforced, and grim and hyprctl calls have no timeouts. Nominal worst case is about 5 to 6 minutes (nest timeout 300 plus gate 60 plus pill 45 plus arms about 80 plus teardown), but a hung call holds the flock indefinitely and blocks Y4-style runners. Fix: wrap the script in a deadline and abort if the live active window changes or loginctl IdleHint clears.

H10. Arm B's animation is never re-validated after restart. The positive control (lines 128 to 133) checks the pre-pill mpv instance, but arm B restarts mpv as a new instance (line 193) with only a pgrep existence check (line 195). If the new mpv renders frozen, arm B silently becomes a second static arm and a negative verdict is void. There is no B_BG_DIFF greater than 0 validity gate. Fix: require B_BG_DIFF greater than 0 or mark arm B void.

H11. Hardcoded live identity. LIVE_SIG (line 32) and PID 1515 (line 50) are hardcoded. Both are correct right now (verified 18:56 +07: the signature dir /run/user/1000/hypr/11cbc6c577b84ffb1edf4df3fc5b6128c3ae6947_1795249046_1138556825 exists, PID 1515 alive since 15:17:25), but both go stale if the live session restarts, and teardown would then report a false "LIVE PID 1515 MISSING". Fix: resolve both dynamically at start.

## Answers to the seven briefed attacks

1. Council C fixes, re-verified: change 5 (hook) and change 2 (files) are real; change 4 (measurement) is not, it cannot run (H1); change 1 (parent path) is real as env but its post-launch check is unenforced and its parent half is still a first-time experiment; change 6 (flock) is real as code but its protection is partial; change 3 (backdrop and arms) exists but cannot attribute (H2, H3); change 7 (teardown and GO/NO-GO) exists but orphans (H7) and never records the version. The fix did not just move the failure: it fixed the env and the hook, but it left the measurement broken, which is a new failure at a later step.
2. Liquid gate import: the brief's premise is wrong right now, and I correct it. The laptop repo is NOT at a detached HEAD with uncommitted changes: it is on branch todolist-push at 4500a18, `git diff HEAD --stat` is empty, tracked tree clean. It is 28 commits behind origin/todolist-push, but `git diff HEAD origin/todolist-push -- scripts/indicator.py` is empty, so the gate imports exactly the origin file. LIQUID_VERSION is '1.1.1-cu.1' (line 191), LIQUID_SCHEMA 1 (line 190), _status runs `hyprctl -j hyprglass status` with a 1s timeout and returns None on any failure, so transient failures just retry in the 60s loop. The real gate gaps are diagnostic, not import: the version is never printed on gate failure (H7 in change 7 above), and the pill's Native does not re-verify liquid after the gate. native/require-liquid does not exist in the laptop repo, so Native will not raise on missing liquid; if liquid flipped between gate and pill start, the pill would silently run non-liquid and the arms would measure a plain pill. The gate itself will pass or fail for the right reason (status content), but a failure is undiagnosed.
3. Probative value: the asymmetry clause is half right. A nest negative does not exonerate live, as stated. But a nest positive is weaker than claimed too. The nest renders 960x540@60 through an extra compositing hop with parent presentation timing and possibly software GL (renderer never recorded, H8), at a different resolution and scale than live 1920x1200@144, over a synthetic testsrc2 backdrop instead of whatever was actually behind the pill on 20/11. A positive could be a nest artifact (double compositing, frame-callback misalignment) rather than the live incident. And the arms as written cannot even attribute a positive correctly (H2, H3). So the run as written is weak in both directions, not just on the negative side.
4. Plugin refusal: yes, a nest NO-GO can falsely kill option C. See H5. The load check is version and API based only if the refusal reason is version or API based; a renderer-dependent refusal is nest-specific. The script must classify the refusal from the nested log before option C is declared dead by exhaustion.
5. Flock: the runner-quiet window is fictional for most runners. See change 6 above. Only Y4-style preflight runners and ZenSession users are blocked. run_live.py, run_agyq.py, run_fcck.py and the y5-tests copy of run_agyq2.py never touch the lock. Y8 E1 and Y9 agy-y2 lock behavior is unverified because no runner files for them were found. The slot queue (Y4d done, Y8 E1 next, then Y9 agy-y2, Y11 proof, then Y6b, per worker-y6b-nested-wayland-log.md) means the window question is about future runs, not the current moment, but the plan must name the exact launch wrapper every queued runner uses, or the flock protects nothing.
6. Window and worst case: nominal about 4 minutes per the script header, worst case about 5 to 6 minutes if no call hangs (nest timeout 300, gate 60, pill 45, arms about 80, teardown about 10). The 30 minute window is probably adequate, but it is unenforced (H9), and there is no owner-return detection. If the owner comes home mid-run, the nest window is on the user's screen, Zen is resized by the tiler, and the script keeps running.
7. New holes beyond the council briefs: H1 (capture cannot run, two defects), H2 and H3 (arms cannot attribute), H4 (sampling versus flicker frequency), H5 (plugin refusal classification), H6 (hook race), H7 (teardown orphans), H8 (renderer never recorded), H9 (no owner-return detection, no deadline), H10 (arm B animation never re-validated), H11 (hardcoded live identity), plus the stale wayland-1 socket leftover in change 2.
