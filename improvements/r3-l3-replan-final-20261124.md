## 7. Orphan-worker prevention (coordinator death)

Owner's failure mode 1: workers still alive but the coordinator died, so nobody reports and work continues silently with no parent.

Prevention (fencing, per Council 1 M-01, Council 3 A5, redteam B-02, Clone1 section 2.2):
- The coordinator epoch: an integer in the heartbeat file, starting at 1. The coordinator increments it only on a takeover. Workers accept only assignments carrying the current epoch. An assignment with an old epoch is ignored and reported.
- The deputy verifies the coordinator is DEAD, not merely silent, before taking over. Silence is not death (tonight the daemon died with its supervisor, so a coordinator can be alive and unreachable for 15 minutes because the channel is down). The deputy checks two independent sources: the parent (who can see the coordinator's session) and the state-file mtime (no heartbeat for 15 minutes AND the state file has not been written for 15 minutes).
- If the coordinator is alive but unreachable, the deputy does NOT take over. The deputy restores the channel instead (restart the daemon, restart the supervisor, verify read.py works within 5 minutes, then confirm the coordinator is reachable).
- The deputy writes a takeover record into the state file BEFORE issuing any order (coordinator_active set to the deputy's id, epoch incremented, timestamp, reason). Workers obey only the coordinator id named in the state file field coordinator_active.
- The old coordinator must check the coordinator_active field before every ledger write and stop writing the moment it is no longer active. If the old coordinator later revives and finds it is no longer active, it stops, reports to the parent, and does not resume.
- The deputy confirms standby in the state file every hour (G-42). If the deputy session ends, the parent names a new deputy before task 1, or the run pauses until one is named.
- The takeover procedure is dry-run before task 1 (G-38): the deputy lists every live worker from the state file and confirms the contact path (SSH/tmux/session) for each, and the result is recorded in the run log. If the deputy cannot reach the laptop, the takeover procedure is unproven and must be fixed or the deputy role reassigned to a session with SSH before task 1.
- The wake chain (per redteam M-02): cron alerts the parent, the parent messages the deputy to take over (the parent is the only party that can reach a standby subagent session). A cron cannot message a subagent session directly.
- Worker self-stop (F-01) is the floor: a worker that cannot reach the coordinator finishes the current task, preserves evidence, and does not start the next one. This bounds orphan work even if the deputy never takes over.

## 8. Reporting chain (live-but-silent detection)

Owner's failure mode 2: nobody died, but subagent messages never reported up to the owner, so he had to ask before anyone went looking. The reporting chain silently broke even though everyone was alive.

Prevention (per Council 2 A1/A2, Council 3 A8, redteam M-01/M-02, Council 1 M-07):
- Heartbeat medium: a shared append-only JSONL log file (not individual daemon messages). Each worker with an outstanding task writes one heartbeat line every 10 minutes (task ID, status, elapsed, next milestone). Standby/research/Mei write on state change or once per hour. The file is checked for a trailing newline before appending, and parse-verified after (F-08).
- Ack load: the coordinator does NOT write an ack per heartbeat. Acks are batched once per 30 minutes (one line listing the heartbeats received in the window). The written ack load is about 60 lines over the run, not about 900.
- Chain-broken definition: the chain is broken if a worker is unreachable for 15 minutes AND no per-task report appears for 30 minutes while a task is outstanding. A missing report alone, with a live heartbeat, is normal for a long task and does not break the chain. A missing ack does NOT define a broken chain (acks are batched, so a missing ack is normal).
- File-based fallback heartbeat channel: heartbeats ride the shared log file, not the daemon. The daemon is the component that died tonight; a heartbeat that rides the daemon dies with it. If the daemon is down, the coordinator reads the heartbeat log file directly from the VM (the file is VM-local, the coordinator has access). The coordinator's 10-minute heartbeat to the parent is also written into the state file (timestamp, next task per lane, unscored queue depth), so the parent can read it without the daemon.
- Per-task report medium: per-task reports are appended to a named run-log file with timestamps (task ID, verdict, pair, tiebreaker if any, invalid or backup if any, elapsed time). The reporting-chain watch greps that file (G-41). The coordinator's chat message to the parent, if any, is a copy of the file line, not the record itself. A cron cannot read chat; it can grep a file.
- The coordinator's liveness watch (section 5) triggers only on a missing coordinator heartbeat (15 minutes), never on a missing per-task report (normal long tasks produce no report). A missing heartbeat alerts the parent, the parent messages the deputy (section 7).
- The 15-minute poke condition (unchanged): last sent newer than last seen reply, silence over 15 minutes, no poke in the last 15 minutes, never while the read path is broken. The poke is a direct message, not a repo push.
- The owner is notified at each milestone (M1 to M5, section 9) and at each invalid (3, 4, 5). The owner is NOT notified per task. If the owner has to ask for a status, the reporting chain has failed, and the coordinator records the failure and fixes the watch.
