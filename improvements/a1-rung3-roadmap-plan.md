### 5.1 How we measure

Wall time per task/run, pass rates, think time (composition think vs wall), session contention time (time a runner waits for the session), recovery steps. The exact metric for each track is:

A1 pilot:
- Median wall CODE vs STEP, per case. Wall_ms: task start to verified end state (headline). run_start ts is the task start instant; run_end ts is the verified end state instant. Finish think is OUTSIDE wall and is reported as a diagnostic only.
- Pass rate: passes out of 3 per arm per case, with the failure reason of every failed run printed.
- Recovery steps: count(retry lines) plus count(recovery lines), summed across the 3 runs per case per arm. One corrective action is exactly one line, or the gate double counts.

Definition: elapsed wall time from the end of the previous model turn (or from task start for the first call) to the submit timestamp of that program call, taken from the timed run log. The executor does no exploratory observe between the end of the previous turn and the program submit except the observes the program itself performs; any exploratory observe before a program call is logged as its own run-log line and its think counts toward that call. - Session contention time: for A1, the wall time from the FCC task-boundary time (logged by the A1 coordinator in ~/workspace/a1-pilot-coord10.log with wall-clock time when FCC reports task end) to the coordinator log line "P1 verified free" (written in the same log when the fd scan first shows free and the fresh driver starts). ### 5.3 How we track performance

The A1 GO bar, pre-registered in the frozen plan (Case B 4 conditions plus Case A feasibility gate, INCONCLUSIVE as a third outcome, detection limit n=3 powered for a 50 percent wall cut, not 30 percent):

Case B (f01), GO needs ALL four conditions:
1. Median wall time CODE at or below 0.70 times median wall time STEP (medians of 3 runs; all six walls printed).
2. Pass rate CODE equal to or better than pass rate STEP (passes out of 3, failure reason of every failed run printed).
3. Total recovery steps across the 3 CODE runs not higher than total recovery steps across the 3 STEP runs (recovery steps equal retry lines plus recovery lines).
4. Total composition think CODE (sum over all program calls) less than STEP median total think for that case. Flagged if total composition think exceeds 50 percent of CODE median wall, even when condition 4 passes.

Additional rules: 2-of-3 rule (at least 2 of the 3 CODE runs in Case B individually at least 20 percent below the STEP median wall). Dispersion: for each arm-case cell of 3, (max minus min) divided by median above 50 percent makes that case INCONCLUSIVE. Flagged runs stay in the median; 2 or more flagged runs in one arm-case cell makes that case INCONCLUSIVE. Robustness check (reporting only, not a gate): every CODE run wall at or below the STEP median wall; GO with it passed on both cases is GO, HIGH CONFIDENCE, otherwise GO, LOW CONFIDENCE.

Case A (Pick 4), feasibility gate: pass rate CODE equal or better than STEP, recovery steps CODE not higher than STEP in total, total composition think CODE less than STEP median total think. Median wall is diagnostic only, not a gate.

Verdict: GO only if Case B passes all four and Case A passes its gate. Case B failing any condition is NO-GO regardless of Case A. Case A failing its gate is NO-GO regardless of Case B. INCONCLUSIVE is a third outcome (dispersion, flagged runs, timed-out median, or any gate metric UNMEASURED on any run). On INCONCLUSIVE the pilot is re-run after the noise source is fixed, not re-run unchanged.

Detection limit (frozen): at n=3 the pilot is powered to detect a 50 percent wall cut, not a 30 percent cut. NO-GO means "not proven at pilot scale", never "batching does not work". GO means "proceed to the confirmatory run", never "a 30 percent speedup is proven".

## 6. RISKS AND STOP CONDITIONS

### 6.1 Session contention: failure modes F1-F10 (redteam section 3.1, in full substance)

Each failure mode below states when to stop, who decides, and what happens to the run-id.

- F1, driver death recurs: the session-driver dies again before or during the run, cause unknown, no mitigation in place. Same session_death, same INCOMPLETE. Stop rule: abort attempt 5 at once, log the exact time and driver exit status, release the session immediately, hand the window back to rung 3, and do not issue another run-id until the driver death has an independent investigation with a named cause or a proven fix. Decider: the A1 coordinator calls the abort; the parent decides whether a second window is ever issued. Run-id: the run is INCOMPLETE if it has no valid end state, or FAIL if it ended with run_end reason failed; the run-id is not reused. If the driver dies pre-submission, abort, release, no retry in that window.
