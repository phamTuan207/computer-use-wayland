### 1.2 What the installed 0.57.2 headers prove

Read from the laptop, `/usr/include/hyprland/src/` (Hyprland 0.57.2, commit 11cbc6c577b84ffb1edf4df3fc5b6128c3ae6947, verified by `Hyprland --version` in the Y6e run log):

- `plugins/PluginSystem.hpp:39`: `SP<CPromise<CPlugin*>> loadPlugin(const std::string& path, ...)`. The load API returns a promise, not a loaded plugin. A caller that holds only this return value cannot observe the plugin synchronously.
- `plugins/PluginSystem.hpp:42`: `updateConfigPlugins(const std::vector<std::string>& plugins, bool& changed)`. Config-declared plugins are applied as a set, compared against what is already loaded.
- `plugins/PluginSystem.hpp:56`: `loadPluginInternal(const std::string& path)` is private. The actual dlopen is not reachable from config code; it runs inside the plugin system.
- `config/lua/ConfigManager.hpp:80`: `virtual void handlePluginLoads() override`. Plugin loads are a distinct phase of the config manager, not part of line-by-line config execution.
- `config/lua/ConfigManager.hpp:119`: `std::vector<std::string> m_registeredPlugins`. The config manager keeps a registered list, which is what `hl.plugin.load` populates.
- `config/lua/LuaEventHandler.hpp` header comment: the event handler is "Destroyed (and recreated) on every config reload so callbacks never double-up." A reload therefore re-runs the whole Lua config from scratch, including the `hl.plugin.load` line and the hook dofile.
- `helpers/defer/Promise.hpp`: `CPromise::make(fn)` invokes `fn` immediately with the resolver, so the promise machinery itself does not prove deferral. The deferral is proved by the call sites (handlePluginLoads, postConfigReload) and by observation, not by the promise type alone. I do not claim the promise type alone settles it.
- `/usr/share/hypr/stubs/hl.meta.lua` (machine-generated stubs for the running 0.57.2): line 934 `get_loaded_plugins fun(): HL.Plugin[]`; line 949 `timer fun(callback: function, opts: HL.TimerOptions): HL.Timer` with `HL.TimerOptions` `{timeout: integer, type: "repeat"|"oneshot"}` (lines 519-522) and `HL.Timer` with `is_enabled` / `set_enabled` / `set_timeout` (lines 835-839); line 1041 `HL.PluginNamespace.load fun(...): any`. The Lua `hl.plugin.load` returns nothing awaitable. There is no Lua-side way to wait on the load from config code.

### 1.3 What independent upstream material proves

- Dotfiles note by an independent author who debugged exactly this path on Hyprland 0.56.2 (`https://dotfiles.v1cferr.dev/notes/desktop/hyprglass/`, read in full 2026-11-21): "The plugin list is DECLARATIVE... Hyprland 0.56.2's `CPluginSystem::updateConfigPlugins` compares the plugins declared in THIS pass of the config with the ones it has: it loads what is new, UNLOADS what a pass no longer declares, and reloads the config when anything changed." And: "A plugin load makes Hyprland run the whole Lua file once more during startup." And: the fixed config "came up with the plugin `active`, then survived five `hyprctl reload`s with one plugin loaded." And: "`hyprctl reload`: the reload runs `glass.lua`, which loads the plugin" and "a reload applies it" (tuning values). The reload-loop crash in that note (reload to postConfigReload to handlePluginLoads to reload, stack overflow) was caused by a declared list that CHANGED between passes (a load-only-if-not-loaded guard); declaring unconditionally on every pass made pass 2 a no-op. Our conf declares unconditionally (line 16, no guard), so it has the safe shape.
- Upstream issue text on bind-dispatcher deferral (GitHub API mirror, read 2026-11-21): "Binds referencing plugin-provided dispatchers are parsed before plugins register those dispatchers... once plugins load and trigger a config reload" the errors disappear; "per-plugin load still schedules its own reload." This corroborates the reload-after-load behavior as current Hyprland behavior, not a proposal-only idea. Caveat: that text is an issue proposing a change (a pending counter for config plugin loads), so I rely on it only for its description of current behavior, which matches the 0.56.2 account and the 0.57.2 headers.
- Hyprland wiki, Lua events page (`https://wiki.hypr.land/configuring/core/advanced-configuration/events/`, read in full 2026-11-21): the full event list contains NO plugin event. Relevant events: `config.reloaded`, "Emitted when the config has been reloaded and applied"; `hyprland.start`, "Emitted once on start"; `config.unload`, "Emitted just before the config is unloaded and Lua state torn down, i.e. on reload or shutdown". There is no event a hook can subscribe to for "plugin finished loading".
- Hyprland wiki, Using plugins page: "You can also load plugins with Lua `hl.plugin.load(path)`" and the FAQ example guards plugin configuration with `if hl.plugin.csgo_vulkan_fix ~= nil then`, with guard checks recommended "to prevent errors if a plugin is not yet loaded". The documented expectation is that a plugin declared by `hl.plugin.load` is not yet loaded when subsequent config lines run.
- Repo design intent, `scripts/setup.py` `_hook_body` (lines 74-75): comment "Apply optics on reloads, but schedule first load only before glass is present." The hook is DESIGNED for two passes: pass 1 (glass absent) takes the else branch; a later pass after the reload (glass present) applies the optics. The nested hook inherits this shape with the else branch replaced by the marker print.

### 1.4 The assembled sequence

1. Fresh nest process starts. `m_loadedPlugins` is empty by construction; nothing has loaded anything yet.
2. Config parse executes line by line. Line 16 `hl.plugin.load(...)` registers the path in `m_registeredPlugins`. It does not dlopen, and it returns nothing awaitable.
3. Line 18 dofiles the hook. The hook calls `hl.get_loaded_plugins()`, which reads `m_loadedPlugins`: empty. Count is 0, version is nil. The else branch prints the "not ready" marker. Optics never runs. This is pass 1.
4. Parse finishes. `postConfigReload()` runs (nested log line 16 shows the postConfigReload stdout-disable line immediately after the hook marker on line 15) and calls `handlePluginLoads()`, which calls `updateConfigPlugins()`, which dlopens what is new.
5. Because the declared set changed (empty to one plugin), the config is reloaded. Pass 2 re-executes the whole Lua file: line 16 declares the same path (already loaded, no-op), line 18 dofiles the hook again, and this time `hl.get_loaded_plugins()` returns count 1, version 1.1.1-cu.1, so the hook dofiles optics and the profile is applied. Pass 2 prints no marker.
6. The liquid gate and the pill measurement then run against the pass-2 state.

## 2. Determinism ruling: the U6 failure is DETERMINISTIC, there is no race window

Ruling: DETERMINISTIC. The retry run with the current conf + v3 runner will fail at U6 (runner lines 302-303) on every run, before the liquid gate and before any pill measurement.

Proof, in three parts:

(a) The marker is printed on pass 1 of every run. At the moment the hook executes (config parse, before postConfigReload), the plugin cannot be in `m_loadedPlugins`: the nest is a fresh process, the only load declaration is line 16 of the same parse, and that declaration takes effect only in `handlePluginLoads()` after parse. `get_loaded_plugins()` therefore returns count 0 on pass 1 by construction, and the hook prints the marker. The observed run (count=0, marker on log line 15, immediately before the postConfigReload line) is exactly this, not a timing accident.

(b) There is no race window. A race would require some interleaving in which the plugin lands in `m_loadedPlugins` between line 16 and line 18. That would require `hl.plugin.load` to dlopen synchronously inside the Lua call. That alternative is refuted by observation: in the one observed run, the very next statement after the load line saw count=0. It is also refuted by the mechanism: the load is driven from `handlePluginLoads()` in `postConfigReload()`, which runs after the whole config is parsed, and the Lua binding returns nothing awaitable. No scheduler timing, machine load, or plugin size changes this ordering, because the ordering is phase ordering (parse, then postConfigReload), not thread timing. The only "window" that exists is the one between pass 1 and pass 2, and the U6 grep does not look at windows: it greps the whole log, so a marker printed on pass 1 fails the gate even if pass 2 later applies the profile.

(c) The U6 gate as written cannot pass. Runner lines 298-305:

```
# Hook marker check (U6): if the hook ran before the plugin loaded, the
# profile was never applied. Fail fast with that diagnosis. The marker can
# land in the nested stdout log or the per-instance log; check both.
# (NEST_LOG was defined right after the signature discovery, above.)
if grep -a -q "Y6-NEST-HOOK: hyprglass not ready" "$LOG" "$NEST_LOG" 2>/dev/null; then
  fail "hook ran before plugin load (profile not applied); see nested log"
fi
echo "Y6-WAYLAND: hook marker absent, profile applied"
```

The grep is whole-file over both logs with no line scoping and no time scoping. The pass-1 marker is already in `$NEST_LOG` before the plugin-list check runs, so by the time execution reaches line 302 the condition is already true. The `echo` on line 305 ("hook marker absent, profile applied") is unreachable with the current conf: the marker is never absent. Note also that line 305's claim is itself unsound even if it were reachable: marker absence is not proof the profile was applied (see section 3).

What would falsify this ruling: a single nest run with the current conf in which the per-instance log contains no "not ready" marker. The mechanism says that run cannot happen. A run in which the marker appears but the profile is later applied does NOT falsify the ruling, because the ruling is about the gate failing, not about the profile never being applied. Those are different claims, and section 3 keeps them apart.

## 3. Precision correction: what the Y6e artifacts do and do not prove about the profile

The Y6e log and Y6r V4 state "the profile was not applied in this run" / "profile not applied". The precise statement is narrower, and the distinction drives the fix:

- PROVEN: the profile was not applied on pass 1 (config time). The hook's glass branch never ran during the first parse; optics.lua never executed in that pass.
- NOT PROVEN EITHER WAY: whether the profile was applied on the automatic reload pass (pass 2) before teardown at 21:57:14. The artifacts cannot answer this, for three reasons:
  1. Pass 2 is silent when it succeeds. The hook prints nothing on the glass branch, optics.lua prints nothing, and the `postConfigReload` stdout-disable line is first-launch-only (per the 0.57.2 `postConfigReload` code shown in the upstream PR #16111 diff: `if (disableStdout && m_isFirstLaunch)`), so a second parse leaves no identifiable line in the 188-line log. The log is consistent both with "pass 2 ran and applied the profile" and with "pass 2 had not run yet at teardown".
  2. The status JSON exposes no material values. `hyprctl hyprglass status` reports version, versionCheck, active, shaders ("pending" at status time), itemProtocol, and feature flags. It does not report blur_strength (0.15), refraction values, or the registered layer list. "layers enabled true active true" is the plugin's default feature state, not proof that `hl.plugin.hyprglass.layer("computer-use-indicator", ...)` ran.
  3. The liquid gate does not cover it. Per Y6r V9, `scripts/indicator.py` `liquid_available` (line 242) is metadata-only: it reads `hyprglass status` and matches the schema. Its docstring says it is not proof that any pixel is drawn, that the optics look right, or that the indicator namespace is glassed. The U6 check is the only gate asserting profile application, and U6 as written asserts a negative (marker absent) rather than a positive (profile applied).
- Consequence: the U6 failure is a TRUE failure of the gate as written (the marker is present), but it is NOT proof the profile was never applied. The gate conflates "the hook ran early on pass 1" (expected on every run, harmless) with "the profile was never applied" (the real condition). Any fix must replace the negative inference with a positive assertion, or the retry will keep failing a gate that does not measure what it claims to measure. This evidential gap is the reason the verdict is AMEND rather than a narrower "scope the grep" fix: scoping the grep alone would let the run proceed without ever proving the profile applied, and the pill measurement would then be uninterpretable (a negative could mean "no flicker" or "no glass").

## 4. Fix candidates

### 4a. Runner-side `nest hyprctl reload` after the plugin-list/version checks, then re-check

- Works: YES, as the deterministic trigger, provided the U6 grep is re-scoped and a positive marker gate is added (section 4d). This is the recommended primary fix, combined with the positive marker.
- Why it works. `hyprctl reload` re-executes the whole Lua config. Evidence: `hyprctl --help` on the laptop (read-only, no session touched) lists `reload [config-only]`, "Issue a reload to force reload the config"; the dotfiles note records "`hyprctl reload`: the reload runs `glass.lua`, which loads the plugin" and "a reload applies it" for tuning values, and a fixed config surviving five `hyprctl reload`s with one plugin loaded; the `CLuaEventHandler` header comment (destroyed and recreated on every config reload) proves a reload re-runs the config including the hook. On the reload pass the plugin is already loaded, so the hook's glass branch (hook line 15-16) runs and applies the profile, and no new "not ready" marker is printed.
- Is the explicit reload redundant with the automatic reload? Possibly, but that is a virtue, not a defect. The system auto-reloads after config plugin loads ("reloads the config when anything changed"), so the explicit reload may be the second reload rather than the first. When the declared list is unchanged, a further reload is a no-op (the dotfiles fixed config proves this shape across five reloads), so the explicit reload is harmless if the auto-reload already fired, and determinative if it has not fired yet. What the explicit reload buys is determinism from the runner's side: the profile application no longer depends on unmeasured auto-reload timing inside a 7-second window.
- Exact change. File: `improvements/worker-y6b-run-nested-wayland-v2.sh` (repo copy, md5 692d427174fa1c335eb02a46fc5e0a18; the laptop copy must be re-verified byte-identical before the retry, per the Y6d procedure). Insert after the version-parse block (after the `PYEOF` version check, before the U6 block at lines 298-305):
  - `nest hyprctl reload` (plain reload, the form the dotfiles author used five times with one plugin loaded; `reload config-only` is an untested variant and is NOT recommended as the first form, since plain reload is the proven one).
  - Then the positive-marker wait from section 4d (poll `$NEST_LOG` for the applied marker, bounded, e.g. 15 s).
  - Then re-run the plugin-list and version checks (the reload must not have unloaded the plugin; the declared list is unchanged, so it must still list hyprglass 1.1.1-cu.1 with versionCheck match).
  - Then replace the U6 block (lines 298-305) with the positive gate. The old whole-log "not ready" grep must be deleted, not merely scoped: scoping by line offset (`wc -l` before reload, grep only after) would work mechanically, but it preserves a negative inference. The positive marker is strictly stronger and makes the scoping question moot. If a "not ready" marker ever appears AFTER the reload, that is itself a failure (it would mean the plugin was unloaded between passes), and the positive gate fails anyway because the applied marker would be absent, so no separate negative check is needed.
- Risks. (i) The 0.56.2 reload-loop crash (reload to postConfigReload to handlePluginLoads to reload, stack overflow) was caused by a declared list that changed between passes. Our conf declares unconditionally on every pass, so the list is stable and the reload is a no-op after pass 2. The dotfiles fix proves this exact shape safe. (ii) A reload issued while the auto-reload is still pending serializes on the compositor event loop; sequential reloads do not race each other. (iii) Plain `reload` also reloads monitors; in the nest the output is the virtual WAYLAND-1, and the dotfiles nested tests reloaded five times without a monitor incident. None of these risks is a block, but the first retry after the amend must be watched for a reload loop (nested log growing without bound, nest CPU spin) and aborted on sight.
- Version caveat. The reload-after-load and five-reload evidence is from 0.56.2; the 0.57.2 evidence is header-level (handlePluginLoads, m_registeredPlugins, updateConfigPlugins, the event-handler recreate comment) plus the observed 0.57.2 run (count 0 at parse, plugin listed later). The mechanism is corroborated across the version gap, but the 0.57.2 `PluginSystem.cpp` / `ConfigManager.cpp` sources were not read (no source tree on the laptop; the `.cpp` files are not shipped with the headers). If the first amended run behaves differently from this prediction, the source gap is the first place to look.

### 4b. Hook-side deferral / poll / retry inside the hook

Three sub-options, judged separately. No blocking wait exists or is acceptable: there is no sleep in the `hl` API, and a top-level `os.execute("sleep ...")` or `io.popen` in config would block the compositor event loop during the startup double-parse (the dotfiles note warns a top-level `os.execute`, `io.popen`, or `hyprctl` at startup "blocks forever"). Any hook-side fix must be event-driven or timer-driven, never blocking.

(b1) `hl.on("hyprland.start", function() ... apply optics ... end)`: NOT RECOMMENDED as the primary fix. The event exists (wiki: "Emitted once on start"; the live hook already uses it for the visuals.py fallback), but its ordering relative to the plugin load is UNVERIFIED: nothing in the sources read states whether `hyprland.start` fires before or after `handlePluginLoads` completes the async load and the scheduled reload. Worse, the subscription registered in pass 1 is destroyed on the reload (event handler recreated on every config reload), and `hyprland.start` fires only once, so if start already fired before the reload, the pass-2 re-registration never fires and the profile is silently never applied. The failure mode is silent, which is the worst kind for this measurement. Do not use.

(b2) `hl.on("config.reloaded", function() ... apply optics ... end)`: PLAUSIBLE, NOT PROVEN, needs a probe before adoption as the sole mechanism. The event exists (wiki: "Emitted when the config has been reloaded and applied"), and it is the natural hook for a post-load application: the handler is registered on every pass, and on the reload pass the plugin is loaded when the event fires. Open ordering question: within `postConfigReload`, does the `config.reloaded` emission happen before or after `handlePluginLoads` completes? If it fires at the end of pass-1 postConfigReload before the async load completes, the handler must no-op under its guard (count 0) and wait for the reload pass, where it re-registers and fires again with count 1. That chain works if the event fires on every reload cycle, but whether it fires on the initial load cycle at all, and where it sits relative to `handlePluginLoads`, is UNVERIFIED from the sources read. A probe run that logs the event with the plugin count would settle it. Until then, (b2) is a candidate for a later simplification, not the fix to land now.

(b3) `hl.timer` poll: VIABLE, the best hook-side option. The API exists in the running 0.57.2 stubs (`hl.timer(callback, {timeout=integer, type="repeat"|"oneshot"})`, timer with `set_enabled` / `set_timeout`). A repeat timer (e.g. 500 ms) that checks `hl.get_loaded_plugins()`, dofiles optics once when count is 1 and version matches, then disables itself, is expressible entirely in Lua with no runner change and no reliance on event ordering. Required shape: bounded (disable after N attempts, e.g. 30, so a never-loaded plugin does not poll forever); the timer must be created on every pass (the hook runs every pass, so a reload restarts it, which is benign); the optics application must print the positive marker from section 4d. Caveat: timer lifetime across a config reload is UNVERIFIED from the headers (the recreate comment covers the event handler; timers are plausibly tied to the same Lua state lifetime, but this was not confirmed). That caveat is harmless here because the hook re-creates the timer on every pass. (b3) is a sound alternative to (4a) if the runner-side reload is for some reason unwanted, but (4a) is preferred because it is deterministic from the runner (one explicit action, one explicit wait) rather than polling, and because it reuses the already-proven `hyprctl reload` path. Do not land both (4a) and (b3) at once: two application paths would double-apply the profile (harmless, `config()` is idempotent, but it would muddy which path produced the marker). Pick (4a); keep (b3) as the documented fallback.

### 4c. Runner applies optics via hyprctl

- Does NOT work. VERIFIED against the pinned plugin source, not just Y6e council 3's word: laptop worktree `~/.local/share/agent-computer-use/worktrees/hyprglass-03a57c4/src/Diagnostics.cpp:589` gives the usage string `hyprctl hyprglass <status|stats [reset]|items>`. Only three subcommands exist, and none applies configuration. Council 3's claim is independently confirmed.
- Further, neither `status` nor `items` can serve as a positive profile-applied gate. `status` reports version, versionCheck, active, shaders, itemProtocol, and feature flags, but no material values (blur_strength 0.15 is not exposed) and no layer list. `items` lists only live subsurface glass items (`Diagnostics.cpp:200-260` iterates live subsurface entries; empty result is "no active subsurface glass items"): it does not list configured layer registrations, so it cannot confirm `hl.plugin.hyprglass.layer("computer-use-indicator", ...)` ran, and with no pill running there would be no items anyway. (c) is dead. The profile can only be applied from inside Lua config (optics.lua) or by a config re-parse that executes optics.lua.

### 4d. Other mechanisms

(d1) Fix the gate only, rely on the automatic reload. MINIMAL but insufficient alone: replace U6 with a positive-marker gate (optics.lua prints the applied marker; runner polls `$NEST_LOG` for it with a bounded wait, e.g. 15 s, after the version check). This is the smallest change (1 line in optics.lua + U6 block replacement) and it is REQUIRED in every variant, but on its own it depends on unmeasured auto-reload timing: if the auto-reload has not fired within the wait, the run fails with "profile not applied" even though nothing is wrong except timing. Combine (d1) with (4a): the explicit reload makes the wait short and deterministic, and the positive marker makes the gate measure the right thing. (d1) is therefore adopted as part of the fix, not as a standalone fix.

(d2) Split conf with a file swap: conf A loads the plugin only; runner waits for the plugin list, swaps the config file to conf B (load + hook), then `hyprctl reload`. REJECTED. It adds a mid-run file swap, a second config path to keep in sync, and a new failure mode (swap racing the auto-reload), for no benefit over (4a), which achieves the same second parse without a swap.

(d3) `hyprctl plugin load` from the runner after the config load: REJECTED. The plugin is already loaded by then; a redundant manual load is a no-op at best and does nothing toward applying the profile.

(d4) Apply optics from the pill process: REJECTED. The pill is a layer client; `hl.plugin.hyprglass.config()` is an in-compositor Lua call with no IPC equivalent (see 4c).
