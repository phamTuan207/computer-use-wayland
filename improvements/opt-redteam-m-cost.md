## 1. Cost per method

### M1 class A (8 steps): cheap on paper, expensive at the live gate

- A1 (verify d27ad0a sha): about 2 minutes, one command, read-only. Cost already paid by this redteam (section 0 N-1). Token cost: negligible (estimate: one short exec + read).
- A2 (code gaps): 6 of 7 items already landed (392bc09, 5b11696). Remaining cost is A7 only: one test assertion change plus an independent test run. Wall time estimate: 30-60 minutes including council + redteam over the diff (Lauren Tan) and the laptop test run (the session tests cannot run on VM Python 3.12.3, so the run needs the laptop). Token cost: low (estimate: one code-edit cycle + one review cycle). Risk: the file scripts/cursor_session.py is concurrently modified (git status 23:01 showed it modified by another worker), so the A7 edit risks a merge conflict if it is not rebased first.
- A3 (re-pin check): one check in sync-installed.py/setup plus a test with a deliberately drifted fixture. Wall time estimate: 1-2 hours (code + test + council + redteam). Token cost: low-medium (estimate). Risk: the check runs on the laptop against gitignored files; a false LOUD failure at login would block the owner's next login loader run, so the check must fail loudly without failing the login itself, a distinction the verdict does not draw.
- A4 (live activation): the most expensive step in class A. One live window, single operator, preconditions 1-8, plus the lock wrapper (unproven, P-6) and the corrected proof (fresh observe, one click, cursorpos + second observe, clean stop). Wall time estimate: 30-60 minutes of live work plus the pre-flight (precondition 2, same-minute checks). Token cost: medium (estimate: one live run with an agent driving). Live-machine risk: HIGH. The activation loads two plugins into the live compositor (glass then guard). A load failure mid-sequence leaves a half state (glass loaded, guard not), and the verdict's half-state recovery (never re-run activate-glass after partial success, guard-only retry) is agreed in advance but untested. A compositor crash during activation stops the user's machine while the user sleeps; the contingency is "stop and report", which is correct but leaves the machine down until the user wakes. The 22:56 recurrence shows the slot can re-wedge within seconds of a tab close, so the activation window's PID-stability precondition (precondition 1) can go stale between sign-off and activation. Cost of a failed activation is not just the run, it is the next F3 restore cycle (about 68s restart + 8.5s cleanup + verify) plus re-gating.
- A5 (proof of restoration): same live window as A4, marginal cost. Wall time estimate: 10-15 minutes inside the A4 window. No separate live risk.
- A6 (hyprglass gate): one code change + its own council + redteam + tests. Wall time estimate: 2-4 hours (design the warm-up distinction with a measured window, implement, review, test). Token cost: medium (estimate). Live-machine risk: MEDIUM. A too-strict gate breaks working sessions (the verdict says so itself); a too-loose gate lets C1 return. The gate is the only step in class A whose failure mode harms the owner's daily use rather than just the test run, because it refuses sessions. It must ship with a bypass or a logged refusal that names the remedy, and the verdict does not specify either.
- A7 (tracked follow-up): process cost only, negligible wall time, but it is the step that decides whether class A is "complete". Cost of skipping it: the next optics change repeats the incident (the drift took one sync to create; the repair took from 22:19 to 22:37 to diagnose and fix live, plus the council cycle).
- Class A total: paper steps about 3-6 hours of agent work (estimates); live steps one 30-60 minute window with HIGH live-machine risk concentrated in A4. The verdict prices A4 as one step; it is the step that can cost the owner the user's morning browser if it goes wrong.

## 2. The commit method and the queue, priced

### Commit method (CM-1 to CM-6, ORDER section 4)

- Small-and-many commits: the cost is paid in push/verify cycles. Each push + ls-remote verification is about 1-2 minutes of wall time. At the observed rate (389 UTC-day commits on todolist-push by 23:05), the fleet paid roughly 6-13 hours of aggregate push/verify time today, spread across workers. That is the price of the discipline, and it bought the merge: 313 commits merged at 23:05, graph 145 to 456. The method's cost is real and its payoff is now measured, not assumed.
- The 26366a9 sweep (Attack F-1) cost: one Y14b file (+329 lines) misattributed to OPT in a log commit. The cost of fixing it is a follow-up commit that re-attributes or a note in the Y14b log; the cost of NOT fixing it is a permanent misattribution in the history, which matters when the owner asks who wrote what. Cheap to fix, embarrassing to leave.
- Merge conflicts: the 23:05 merge resolved 3 conflicts by "keeping both sides". The cost of a keep-both-sides resolution is a post-merge content check on each conflicted file, about 15-30 minutes, which no verdict prescribes. A duplicated section in a coord file can silently double-count a task or re-open a closed gate. The cost of skipping the check is paid later, by the worker who trusts the duplicated text.
- The graph target is exceeded (456 vs 240). The remaining cost of the commit method is therefore zero on the graph axis: no further commits are needed for the number. Any further "commit more and smaller" pressure after the target is met is pure cost with no payoff, and the verdicts should say the target is closed. ORDER 4.3's arithmetic is moot (Skeptic P-22).

## 3. Risks the verdicts underprice

- R-1. The restart tax. Seven slot failures in one evening, two after the "fix". Each restart costs about 2-3 minutes and one unflushed tab. The verdicts treat the restart as a recovery with a one-time cost; the evidence shows it is a recurring tax until D-6 lands. D-6 should be first on cost, not last in the method.
- R-2. The rehearsal wedge. B4's close step is a trigger for the exact failure D is fixing. The verdicts price the rehearsal as harmless; the 22:56 recurrence says the close step is the most dangerous part of the rehearsal.
- R-3. The activation half-state. A4 loads glass then guard; a failure between them leaves glass loaded and guard not, with a recovery that has never been tested. The cost of the half-state is a second live window to recover, or a session that starts pill-less (C1 through the second door).
- R-4. The gate that breaks working sessions. A6 refuses sessions when glass is down. A false refusal on a working session costs the owner the user's morning automation, not just a test run. The verdict does not price the false-refusal rate or specify a bypass.
- R-5. Idle live slots. O-3 has no judge, Y13g has no output, Y14b is still re-staging. The live slot is the scarcest resource in the queue (one runner, one session, one screen), and the verdicts leave its allocation to an unnamed judge at slot-free time. Every hour the slot idles while the owner sleeps is an hour that cannot be recovered.
- R-6. The keep-both-sides merge. Three conflicts resolved by keeping both sides at 23:05, with no prescribed post-merge content check. A duplicated gate or task in a coord file is a cheap defect to create and an expensive one to debug at 03:00.
- R-7. The scrub re-clone. Rank 11 requires every agent to re-clone. The verdict never prices the re-clone or names who notifies whom. An unpriced, unscheduled fleet-wide operation is the item most likely to be deferred forever, which is exactly what O-5's missing date guarantees.
