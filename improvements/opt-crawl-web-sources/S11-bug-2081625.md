# S11. Bugzilla 2081625: connect-existing hangs 60s when another session is active

- Class: (d) Firefox Marionette browserElement is null and session creation failures
- URL: https://bugzilla.mozilla.org/show_bug.cgi?id=2081625
- Accessed: 2026-11-21
- Crawler: OPT-WEB, 2026-11-21 22:50 +07

## What they did

Mozilla fixed the firefox-devtools-mcp connect path. Marionette allows only one session; a second client gets its socket closed with no error, and geckodriver retries silently for about 60s. Fix: the checkPort probe now waits for the Marionette hello greeting; if the socket closes before the greeting arrives, it fails at once with "Another WebDriver session is already active".

## Evidence shown

Measured 60.1s on main, 4-6ms with the patch. Same PR added a 45s timeout (with geckodriver killed) when Firefox never answers the session request, e.g. an unanswered "Allow remote control?" prompt, and an idle-timeout option for the fixed 30-minute idle hold.

## Applicability verdict: APPLIES

This explains a whole class of our "session creation hangs with no error" reports: a stale session is still attached, and our new connect attempt waits 60s in silence. The fix is directly copyable: before creating a session, probe the Marionette socket and wait for the greeting; if the socket closes, report "another session is active" at once instead of retrying for 60s. Also copy the 45s hard timeout with kill: a session request that never answers must die loudly, never hang the runner. This also reinforces our one-live-runner rule with a mechanism: the second runner must fail fast with a clear message.
