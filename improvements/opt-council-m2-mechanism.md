## D. Marionette browserElement-null slot

### How the driver actually works

- Session creation path, proven from the shipped source copy at ~/workspace/zen_tab_cleanup/source/driver.sys.mjs-FIREFOX_160_0_RELEASE (160,552 B, 4,794 lines, extracted from the laptop top-level omni.ja, upstream cross-check FIREFOX_160_0_RELEASE, line numbers identical; source: improvements/worker-f3-marionette-slot-log.md, root cause section):
  - `newSession` at line 2616. Its loop at lines 2706-2707 iterates every window and calls `this.#registerWindow(win, { registerBrowsers: true })`.
  - `#registerWindow(win, options)` at line 4633. At line 4640 it passes `lazy.TabManager.getBrowserForTab(tab)` into `#registerBrowser`, with no null check and no filtering.
  - `#registerBrowser(browserElement)` at line 4608. At line 4616 it dereferences `browserElement.namespaceURI` with NO null check. A null input throws exactly the observed TypeError.
  - `TabManager.sys.mjs` `getBrowserForTab(tab)` at lines 39-41 returns `tab?.linkedBrowser ?? null`. So a tab whose `linkedBrowser` is null produces a null input to `#registerBrowser`, and ONE such tab kills the whole session.
  - `TabManager.getBrowsers()` (same file, lines 60-75) maps tabs through `getBrowserForTab` and then filters `browser !== null`. `#registerWindow` does NOT use it. The null filter exists in the codebase; the session path does not call it.
- Client side, proven from scripts/zen_dom.py lines 81-112: `__enter__` takes a non-blocking flock (lines 85-90, one session only), spawns geckodriver with `--connect-existing --marionette-port 2828 --port 4444` (lines 93-99), waits for the status endpoint, then POSTs `/session`. On failure it calls `_cleanup` (lines 117-137: DELETE session if any, terminate geckodriver, unlock) and raises. The error message at lines 106-111 already names the single-session-slot leak as the suspect ("only a Zen restart clears it").
- Session cap, proven from docs/zen-dom-control-comparison.md via todolist 1.2.1: BiDi and Marionette SHARE one session cap (1 session TOTAL). A leaked session blocks both.
- Observed failures, from improvements/worker-f3-marionette-slot-log.md event log: POST /session HTTP 500 "browserElement is null" at 22:06, 22:10, 22:12, 22:20, and 22:31 (instant, 0.0s). Five failures over 25 minutes, same string every time.

### The exact failing point

- The failing point is `#registerBrowser` line 4616, reached through `#registerWindow` line 4640 with a null `linkedBrowser`, reached through `newSession` lines 2706-2707. The driver has no guard at any of the three levels.
- The trigger is a tab with null `linkedBrowser` sitting in the tabbrowser. Two upstream facts bound it: Bug 1342723 says `removeTab` sets `aTab.linkedBrowser = null`; Bug 1366988 (2017) is the same `be.namespaceURI` access in the same error family (source: F3 log root cause section).
- What the trigger is NOT, proven by F3 22:38: lazy tabs do NOT break `#registerBrowser`. After the restart, Marionette created a session in 0.1s and listed 67 tabs with about 52 lazy tabs present (F3 log 22:37:32). A lazy tab still has a `linkedBrowser`; only a destroyed or mid-removal tab has null.
- Prime suspect for the trigger, UNPROVEN (F3 log, corrected theory 22:38): the pass-1 cleanup teardown. Its sacrificial-tab open failed with 404 "Browsing context has been discarded", and DELETE /session ran while current was a discarded tab. That sequence can leave a zombie tab element with null `linkedBrowser` in the tabbrowser from about 22:06 through 22:31. The restart rebuilt the tabbrowser fresh and cleared it. The 22:03 to 22:06 change trigger is still unproven, and the zombie was destroyed by the restart, so its identity can never be recovered from that instance.

### What must change

- D-1 (this voice's position, adopted in the verdict): client-side avoidance plus a restart ladder. No browser patch. Three changes:
  1. `scripts/zen_dom.py`, session creation: before POST /session, run a BiDi liveness probe (BiDi `session.new` plus `browsingContext.getTree` do NOT call `#registerBrowser`; F3 log states BiDi worked throughout the outage). If BiDi answers and POST then fails with the exact string `browserElement is null`, do NOT retry POST blindly. The retry ladder is: record the failure, restart Zen by the F3-proven sequence, POST once more.
  2. Restart sequence, exact commands from F3 log 22:36:24 to 22:37:32: `pkill -TERM zen-bin` on PID 27958 (clean exit after 1s, no zen/gecko processes left), relaunch via the zen-ai wrapper detached (new PID 426338), wait for BiDi 200 on 9222 and LISTEN on 2828, then POST /session once. Result proven: session created in 0.1s, id dfd532f5-7423-4e11-9171-f35410d0a73e, list_tabs 67 tabs in 7.7s.
  3. Cleanup hygiene, in the cleanup code and in the todolist gate G-TAB: open the sacrificial tab FIRST, end the session while focused on a live tab, never DELETE /session while current is a discarded tab. This is the step whose violation is the prime suspect for creating the zombie.
- D-2 (rejected by this voice after debate): patch `driver.sys.mjs` inside omni.ja, adding a null check at line 4616 or making `#registerWindow` use the `getBrowsers()` null filter. It is the root fix at the exact line, and this voice argued for it first. It loses on three mechanism facts: the file is shipped inside omni.ja, so a repack must be redone on every Zen update and there is no verified signature story for a repacked omni.ja; the restart already clears the zombie, so the patch buys nothing the ladder does not already buy; and the patch is untestable without a restart anyway. Keep D-2 as a redteam attack surface, not the method.
- D-3 (rejected): avoid Marionette entirely and drive by BiDi only. BiDi pointer click is proven broken twice (todolist 1.1.1: v1 counter STILL 0, v3 stayed 1; firefox-mcp click works because it goes through Marionette). Marionette is needed for clicks. BiDi alone cannot drive.
- Interaction with F1: the computer-use session guardian failure (22:15, dies in 0.46s, "session guardian startup failed") is a DIFFERENT session path from `zen_dom.py`. F1 log proves its cause is the cursor-guard plugin not loaded (live plugin list hyprbars only, `hyprctl cu-cursor status` returns "unknown request", `check_guard` throws JSONDecodeError). Do not conflate the two. The D method touches only the Marionette slot; F1 owns the guardian path.

## E. Zen wedge / workspace switching

The owner order 22:45 (todolist 4.28, J21) is: open the Omarchy menu and switch workspaces by COMMAND in hl.dsp form, NEVER mouse click on bar buttons; CLI first, mouse last.

## G. Hidden-body decisive experiment + composite/blind test design

### How the suspect mechanism actually works

- Proven from improvements/worker-y4b-hidden-body-root-cause.md, which this voice verified against its cited sources: Transparent Zen 0.9.4, installed at ~/.config/zen/profile.Default (release)/extensions/{74186d10-f6f2-4f73-b33a-83bb72e50654}.xpi, injects a content script on every page (all_urls, document_start): CSS dist/transparent-zen.css plus JS dist/transparent-zen.js.
  - CSS: `:root.tz-hidden body { transition: none; visibility: hidden; background: none; opacity: 0 }` and `:root body { transition: visibility .25s, opacity .25s, background-color .25s; visibility: visible; opacity: 1 }`.
  - JS: `initLoadingScreen()` runs first in the constructor, adds `tz-hidden` to documentElement synchronously at document start. The only removal is `removeLoadingScreen()`, which removes the class 500 ms after being called. Removal is gated on an async chain: fetch of data/ContentScripts.json, then browser.storage.local.get("transparentZenSettings"), then branch paths, with a .catch that also removes. A stall anywhere before a remove call leaves the class on, with NO timeout or fallback in the decoded chain.
  - This produces exactly the observed symptom: body computed visibility hidden plus opacity 0, html visible, no inline style, no author rule, DOM present, innerText empty, visibilityState and hasFocus unaffected.
- V1 (class stuck): badly wounded, not dead. Its wounds, from the Y4b synthesis: R's "no class" is two concordant records (RUN-REPORT-AGYQ-20261121.md lines 133-135 and worker-r-test-run-log.md line 73), and probe_q05e was built to capture exactly htmlClass (probe_q05e.py lines 12-14), but the output was never saved, so V1 is not logically falsified; the burden of proof now sits on V1. Second denied prediction: initLoadingScreen() also sets the --zen-logo-path inline property, and removeLoadingScreen() removes it, so under V1 the inline property should still be present, but R reported "no inline style". Zero positive sightings: no probe ever saved a classList.contains("tz-hidden") result, an opacity reading, or a screenshot of the logo pulse markers. No clearing mechanism: a geckodriver kill cannot unstick an extension content-script fetch in already-loaded tabs, and a click in a different visible tab cannot settle a stalled chain in hidden tabs; old hidden tabs were never re-checked. The reused-tab datum is awkward: probe_y4c navigated a pre-existing about:blank tab to q01 and got a visible body, while new tabs to the same fixture were hidden seconds earlier; a document_start content script runs on a navigation in an existing tab exactly as on a window/new tab, so V1 needs an auxiliary hypothesis it does not have.
- V2 (transition frozen): DEAD as stated. The CSS visibility interpolation rule, verified against two independent sources after the council met (css-animation.com; blog.kizu.dev quoting the spec): during a hidden-to-visible transition the interpolated value is visible from the first frame. The probes read hidden minutes later, across many evals. V2 predicts the exact opposite of the measured value. Any future observation of class-absent plus computed-hidden is OTHER_HIDDEN, not V2. The fix design's V2 category and repaint step must be removed.
- Stale geckodriver as common cause: DEAD. Incident 2 ran on a fresh port (4448, never used; R used 4446, P used 4450, default 4445), no geckodriver process was running at the 18:05 check, and the state cleared with no kill performed.
- Third mechanism (required if R's "no class" is accurate): strongest sketch is redteam E1, a blind-scan / hidden-sheet rule. Carriers visible in probe_q05e's own code: a rule nested inside a grouping rule (@media, @supports, @layer, @container) that the flat top-level scan never visits (r.style is undefined on grouping rules), or a sheet whose cssRules throws in page context (cross-origin or extension sheet, silently skipped by catch (e) { continue; }). Transparent Zen's dynamically injected sheet is ruled out as the carrier (no visibility/body rule). Obsidian Web Clipper remains the unexamined candidate.
- Record corrections adopted from Y4b: "switch away and back does not fix it" is a non-observation (probe_y4d's tab was visible from the start; probe_q05d's code only fetches handles and prints the count, the switch was never executed). "Cleared by itself" is mislabelled in both incidents (clearing verified only on NEW tabs under new sessions; old hidden tabs never re-checked). The fix paper's bootstrap story is false (a navigation in a reused tab creates a new document and document_start scripts run on it). The geckodriver-kill causation for incident 1 is unproven correlation. The input freeze onset (17:59:13) predates probe_y4c's navigations (17:59:27, 17:59:33), so y4c did not cause the freeze.

### What must change

- Fix design, adopted from Y4b with its redteam corrections, in run_live.py / run_agyq2.py: one eval, one snapshot (`diagnose_body`): readyState, documentElement classList (tz-hidden, tz-initialized), body computed visibility/opacity/display plus html visibility, body inline style, transition property/duration/delay, body rect, innerText length (corroboration only), hasFocus/visibilityState, URL. Sample twice 300 ms apart when hidden. Classification: VISIBLE, TZ_STUCK_V1, OTHER_HIDDEN, FIXTURE_FAILURE. Recovery ladder, 8 s total budget per tab opening: poll 250 ms up to 2.0 s for the extension's own removal; if V1 persists, remove tz-hidden exactly as removeLoadingScreen does (single eval, test tab only, test origin only, logged as intervention); then fall back to the bootstrap tab; then declare infra-blocked (`INFRA: hidden-body`, never a fixture failure; two consecutive infra-blocked tests abort the suite). The repaint step is removed (V2 dead). Never use a real click as a recovery probe. The switch-away step is removed entirely: the landed `ensure_visible` switches to the first non-test handle, which is a user tab by definition in a live Zen, a focus steal that violates the no-tab-driving rule while the owner is present. Replace `ensure_visible` internals, keep the name and call sites.
- `bootstrap_tab`: KEEP and strengthen (verify the reused tab with `diagnose_body` before returning it; narrow the reuse match to known fixture paths; record handle and URL; re-verify the handle still exists per test; add a `rebootstrap_tab` path). Its evidence base is n=1 confounded by time, so it is harness defense, not a validated fix. It must never take an about:blank tab without an ownership check, and the tab is returned to about:blank at suite end, never closed.
- Pass accounting: a test that passed only after `removed-tz-hidden` is a FLAGGED pass, counted separately, not folded into the headline pass count. Removing the class masks a real user-facing defect (a real user opening a new tab in this Zen during such a window sees a blank page for minutes), so the intervention must be disclosed in the test report and tracked as a separate item to fix or disable the extension.
- `WD.goto` is the choke point: diagnose after the 1.0 s settle, never return a hidden page as ready. `WD.__enter__` orphan fix: cleanup on raise, PID file, geckodriver log file instead of DEVNULL. `preflight()` fails closed before any tab opens: stale-geckodriver sweep by PID with parent check (kill only verified orphans), single-session lock check, Zen liveness, fixture server loopback check, owner-away check (explicit `LIVE_OWNER_AWAY=1`, never inferred from silence). The Hyprland IPC check, if kept, is a safety gate, not an incident detector.
- Decisive experiment, adopted from Y4b (design only, do NOT run now): 6 phases. Phase 0 baseline snapshot (Zen PID, Marionette, hyprctl with 10 s timeout, geckodriver ps table, extension state, bootstrap tab recorded). Phase 1 reproduction loop, extension ENABLED, up to 30 window/new opens alternating example.com and the q01 fixture, full payload at 0 / 0.5 / 1 / 2 / 5 s; stop early on a hidden tab, keep it open, go to Phase 2. Phase 2 frozen-state capture on the SAME hidden tab, in order: wait 10 s, window.focus() plus 2 s, switch away and back (the test that never ran), Marionette click attempt (record the exact error), then open a NEW tab and IMMEDIATELY re-capture the OLD tab; this old-versus-new pair is the single most important capture. Phase 3 stale-driver test, only if a hidden tab persists: ps table, kill orphan by PID only (or record that none exists), fresh session on a fresh port, re-eval the SAME old tab, then a fresh new tab. Phase 4 control arm, extension DISABLED, repeat Phase 1 (30 iterations); re-enable at the end and confirm the original state. Phase 5 control arm, bootstrap navigation vs window/new, 10 each, extension enabled. Capture payload at every step: htmlClass full string plus classList array, htmlInline, bodyClass, bodyInline, bodyVis, bodyOpacity, htmlVis, transition property/duration/delay, matching-rules scan (recursive into grouping rules, with per-sheet readability flags), innerLen, hasFocus, visState, readyState, URL, rect, rAF tick count and largest gap over a 5 s window, presence of the Transparent Zen ::before/::after logo markers, a screenshot, and the geckodriver ps table at the same minute.
- Composite/blind test design, adopted from improvements/zen-ordinary-user-tests-20261121.md (ZT-A v2) and the owner test rule 22:23 (F1 log): future tests are composite (DOM + CLI + mouse + keyboard in one test), the test-maker must not know the questions (independent test-designer), the executor runs blind (ZT-B has not seen the scenarios), cleanup is identity not count (title set must equal the pre-scenario set, count alone never enough), pre-close check before EVERY Ctrl+W (DOM active title must equal the expected test-tab identity or STOP), [CHECK] steps are instrumentation not user steps (a failed control makes the scenario INCONCLUSIVE not FAIL, except the two safety gates), ZT-00 health gate first (step 3, Marionette session creation, is the deciding check; the known "browserElement is null" failure is a gate failure), one runner at a time, 90 minutes maximum.
