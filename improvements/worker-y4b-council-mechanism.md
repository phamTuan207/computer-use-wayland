# Council Member A (mechanism): position paper on the hidden-body incident

## Verdict

V1 (Transparent Zen class stuck) is the best supported mechanism for the hidden-body symptom as a class, and V2 (class removed but the 250 ms visibility transition frozen by a stalled refresh driver) is the weaker rival: V1 needs only one verified failure point, a stall anywhere in the extension async chain that gates removal of `tz-hidden`, and it predicts the exact observed CSS state, the new-tab-only pattern, and persistence through focus changes, while V2 needs a second, unevidenced failure, a total stop of paint ticks for 5+ minutes on a foreground tab in an actively used window, and its predicted clearing on repaint was never observed on a hidden tab. The one datum that points the other way is R's incident 1 report of "no class" and no matching rule, which if accurate would falsify V1 for incident 1 and leave V2 standing there, but that datum survives only as a summary, the probe output was never saved to disk, so it cannot overturn V1's structural case. The verdict is therefore a lean, not a proof: V1 leading, V2 live for incident 1 only if R's summary is verified, and the two incidents are not proven to share one mechanism.

## What is not in dispute

Transparent Zen 0.9.4 is the only candidate in the evidence that produces exactly this symptom by code, not by analogy. Its manifest content scripts match `<all_urls>`, run at `document_start`, and inject both CSS and JS on every page, including the http://127.0.0.1 fixtures and example.com (evidence pack lines 45-46). Its CSS sets `:root.tz-hidden body { transition: none; visibility: hidden; background: none; opacity: 0 }` (pack lines 49-51). Its JS adds `tz-hidden` to `documentElement` synchronously at document_start in `initLoadingScreen()`, called first in the constructor (pack line 54), and the only way the class leaves is `removeLoadingScreen()`, which removes it 500 ms after being called (pack line 55). Removal is gated on an async chain: fetch of `data/ContentScripts.json`, then `browser.storage.local.get("transparentZenSettings")`, then branching through supported-site, dynamic-transparency, or `processPage()` paths, with a `.catch` that also calls remove (pack lines 56-60). A stall anywhere before a remove call leaves the class on indefinitely, with no timeout or fallback in the decoded chain. No author CSS, inline style, user stylesheet, or UA rule explains the symptom: the fixture contains zero occurrences of "visibility", example.com has no author stylesheet, and no `chrome/` directory exists in either Zen profile (pack lines 73-76).

## Evidence for V1 (class stuck)

1. Single failure point, code verified. V1 requires only that the fetch, the storage read, or the extension background process stall. Each of those is a real async step in the removal path (pack lines 56-60). A fetch that never settles or a storage read that never settles produces a hidden body lasting minutes with no further assumption. Weight: strong for V1.
2. New-tab-only pattern fits V1 exactly. Pre-existing tabs loaded before the wedge already had the class removed and stay visible; new tabs loading during the wedge get the class added at document_start and never get it removed. Probe y4b found all 22 pre-existing tabs visible and a fresh test tab hidden (worker-y4-run-log.md lines 17-20; probe_y4b.py lines 36-52). Weight: strong for V1, and equally strong against any page-content cause.
3. Persistence through focus fits V1 and is predicted by it. The class is in the DOM, so `window.focus()` and waiting change nothing. Incident 1 persisted past 5 s and past `window.focus()` (RUN-REPORT-AGYQ-20261121.md lines 137-141; worker-r-test-run-log.md lines 63-76). Probe y4b re-checked after `window.focus()` plus 2 s and the tab was still hidden (probe_y4b.py lines 51-56). Weight: moderate for V1, moderate against V2 (see below).
4. One mechanism covers both incidents without extra parts. Incident 1 and incident 2 share the same symptom, the same new-tab-only scope, and the same Zen process (PID 27958, alive since 15:31; worker-y4-run-log.md lines 7-9). V1 explains both with the same wedge and recovery. Weight: moderate for V1 as the common cause.
5. The stale-geckodriver and Hyprland facts do not compete with V1. A geckodriver cannot set CSS visibility, and incident 2 had no geckodriver running at the 18:05 check (pack line 39), so a geckodriver mechanism cannot be the necessary cause. The Hyprland IPC wedge (pack line 37) has no path into the extension async chain. Neither fact weakens V1; both are at most correlates of a bad window, not rival CSS mechanisms. Weight: neutral to slightly for V1, by elimination.

## Evidence against V1

1. R's "no class" finding, incident 1. R's report says "No inline style, no class, and no stylesheet rule sets it" (RUN-REPORT-AGYQ-20261121.md lines 133-135), and R's log repeats "No inline style, no class, no matching stylesheet rule" (worker-r-test-run-log.md line 73). V1 predicts `document.documentElement.className` contains `tz-hidden` during the hidden state (pack line 66). If R's summary is accurate, V1 is falsified for incident 1. Weight: this is the single strongest datum against V1, and the only direct evidence for V2. But it is discounted heavily for three reasons, and the discount is the crux of this paper.
   a. The probe output was not saved. Only R's summary survives (pack line 84). The exact `htmlClass` value is unverified, so the finding cannot be checked, quoted, or re-read. A summary is not a measurement.
   b. The wording is ambiguous. "No class" does not say which element had no class, nor does it quote the value. Probe q05e collected both `bodyClass` and `htmlClass` (probe_q05e.py lines 12-14), and the summary collapses them. It is possible R meant the body had no class, or that no class relevant to hiding was seen. The paper does not claim R misread it; it claims the record does not let us tell.
   c. The matching-rule scan is a second check pointing the same way, but it shares the same unverified status, and it has its own blind spot: it skips sheets whose `cssRules` throw (probe_q05e.py lines 20-28). If the Transparent Zen sheet were inaccessible from page script, the scan would miss `:root.tz-hidden body` even with the class present. The `htmlClass` read has no such blind spot, which is why its loss matters more than the scan's.
   Net weight: strong against V1 if true, but treated as unproven because unverified. It keeps V2 alive for incident 1; it does not establish V2.
2. No direct observation of `tz-hidden` anywhere. No probe in either incident saved a `classList.contains("tz-hidden")` result, and incident 2 never collected `htmlClass` at all (see below). V1 is therefore supported by code plus fit, not by a sighting of the class. Weight: moderate against V1 as a proven claim, though not against V1 as the leading hypothesis.
3. The reused-blank-tab datum is awkward for a pure V1 reading if read as a tab-type effect. If the extension chain were wedged globally, a navigation in a reused tab during the wedge should also add the class at document_start and stick. The reused tab was visible (pack line 34). This is only awkward, not fatal, because of the time-order confound discussed below. Weight: weak against V1.

## Evidence for V2 (transition frozen)

1. R's "no class" plus "no matching rule" is exactly what V2 predicts (pack line 67). If the class was gone and no rule matched while the body was still computed hidden, something below the rule layer must be holding the old value, and a frozen transition is the candidate the evidence offers. Weight: moderate for V2, entirely conditional on R's unverified summary being accurate.
2. V2 explains why the symptom looks browser-side with no author trace. That part is shared with V1, not distinctive. Weight: weak for V2 specifically.

## Evidence against V2

1. V2 needs paint ticks to stop entirely, not just slow down, and nothing in the evidence shows that. The pack itself notes background tabs in Firefox are throttled to about 1 Hz, which alone would complete a 250 ms transition within about 1 s of wall time, so V2 needs a total stop for 5+ minutes (pack lines 69-70). No probe measured paint ticks, frame presentation, or vsync, and no evidence shows a foreground tab in an active window can have a fully stopped refresh driver. Weight: strong against V2.
2. The window was evidently painting. All 22 pre-existing tabs rendered visible during incident 2 (probe_y4b.py lines 36-52), and the owner was actively using the machine until about 17:59 (worker-y4-run-log.md lines 20-21). A compositor or refresh stall total enough to freeze one foreground tab for minutes sits badly with a live, usable window. A per-tab refresh stall affecting only `window/new` tabs and sparing a reused tab in the same window is possible in theory but is an extra mechanism with no supporting observation. Weight: strong against V2.
3. V2 predicts clearing on repaint, and repaint attempts on hidden tabs failed. Incident 1 persisted past `window.focus()` (RUN-REPORT-AGYQ-20261121.md lines 137-141). Probe y4b tried `window.focus()` plus 2 s on a hidden tab and it stayed hidden with the click still failing (probe_y4b.py lines 51-56). Switch-away-and-back was never successfully tested on a hidden tab: probe y4d's fresh tab was already visible from the start (worker-y4-run-log.md line 20; probe_y4d.py lines 38-47), so it proves nothing about un-hiding. The "cleared right after a real click" claim in the Y4 log is about a new tab being visible, not an old hidden tab clearing (see the clearing caveat below). Weight: moderate against V2.
4. V2 needs two independent failures where V1 needs one: the removal chain must complete normally and on time, and the refresh driver must then freeze completely. Nothing in the evidence links those two, and the timing flip (same flow passing at 16:34, failing at 16:36; passing at 16:58 in U's run, failing at 17:52) is easier to read as a wedge starting and stopping than as a refresh driver stopping exactly on new tabs. Weight: moderate against V2 on parsimony.
5. Incident 2 gives V2 no support at all. None of the Y4 probes collected `htmlClass`: probe_y4b's VIS_JS reads body visibility, html visibility, rect, focus, visibility state, and viewport only (probe_y4b.py lines 12-20); probe_y4c adds only inline body visibility (probe_y4c.py lines 12-17); probe_y4d reads only body visibility, focus, and visibility state (probe_y4d.py lines 12-17). So incident 2 cannot discriminate V1 from V2, and V2's only positive evidence comes from incident 1's unverified summary. Weight: V2 is untested in incident 2, not supported by it.

## The five weighted items the task names

1. R's "no class" finding. Weight: the decisive item if verified, heavily discounted because unverified. It is the only evidence that separates V1 from V2 in incident 1, and it was collected by a probe that demonstrably read `htmlClass` (probe_q05e.py lines 12-14), so the collection is real and the reporting is the weak link. Treat it as a live hypothesis-killer for V1 in incident 1, not as a fact. Incident 2 has no equivalent datum.
2. "Clearing verified only on NEW tabs." Weight: neutral between V1 and V2, but destructive to three inferences in the record. Incident 1's clear was verified only on a new tab under a new session after the geckodriver kill (pack lines 23-26), and incident 2's clear was verified only on a fresh tab in probe_y4d (pack line 36). In both cases the old hidden tabs were never re-checked, so whether they stayed hidden is unknown (pack line 26). This kills: (a) the claim that killing the stale geckodriver caused the clear, which is correlation with a new-tab observation, not a before/after on the same tab; (b) the claim that the state "cleared by itself" in incident 2, which is a new-tab observation mislabelled as a state change; and (c) any V2 support from "clearing on repaint", since no hidden tab was ever observed clearing. It is consistent with both variants under a global wedge lifting: tabs created after recovery are visible, tabs created during the wedge may stay hidden forever. A future probe must re-check the original hidden tab.
3. The example.com datum. Weight: strong for a browser or extension cause, neutral between V1 and V2. A new tab to example.com was hidden (probe_y4c.py, via worker-y4-run-log.md line 18; pack line 14). Example.com is a bare page with no author stylesheet, so author CSS and fixture bugs are out as the common cause. Transparent Zen matches `<all_urls>` and runs there (pack line 45), so the datum fits the Transparent Zen family in both variants. It also rules out Browsec as the common cause (https-only scripts cannot explain the http fixture tabs; pack line 78) and rules out the fixture as the cause.
4. The reused-blank-tab datum. Weight: moderate for a tab-creation or timing effect, weak as a discriminator between V1 and V2. Navigating a pre-existing about:blank tab to the q01 fixture gave a visible body with working click and type (probe_y4c.py lines 40-60; pack line 34). Two readings compete and the evidence does not separate them. Reading A (tab-type): something about `window/new` creation, as opposed to navigation in an existing tab, triggers the hiding, which would point at creation-time injection or a fresh-tab refresh state. Reading B (time-order): probe_y4c ran its checks in sequence, new q02 tab hidden, new example.com tab hidden, then the reused tab visible, so a global wedge may simply have lifted between the second and third checks. Under reading B the datum is consistent with both V1 and V2. Under reading A it is awkward for V1 (a wedged chain should also stick on a navigation) and awkward for V2 (a stalled refresh driver should also freeze the reused tab in the same window). The probe checked the reused tab about 2 s after navigation against about 2 s for the new q02 tab, so settle time does not obviously explain the difference, but the sequential order means time is confounded with tab type. No conclusion about mechanism follows from this datum alone.
5. The Hyprland IPC wedge. Weight: weak and indirect, slightly against V2 as a direct cause and neutral for V1. Hyprland IPC was unresponsive through the whole incident 2 probe window: `hyprctl version`, `monitors`, and `clients` hung, and direct socat to `.socket.sock` hung, while Zen PID 27958 stayed alive and Marionette stayed fine (pack line 37; worker-y4-run-log.md line 21). Three readings are possible and the evidence separates none of them: cause (a compositor problem stalls paint, feeding V2), coincidence (IPC control-plane hang with rendering unaffected), or effect (something flooding IPC). Against the cause reading: the journal shows no Hyprland errors from 17:50 to 18:02, only one xdg-desktop-portal-gtk ScreenSaver dbus error at 17:58:13 (pack line 86), and the window kept rendering 22 visible tabs while the owner used the machine, so frame presentation was evidently not stopped. Against it being necessary: incident 1 has no reported Hyprland wedge and the same symptom appeared, though incident 1 did not check IPC, so absence of a report is not absence of a wedge. The IPC wedge is therefore a correlate worth recording, not a mechanism, and it does not supply the total refresh stop V2 needs. Its onset timing also cuts against a simple focus-steal story for the input freeze: the freeze onset at 17:59:13 slightly predates probe_y4c's navigations at 17:59:27 and 17:59:33 (pack line 38), so the freeze cannot be blamed cleanly on those navigations.

## Third mechanisms considered

1. Stale geckodriver or Marionette wedge. Rejected as the hiding mechanism. A geckodriver is a Marionette client proxy; it has no path to set computed CSS visibility on a page, and incident 2 had no geckodriver running at the 18:05 check on a fresh port 4448 (pack line 39; worker-y4-run-log.md line 7). The incident 1 kill correlation is explained by the new-tab-only clearing caveat above. The orphaning bug in the WD class (pack lines 93-94) is real and worth fixing, but it is a session-management bug, not a visibility mechanism.
2. Hyprland or compositor wedge as the direct cause. Rejected as a standalone mechanism. It offers no CSS path to `visibility: hidden` on body with html visible, and rendering demonstrably continued during incident 2. It survives only as a possible contributor to V2's refresh stall, and V2's stall is itself unevidenced.
3. Another extension with a loading screen, notably Obsidian Web Clipper. Not defended and not ruled out cleanly. It runs on http and https and was not cleanly grepped (pack line 83), and no loading-screen pattern is known for it. Prior is low: no other extension in the evidence produces this exact CSS, and Transparent Zen is byte-verified to do so. This stays an open unexamined item, not a rival theory.
4. Firefox new-tab background throttling or an inactive window. Rejected as a standalone mechanism. Throttling affects timers and paint frequency; it does not set computed `visibility: hidden`. At most it interacts with V2 by slowing transitions, and the pack notes even 1 Hz throttling would finish a 250 ms transition in about 1 s (pack lines 69-70). The "new tabs in an inactive window" candidate in the Y4 log (worker-y4-run-log.md line 51) is untested and has no CSS path.
5. The open alert on user tab 4. Rejected as a mechanism for other tabs. A tab-modal alert blocks JS in that tab only, and the tab was never touched (pack line 37). No evidence links it to other tabs, and incident 1 had no such alert reported.
6. A split verdict across incidents. Not a mechanism, but a live possibility the evidence cannot exclude: incident 1 could be V2 (if R's "no class" is accurate) and incident 2 could be V1 (no class datum exists there), or both could be V1 with R's summary mistaken. The paper's V1 lean is for the symptom class; it does not claim both incidents share one mechanism.

## What would change my mind

One observation, done on a hidden tab before any recovery step, kill, or navigation, and saved to disk verbatim: a single eval returning `getComputedStyle(document.body).visibility`, `getComputedStyle(document.body).opacity`, `document.documentElement.classList.contains("tz-hidden")`, `document.documentElement.className`, `document.body.className`, and the list of stylesheets whose rules match body with `visibility: hidden`, together with a re-check of that same tab 10 s later and after a `window.focus()`. If `tz-hidden` is present on the hidden tab, V1 is proven for that incident and V2 is dead there. If `tz-hidden` is absent while the body is still computed hidden, with the raw output saved, V1 is dead for that incident and V2 (or a third mechanism with the same signature) wins it. Nothing else in the current record can settle the question, because every other datum is either a summary without its raw output, a new-tab observation standing in for an old-tab state change, or a correlate without a CSS path.
