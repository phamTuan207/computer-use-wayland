# Redteam verdict: Worker Y11 live-metrics instrumentation design

- Role: redteam for Worker Y11. Job: attack the proposed design and find every way the metrics could lie, be gamed, or be vacuous.
- Verdict: **BLOCK**. The design as written would let a runner report a perfect hit rate and a zero think time while the agent's grounding is still broken and its thinking is still unmeasured. It must not be implemented as written. Eight blocking holes below, each with a concrete trigger scenario and the cheapest fix that closes it.
- Rule compliance: no em dash or en dash used in this file. No personal info. No live browser work was done; all findings are from reading the repo files listed below.

## Design under attack (as briefed)

- New module scripts/live_metrics.py: LiveMetrics wrapping TimingLogger plus click_attempt rows into ONE JSONL file, envelope {run, wall Asia/Ho_Chi_Minh, elapsed_s, event}. Events: step, action, click_attempt, summary.
- Runner.step wraps fn in think_step; scripted runs call act() immediately so think_s is about 0 with think_source="scripted". hand_drive.py records inter-command arrival gaps as think time.
- WD.click: resolve rect center, click, elementFromPoint at that point; hit if the element at point is the intended element or its descendant; miss otherwise (occlusion / wrong_target). click_js excluded from the hit-rate denominator; type_text records an action only.
- Integration: WD.metrics attribute (default None), Runner metrics=None, env LIVE_METRICS, run_id unique per run.

## Blocking holes

### B1. Self-congratulatory hits: the elementFromPoint check is theater on the DOM path

- What the design measures: WD.click resolves the intended element by css selector, Marionette clicks that resolved element, then elementFromPoint is asked what is at the rect center. The agent never supplies coordinates. The test author supplies the selector, and the selector is the answer.
- Trigger scenario: take the E2 calibration case verbatim. Vision aims at T03 with the measured 10 percent x-scale error and would land on T04. A scripted run never uses the vision point. It calls d.click("#submit") or the equivalent selector, Marionette clicks the correct element by construction, elementFromPoint returns the correct element, the row is a hit. Repeat for every step. Result: 100 percent hits.
- False claim produced: "hit rate 100 percent, up from 58.6 percent in E2 calibration; grounding fixed." The 58.6 percent measured vision-estimated points against DOM truth. The 100 percent measured the fixture author's selectors against themselves. The two numbers share a name and nothing else. Worse, an agent that is completely broken, one that would click the wrong target on every step if it had to aim, still scores 100 percent as long as the script's selectors are right.
- Why elementFromPoint adds nothing here: the only failure it can detect on this path is occlusion or a covered center, and Marionette's own interactability check already refuses or fails those clicks ("could not be scrolled into view", element not interactable). The check re-proves what the click call already proved.
- Cheapest fix: split the metric in two and never let one borrow the other's name. DOM-selector clicks report as selector_delivery_rate, never as hit_rate. hit_rate counts only clicks where the point came from agent vision coordinates and was executed through a real pointer (desktop backend). Add a control the design currently lacks: report the selector-only rate next to the agent rate, so a 100 percent selector rate with a 58 percent agent rate reads as what it is, a harness that can deliver and an agent that cannot yet aim.

### B2. Vacuous think time: scripted runs report think_s about 0 on every step

- What the design does: Runner.step wraps fn in think_step, and scripted runs call act() immediately, so think_s is about 0 with think_source="scripted".
- Trigger scenario: run t01-t10 scripted, 20 steps each, 200 steps. Every step row carries think_s 0.000 to 0.005 and think_source="scripted". The summary computes think_median_s 0.0, think_max_s 0.005. Nobody reads the think_source field.
- False claim produced: "think time solved: median think 0.0s, down from minutes of thinking on 20/11" or "think fast goal met." The file contains no model call at all, so there was no thinking to measure. The zero is the absence of a model, not the speed of one. It also poisons before/after comparison: any later real agent run with a genuine median think of 8s looks like a 8s regression against a fake 0.0s baseline.
- Compounding defect, verified in code: _ThinkStep.__enter__ (timing.py line 169) calls note_model_call() unconditionally. A scripted run therefore records one model call per step with zero real model calls, and pace() divides actions by that invented count. If clicks do not call note_action, actions stays near 0 and pace() flags slow_think True on a run with no thinking; if they do, the ratio is still meaningless. Either way the pace block in the summary is fiction on scripted runs.
- Cheapest fix: think_s must be null, not 0, on scripted rows, and scripted rows must be excluded from every think median, max, and slow-step count. The summary must print a banner line, "scripted runs carry no think measurement", plus scripted_share, and headline think numbers may only come from hand_drive or a real agent loop. As a guard, think_step must not call note_model_call() when no model call happened; the caller that actually made the model call records it.

### B3. Denominator gaming: click_js excluded, eval .click() not even named

- What the design does: click_js is excluded from the hit-rate denominator. The design says nothing about d.eval() calls that contain .click().
- Trigger scenario, using counts verified in the repo at 18:53:32 +07: run_live.py already routes its hard cases through click_js (the f01 td#a2 trap, the calendar slot children[6+1*6+1], the source cards, the file move) and through raw eval .click() (four sites in f01 that click the type and Enter buttons). run_agyq.py routes at least eight steps through click_js (photo cards, albums, feeds, articles, sidebar notes, renamed rows). run_fcck.py has the same pattern. A runner that wants a perfect rate moves every click that could miss, every small target, every trap, every element Marionette refuses, into click_js or eval .click(). The denominator keeps only the large, stable, easy buttons. Result: 100 percent hit rate, with the hard half of the task invisible.
- Second gaming path in the same hole: retry masking. WD.click raises (element not interactable, covered, stale), the runner catches it and retries with click_js, which succeeds. If the attempt row is written only on the success path, the failed DOM attempt never exists in the file. The miss that the metric exists to catch is erased by the recovery that the metric does not see.
- False claim produced: "hit rate 100 percent on 20 realistic tests" when the honest sentence is "hit rate 100 percent on the easy DOM clicks; all hard clicks were routed around the metric."
- Cheapest fix: log every click attempt including failures and retries, with a click_method field (dom, click_js, eval_click) on every row. Report three numbers together, always: dom_hit_rate, js_share plus eval_click_share, and all_click_hit_rate. Flag the run UNRELIABLE if js plus eval share exceeds 10 percent, or if any step retried through JS after a DOM failure. The cheapest version of this that still works is disclosure plus the flag; the stronger version, counting JS clicks as attempts judged by post-click state change, can follow, but the run must not be quotable as a hit rate without the shares printed beside it.

### B4. elementFromPoint flakiness: the check is wrong before the click and wrong after it

- What the design does not pin down: whether elementFromPoint runs before or after the click. Both timings are wrong in different ways, and the design lets the implementer pick either silently.
- Trigger scenario A, check after the click (false misses on good clicks): the step clicks a link, a submit button, a delete button, or a modal close. The page navigates, the element is removed, or a toast/modal covers the point. elementFromPoint now runs on a new document or against an overlay and returns an unrelated element or null. Every successful navigation click, every successful delete, every successful submit counts as a miss. A run that completes every task can report a hit rate near zero.
- Trigger scenario B, the descendant rule (false hits on wrong clicks): the intended target is a large card div and its rect center is covered by a nested delete button. elementFromPoint returns the delete button, a descendant of the intended element, and the design calls it a HIT. A real pointer click at that point deletes the item instead of opening the card. The same applies to any nested link, icon button, or child control sitting at the parent's center. Geometry containment is not event outcome: a click on a descendant bubbles differently and can trigger a different handler.
- Trigger scenario C, false misses from page mechanics: (1) scroll_into_view moves the element under a fixed header, so the center is covered by the header at check time. (2) An animation or transition moves the element between the rect read and the check. (3) The target is inside an iframe: elementFromPoint on the top document returns the iframe element, never the inner target, so every iframe click is a miss. (4) The target is inside shadow DOM: elementFromPoint returns the shadow host, never the inner target, so every shadow click is a miss. (5) The intended element has pointer-events none: elementFromPoint returns the element underneath, even when Marionette clicked the intended handle successfully. (6) CSS transform, rotation, border-radius, or clip-path puts the rect center outside the visible shape, so elementFromPoint returns the background while the element click itself succeeded.
- False claim produced, both directions: a good run quoted as a bad hit rate (scenario A and C), or a destructive wrong-target click quoted as a hit (scenario B).
- Cheapest fix: check BEFORE the click, in the same instant as the rect read, and record the post-click outcome separately as state_change_observed (did the expected DOM state change), never as a hit or miss. Treat a post-click overlay, navigation, or element removal as inconclusive, not a miss. Recurse into iframes and shadow roots instead of comparing against the top-level element. Tighten the descendant rule: a descendant counts only if it has no click handler of its own; the safe default is exact-element match only.

### B5. Timing attribution: the settle and wait seconds have no bucket

- What the design does not pin down: where act() is called relative to the waits inside fn, and where the waits land (think vs act).
- Measured sleeps inside a single Runner.step call, all verified in run_live.py: switch 0.5s, goto 1.0s, refresh 1.0s, new_tab switch plus goto plus diagnose about 1.8s, wait_for polling up to 10s at 0.1s intervals, diagnose_body second sample 0.3s plus a 0.5s reload sample, the t05/t06 detail-tab settle of wait_ready plus 1.0s, wait_download polling up to 15s. All of these run inside fn, inside the think_step context.
- Trigger scenario: if act() is called at fn entry, a "click save" step reports act_s about 1.9s of which 1.8s is sleeping for paint and tab settle and 0.1s is the click. If act() is called after fn returns, or never on the exception path, the same seconds report as think_s, and a step that waited 9s for a slow page reports a 9s think time for an agent that thought for 0.2s. The same run can produce either headline depending on one unpinned call site.
- False claim produced: "act time is slow, execution needs optimizing" when act is 90 percent sleeping; or "think time is 9s per step" when think is 0.2s and the page was slow. Either misdiagnosis sends the next worker to optimize the wrong stage.
- Cheapest fix: three buckets per step, think_s, wait_s, settle_s, exec_s, with act() pinned to the first real action call and every wait_for, wait_ready, sleep, and diagnose call wrapped in explicit wait markers. The summary reports wait plus settle share separately and the headline act number excludes them.

### B6. File integrity: two writers, one file, no lock, no run identity, silent off

- What the design does: TimingLogger._write and jsonlutil.append_jsonl both write to ONE file, plus the existing log_step writer in run_live.py if the same path is reused. WD.metrics defaults to None, Runner metrics defaults to None, metrics are enabled by env LIVE_METRICS, run_id is "unique per run" with no generator specified.
- Trigger scenario A, interleaving: LiveMetrics calls TimingLogger._write (text mode "a", one stream.write of json plus newline, no lock, no fsync, no repair, no verify) and hit_rate.append_attempt (binary mode "ab", last-byte check then write). Two handles, one file, no lock. A step row and a click_attempt row landing at the same moment interleave or glue into one invalid line.
- Trigger scenario B, torn write poisoning: a crash mid-write leaves a partial line with no trailing newline. The next append_jsonl call "repairs" it by writing a newline after the partial line, which preserves the corrupt partial line as its own bad line. verify_jsonl then flags it, and hit_rate.summarize raises, so the whole file becomes unreadable and the summary for the entire run is lost because of one torn row. TimingLogger._write never verifies at all, so its torn rows are discovered only when a reader fails.
- Trigger scenario C, run_id collision: two concurrent runners share a LIVE_METRICS path and a run_id derived from the test id plus a one-second timestamp. Rows interleave, elapsed_s mixes two different t0 clocks, medians mix two runs, and hit_rate.summarize raises on duplicate (case_id, attempt) because both runs restart attempt counting at 1 for the same case. The WD pid/log comment in run_live.py already warns that two concurrent sessions on one port collide; the metrics design repeats the same mistake for the file.
- Trigger scenario D, silent off: env LIVE_METRICS unset, or WD.metrics left at its None default because one integration site was missed. The run passes, the file is empty or absent, nobody notices, and the team repeats the exact H2/G22 failure the design exists to fix, an instrument that exists but never runs. The design has no loud failure for this case.
- Trigger scenario E, metrics failure becomes test failure: _finish_step is called from _ThinkStep.__exit__. If _write raises (disk full, permission, deleted path), the exception propagates out of __exit__ and either masks the step's real exception or fails a step that otherwise passed. The design says nothing about fail-open versus fail-closed for metrics writes.
- False claim produced: a summary computed over a mixed, glued, or half-missing file, quoted as a run's numbers; or a run with no metrics file quoted as if it had been measured.
- Cheapest fix: one writer only. LiveMetrics owns the file; TimingLogger and hit_rate write through it and never open the path themselves. Append under a file lock, verify the tail after a crash and quarantine (not repair-in-place) a torn line, fsync on summary. run_id must be test id plus timestamp plus 8 hex chars of uuid4, and the path must contain the run_id with exclusive create so a collision fails loudly instead of mixing. Metrics failure must be fail-open for the test (count dropped rows, mark the run UNMEASURED in the summary) and never raise into Runner.step. And the off case must be loud: if LIVE_METRICS is set, a missing metrics object raises at Runner init; if it is unset, the summary prints METRICS_OFF.

### B7. Hand-drive think gaps: the gap is not think time

- What the design does: hand_drive.py records inter-command arrival gaps as think time.
- What hand_drive.py actually does today: it prints execution ms per command only, with no arrival timestamps at all. The gap the design wants does not exist yet in the harness, so the design is also underspecified about where the timestamps come from.
- Trigger scenario A, slow thinker hides: the agent thinks for 20s while the previous command is still executing, pre-decides the next five commands, then fires them at 200ms gaps. The file records five think times of 0.2s. The 20s of thinking is invisible because it happened during execution, not between result and next command.
- Trigger scenario B, fast thinker looks slow: the agent decides in 0.5s, then types a long JSON command by hand (a type_text with a long statement, a selector with a long path), waits on model queueing, or is briefly scheduled away. The gap records 6s of "think" for 0.5s of thinking plus 5.5s of typing and queueing. Gap size now correlates with command byte length, not decision difficulty.
- Trigger scenario C, no baseline: the first command has no previous result, so the largest think of all, reading the task and the first observation, has no start timestamp and is either dropped or measured from harness startup, which includes geckodriver launch and session creation.
- False claim produced: "hand-driven median think 0.4s" from scenario A, or "hand-driven median think 6s" from scenario B, neither of which is a think measurement.
- Cheapest fix: rename the field to inter_command_gap_s and never call it think_s. Record per-command arrival timestamp, result delivery timestamp, and command byte length, and report the gap distribution split by first gap versus later gaps and by command length. The real fix, if think time is wanted from hand driving, is explicit markers: the agent sends a thinking_start event when it starts deciding and the command when it finishes, and think is measured between those markers, not between harness lines.

### B8. The ID mapping is undefined, so the design cannot be implemented as written

- What the design does not say: how a DOM element becomes the short lowercase identifier that hit_rate.append_attempt demands. _SAFE_ID is ^[a-z0-9][a-z0-9_-]{0,63}$. A css selector such as #submit fails it (the # alone raises ValueError). A tag name such as button passes it but collides across every button on the page. An element id attribute exists on fixtures but is often absent on real pages, leaving actual_target None and every miss to be forced into issue_group unknown or to raise.
- Trigger scenario: the implementer passes the css selector into append_attempt, every WD.click raises ValueError, and either the run crashes on the first click or the implementer catches the error and silently skips logging, producing a file with zero click_attempt rows and a summary that divides by zero or reports hit_rate None as if it were a result. The alternative implementer passes tag names, and a click that lands on the wrong button still records actual_target button, intended_target button, hit True.
- Schema mismatch in the same hole: the envelope is {run, wall, elapsed_s, event}, but hit_rate rows carry {schema, event, case_id, attempt, backend, intended_target, actual_target, hit, issue_group} with no run, no wall, no elapsed_s, and timing rows carry {run, wall, elapsed_s, event, step, think_s, act_s} with no case_id, no attempt, no think_source, no click_method, no backend. Merging them into ONE file without a schema version forces every reader to guess which fields exist on which rows.
- Cheapest fix: define the mapping now, before implementation. intended_target is a step-scoped slug (test id plus step name, lowercased, non-alphanumerics to hyphens), never a css selector or tag name. actual_target is the slug of the element at point resolved through the same registry the steps were built from, or null. Put schema: 1, run, think_source, backend, click_method on every row, and put the row type in event.

## Non-blocking observations (fix with the blocking holes, do not ship alone)

- N1. summary() median is an upper median: sorted[mid] for an even count picks the upper middle value, not the average of the two middle values. On small runs this biases the headline by one step. Cheapest fix: use statistics.median.
- N2. pace() reuses the key slow_think for two different meanings: per-step slow_think is a bool for think over 60s, while pace()["slow_think"] is a bool for actions per call below 1.0. The summary merges pace() into totals, so one key means two things in one file. Cheapest fix: rename the pace flag to low_pace.
- N3. Three clocks disagree: Runner.step uses time.perf_counter, TimingLogger uses time.monotonic, wall uses Asia/Ho_Chi_Minh wall text. elapsed_s from two monotonic clocks on one machine is comparable in duration but the file never states which clock each row used, and wall text has one-second resolution. Cheapest fix: one clock source for all elapsed_s, and wall with milliseconds.
- N4. No durability promise: neither writer fsyncs, so an OS crash loses the tail. For a metrics file this is acceptable if the summary records rows_written and the reader treats a missing summary row as an incomplete run, which the design should state.

## What would unblock this design

All eight blocking holes need their cheapest fix landed in the design doc before implementation, not discovered during it:

1. B1: selector_delivery_rate separated from hit_rate; hit_rate only for vision-point real-pointer clicks; control rate reported.
2. B2: think_s null on scripted rows, excluded from medians, summary banner, no invented model calls.
3. B3: every click attempt logged with click_method, js and eval shares reported, UNRELIABLE flag over 10 percent or on any DOM-to-JS retry.
4. B4: pre-click elementFromPoint, post-click state outcome separate, inconclusive for navigation and overlay, iframe and shadow recursion, exact-match default.
5. B5: think, wait, settle, exec buckets with a pinned act() call site.
6. B6: single writer with lock, quarantine of torn lines, uuid4 run_id with exclusive-create path, fail-open metrics writes, loud METRICS_OFF.
7. B7: inter_command_gap_s renamed and split by first gap and command length, or explicit think markers.
8. B8: step-scoped slug mapping and a schema version on every row.

## Residual risks if the design ships as written (ranked)

1. A 100 percent hit rate and 0.0s think time get quoted to the user as proof the two headline goals are fixed, when both numbers measure the harness, not the agent. This is the highest risk because it closes H2/I8 on paper while leaving them open in reality, exactly the pattern Y3 caught in t05, where a vacuous assertion passing was counted as evidence.
2. A real improvement becomes unmeasurable: once scripted zeros enter the baseline, every later real agent run looks like a regression, and the team either chases a fake regression or stops trusting the file.
3. A torn or mixed file silently produces a wrong summary that nobody can reproduce, because the file has no schema version, no run identity guarantee, and no incomplete-run marker.
