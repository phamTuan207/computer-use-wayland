# Council Member 3 verdict: Worker Y8 E1 execution-comparison design

Status: PAPER DEBATE ONLY. No Zen driving, no tab opened, no infra started, no ydotool. This paper judges the draft at `improvements/worker-y8-e1-comparison-design.md` against its 5 open questions, using the deliberation report (`improvements/worker-x-e1-experiment-report.md`, deliberation 8m 40s parallel max, merge about 2 min, merged plan 58 steps, md5 a7b5646b2bf081386bb7bcea0563ad5a) and the hidden-body root cause (`improvements/worker-y4b-hidden-body-root-cause.md`, Transparent Zen 0.9.4 prime suspect, V1 badly wounded but not dead, V2 dead, stale geckodriver dead as a common cause).

Overall: the design is careful, honest about n=1, and right to freeze win criteria before either arm runs. It is not yet runnable as written. Two questions are BLOCK, three are AMEND. No executor runs until the two BLOCK replacements are written into the design and into the executor briefs.

Verdict summary:
- Q1 win criteria: AMEND
- Q2 INFRA retry-once rule: BLOCK
- Q3 n=1: AMEND
- Q4 pre-flight recovery ladder: BLOCK
- Q5 other false-win sources: AMEND (list below, with required fixes before launch)

## Q1. Are the win criteria fair, or do they bias toward A (total-time bar) or toward B (accuracy bar)?

Verdict: AMEND.

What is sound and must stay: the total-speed bar is the right primary bar for the question as asked. Quoted: "SPEED (total): B wins ONLY if B total (deliberation + merge + B execution) < A total (A execution). Otherwise B loses on total speed, whatever B execution alone shows." That is correct. Deliberation is part of the cost of condition B, it cannot be wished away. The execution-only bar as a separate, explicitly partial result is also correct. Quoted: "If B execution < A execution but B total > A total, the verdict is: execution faster, total slower. That is a partial result, not a win." The two bars do not double-count each other numerically, because they are two different quantities reported separately. They would only contradict each other if a later summary headlined the execution-only number as a win, so the headline rule needs freezing in the design, not just in this paper.

What is unsound, in four parts.

1. The total bar is near-unwinnable at this task size, and the design never says so. Deliberation plus merge is 8m 40s + about 2 min = about 10m 40s (640 s) sunk before B execution starts. B execution must therefore beat A execution by more than 640 s to win on total speed. If A execution takes, say, 6 minutes, a total win for B is mathematically impossible even if B execution takes zero seconds. That is not bias in the logic, it is a sensitivity failure: the experiment as sized can almost only return "B loses on total", which is already known from the deliberation report before either arm runs. The design must state this pre-registered expectation in plain text, and must freeze the exact sunk cost instead of "about 2 min". The merge wall is not a stopwatch reading, it is bounded by file mtimes: drafts fetched 18:03:48, plan written 18:05:50, which is 122 s, while deliberation end 18:03:25 to plan written 18:05:50 is 145 s. Freeze one number with its definition, for example "merge = 122 s, draft-fetch to plan-write, excluding draft transfer", and use that exact number in the total. Do not let the total move after the arms run.

2. The accuracy bar is asymmetric and it counts the wrong things. Quoted: "ACCURACY: B wins ONLY if (B passes and A fails) OR (both pass AND B has strictly fewer errors + recovery steps than A)." First, there is no symmetric rule for A. If both pass and A has strictly fewer errors + recovery steps, the design never says A wins on accuracy, it only says B does not win. Add the mirror clause, and add the draw clause: equal errors + recovery steps when both pass is an accuracy draw, not a B loss and not an A win. Second, "errors + recovery steps" is an unweighted sum of unlike things. A driver {"ok": false}, a misclick, a failed click that fell back to click_js, a check retry, and a re-find are not equal in severity, and the design never defines whether a retry that succeeds counts the same as a failure that is recorded and continued past. Freeze the counting rule: count each category separately, report the vector, and define the win on the vector only after the categories are named. Third, and most important, the bar biases toward B by construction. B's plan already contains verified selectors, explicit re-finds, click_js for the star, and event dispatches after clear and select changes. A must discover all of that live, so A's discovery errors are counted as execution errors while B's equivalent work was done in deliberation and is not counted at all. Delib-2's first plan write failed and was rewritten, and that 1 error is recorded in the deliberation report but nowhere in the accuracy bar. The fix is to count B's deliberation + merge errors and PLAN DEFECTs in B's accuracy total, or to state explicitly that the accuracy bar compares execution-phase driver errors only and therefore favours B by design. Either is honest, the current silence is not. Fourth, PLAN DEFECTs are missing from the win formula entirely. A B run can pass with, say, 5 plan defects (steps impossible as written, executor improvised around them) and few driver errors, and still "win" on accuracy under the current formula, even though the plan that deliberation produced was defective. Add: each PLAN DEFECT counts against B in the accuracy comparison, at least one-for-one with an error, and a B pass with any PLAN DEFECT cannot win on accuracy over an A pass with zero defects. The deviation accounting section already requires defects to be logged with plan step number, so the data exists, it is only missing from the formula.

3. "If both fail, accuracy is a draw at failure" is wrong as a scoring rule. Quoted in full: "If both fail, accuracy is a draw at failure, and the failure modes are compared." A fails 1 check at step 48 and B fails 12 checks from step 21 onward are not a draw in any sense that matters, and "failure modes are compared" with no rule is hand-waving that invites a post-hoc verdict. Replace with: if both fail, accuracy is undecided by PASS/FAIL alone, and the comparison is by count of failed checks and by earliest failing step, both stated, with no accuracy win awarded to either arm. A win on accuracy requires a pass, except for the (B passes and A fails) case already in the design.

4. Error counting relies partly on executor self-report. Quoted metrics: "Driver commands run (counted from the executor report + /tmp/e1/out.log lines)" and "Errors: count of {"ok": false} driver results, with step numbers." The executor report is the executor's own claim. PASS/FAIL is correctly decided only from DOM reads plus window.__agyVerify(), never from an executor claim, but errors, misclicks, recovery steps, and deviations are not given the same protection. The coordinator must count errors, driver commands, and tool calls independently from /tmp/e1/out.log and from the codex --json event stream, and must reconcile any difference against the executor report in writing before a verdict. If the two counts disagree, the independent count governs and the disagreement is reported.

Exact replacement for the accuracy clause: "ACCURACY: B wins ONLY if (B passes and A fails) OR (both pass AND B has strictly fewer (errors + recovery steps + PLAN DEFECTs) than A, counted by the coordinator from out.log and the --json stream, with deliberation errors included in B's total). A wins ONLY on the mirror condition. Equal totals when both pass is a draw. If both fail, no accuracy win is awarded to either arm; report failed-check count and earliest failing step for each. A flagged pass (see Q4) cannot win on accuracy over an unflagged pass." Headline rule to add: "The headline speed verdict is always the total-speed verdict. The execution-only number is reported second and is never headlined as a win."

Note on cost: the win criteria ignore token and money cost entirely. Deliberation cost about 463,124 tokens in and 67,995 out across three deliberators. That is not a fairness flaw in the wall-time question, but any later claim that deliberation "wins" without stating that cost would be misleading. Record total tool calls and total tokens per condition (deliberation + merge + B execution versus A execution) in the metrics table, even though they do not enter the win formula.

## Q2. Is the INFRA retry-once rule right, or should a hidden-body hit invalidate the whole comparison (both arms must run in the same browser-health window)?

Verdict: BLOCK.

The rule as written creates a selection-bias loophole and it stacks. Three separate retry grants are written as if they were one:

- Quoted INFRA: "Retry the whole arm once after 5 min. If it recurs, report both arms as blocked with the infra evidence and stop; do not run one arm and compare it against nothing."
- Quoted DRIVER DEAD: "That arm is INVALID, not a fail. Retry once from scratch after infra restart; if it recurs, report as blocked."
- Quoted crash: "An arm that starts but whose executor crashes mid-run (codex process dies, SSH dies) is INVALID and is re-run once from scratch. The crashed partial run is logged, never silently discarded, never counted as the arm's result."

Read together, one arm can be retried up to three times for three different labelled causes (infra-blocked once, driver-dead once, crashed once), each time discarding a bad draw and keeping only the clean run. That is re-running a bad arm until it passes. The "logged, never silently discarded" sentence does not cure it, because the logged partial is explicitly "never counted as the arm's result", so the published result is still the luckiest draw. The bias is worst for the post-start cases: a crash or driver death after the executor has attempted spec steps is not independent of arm difficulty. An executor that is failing steps, hitting hidden-body on its own tab, or stuck in a retry loop is more likely to hit a timeout or to be killed, so discarding its partial run and re-running selects for the run where nothing went wrong. A re-run that passes after a discarded failing partial is a false pass, not a clean measurement.

The 5-minute wait is also arbitrary and shorter than the observed incident. The hidden state lasted about 7 to 8 minutes in incident 1 (16:36-16:44) and about 7 minutes in incident 2 (17:52 to about 17:59). A retry after 5 minutes can land inside the same bad window, waste the one retry, or pass only because the window lifted mid-run. The design gives no reason for 5 minutes, and no rule for what "after 5 min" is measured from.

"If it recurs, report both arms as blocked" is wrong in the case that matters most. If A has already completed cleanly and B is then blocked twice, A is not blocked, A is a completed observation. Reporting both as blocked discards a valid A result and hides the actual state (A done, B blocked, comparison inconclusive). The "do not run one arm and compare it against nothing" principle is right, but it does not require erasing the completed arm.

The "same browser-health window" ideal in the question cannot be fully achieved with sequential arms and an intermittent fault: A and B always run minutes apart, in different windows, and pre-flight results per arm are the only record of that difference. Invalidating the whole comparison on any single hidden-body hit would make the experiment nearly un-runnable if the fault recurs, and would discard good data. The sound rule is not "any hit kills everything", it is "a hit before the arm starts is a different event from a hit after the arm starts, and only the first may be retried, once, under a single shared budget".

Exact replacement, to be written into the design before any executor runs:

- One retry budget per arm, total, across all causes. An arm gets at most two starts. The second start, if any, is labelled A2 or B2 in every table and every verdict sentence. It never silently replaces A1 or B1.
- Pre-start INFRA-BLOCKED only (pre-flight diagnose fails before the executor issues its first driver command, zero executor steps attempted): the arm does not start, the block is recorded with the full diagnose JSON, and one retry is allowed after at least 10 minutes, not 5, timed from the failed diagnose, and only after a fresh clean pre-flight. If the second pre-flight also fails, the arm is INFRA-BLOCKED, the comparison is ABORTED, and the report states each arm's status as it stands (completed arms stay completed, blocked arms stay blocked). No executor runs after that point.
- Post-start INVALID (crash, DRIVER DEAD, or any stop after the executor's first driver command): the first started run IS the arm's result for accuracy. If the executor never reaches final verification, the arm is recorded as FAIL (incomplete), with the partial step reached, the failed checks so far, and the crash or timeout evidence. A re-run, if the coordinator judges it worth doing, is a second observation (A2/B2) reported alongside A1/B1, never a replacement. No accuracy or speed win may be claimed from a second observation alone; a win requires the first observations to support it, or requires both observations to agree.
- DRIVER DEAD must be defined against the driver, not the arm: "step.sh times out twice in a row" is in the briefs, but step.sh has a 30 s wait loop and the driver has a 20 s per-request timeout, so two consecutive timeouts can be one slow Marionette stall, not a dead driver. Before declaring DRIVER DEAD, the coordinator must check the driver process is alive, the geckodriver process is alive, and port 4451 answers, and must log those three checks. If the driver is alive, the event is a timeout, not a death, and the arm continues or fails on its own evidence.
- A retry executor is a fresh codex process that must not see the previous attempt. The design must forbid the retry executor from reading the previous run report, the previous out.log, or any coordinator note about what failed, and must use a fresh report filename (run-a2-report.md, run-b2-report.md). The current briefs forbid reading other agent work and plans, but they do not forbid reading the same arm's previous attempt, which is the exact leak that would let a retry executor route around the failure that killed the first run.
- "The two arms must use the SAME tab-acquisition method" is correct and must stay, but it needs the same single-budget logic: if the fresh-tab method fails for A and a fallback is used, the fallback is used for B, and the change is recorded, and the fallback itself counts as the one method change for the whole comparison, not one per arm.

## Q3. Is n=1 acceptable as a first observation with honest scoping, or should each arm run twice (A1/A2/B1/B2) before any verdict?

Verdict: AMEND.

n=1 is acceptable as a pilot, and only as a pilot. The design's scoping sentence is correct and must stay. Quoted: "n=1 per arm: one run each, one task, one model. This is ONE observation, not proof of a general effect. Any verdict is scoped to 'this task, this run'. No claim about deliberation in general follows from n=1." That sentence is the strongest part of the design. Requiring A1/A2/B1/B2 before any verdict would be the wrong fix: it doubles live-run time, doubles exposure to the hidden-body fault and to the owner-at-keyboard risk, doubles token cost, and still leaves n=2, which is still not proof of a general effect. It also doubles the chance that one of the four runs hits an infra fault and triggers the Q2 retry machinery, which as written would compound the bias.

What n=1 cannot do, and the design must say so, is distinguish a deliberation effect from executor luck. Codex runs are not deterministic, the design admits this, and the plan itself is a single draw: the three drafts were 68, 62, and 58 steps, so plan length alone varies by about 15 percent across deliberators, and the merge made contested choices (dropping the draft-2 re-find step and the draft-1 extra clear-search step) that a different merge could have made differently. A single B pass or fail therefore confounds deliberation quality, merge quality, plan luck, executor luck, and order. n=1 can answer "did this plan, executed once, beat this direct run once, on this task", and nothing broader.

The amendment is to pre-register the replication trigger now, before either arm runs, so that a second pair is not decided post-hoc after seeing a split result (which would be optional stopping). Add to the design:

- Stage 1 is the n=1 pilot (A1, B1). Its verdict language is frozen to pilot language: "on this task, this run, B was faster/slower, more/less accurate", with no sentence of the form "deliberation helps" or "deliberation hurts".
- A second pair (A2, B2) is run before any comparative verdict beyond pilot language if any one of these holds: the arms split PASS/FAIL; execution wall times differ by less than 20 percent; either arm is flagged (Q4) or invalid under the Q2 replacement; or the coordinator's independent error count disagrees with either executor report by more than 2. If none holds, the pilot verdict stands as a pilot verdict and the replication is recorded as not triggered, not as unnecessary.
- If a second pair runs, its order is B then A (ABBA overall: A1, B1, B2, A2), to balance the warm-state order effect instead of repeating A-first. The second pair uses the same briefs, the same plan file (same md5), and the same tab-acquisition method, and its results are reported as a second pair, never merged into a single average with the first pair without showing both pairs separately.
- The design must also state the cost of the second pair in advance (two more executor runs, live-run time, tokens) and that the second pair runs only in a fresh handover window, not by extending a window that has already closed.

## Q4. Does the pre-flight recovery ladder (removing tz-hidden on the test tab) contaminate the comparison, since a FLAGGED pass is still a pass?

Verdict: BLOCK.

The ladder as written is a transplant error. It is copied from the Y4b fix design, where the tab being diagnosed and fixed IS the tab under test: diagnose in WD.goto, remove the class on that tab, continue the test on that same tab, and flag the pass. In Y8's design the tab being diagnosed and fixed is a throwaway pre-flight tab that is then closed, and each executor opens its own fresh tab afterwards. Quoted: "The pre-flight tab is closed after diagnose; each executor opens its own fresh tab afterwards." Removing tz-hidden from the pre-flight tab therefore fixes nothing the executor will touch. Each new tab gets a fresh document_start injection, a fresh async chain (fetch of data/ContentScripts.json, then browser.storage.local.get, then branch paths), and a fresh chance to stall. A pre-flight pass achieved only after removal tells the coordinator that the extension could be un-stuck on one tab, not that the executor's tab will be visible. Worse, it authorises launch into a browser that has just demonstrated the fault, and the executor's own tab has no diagnose step at all in either brief: executor A confirms #contacts-count expects "6" and executor B follows plan step 2 (new_tab) then step 4 (check initial render), but neither brief contains a diagnose_body step, a tz-hidden check, or a recovery ladder. If the executor's tab is hidden, its DOM reads via eval can still succeed, because visibility does not block JavaScript reads, so the run can proceed and even PASS while the page is blank to a human eye. The pre-flight is then not a guard, it is a ritual that can pass while the real tab fails.

Three further defects in the ladder as written:

1. The removal step is transcribed incompletely. Y4b's fix design gives the exact eval. Quoted from worker-y4b-council-fix.md section 3 step 2: `document.documentElement.classList.remove("tz-hidden"); document.documentElement.style.removeProperty("--zen-logo-path"); return "removed";`, followed by a 500 ms wait for the visibility and opacity transition to complete, then a re-diagnose. Y8's design says only "remove tz-hidden exactly as removeLoadingScreen does (single eval, test tab only, test origin only, logged as intervention)", with no JS given, no --zen-logo-path removal, and no wait before re-diagnose. Removing the class alone leaves the --zen-logo-path inline property in place, and re-diagnosing immediately, inside the 250 ms transition, can read opacity still rising and misclassify a recovering tab as still hidden. The 8 s total budget quoted in the design ("Recovery ladder, 8 s total budget") is also borrowed without its steps: Y4b's 8 s budget covers poll, removal, repaint, and bootstrap fallback. Y8's ladder has only poll (2.0 s) and removal, so the 8 s figure is unaccounted for and the remaining budget is undefined.

2. The diagnose payload is missing the second V1 prediction. Y4b's root cause puts weight on this: initLoadingScreen sets --zen-logo-path as inline style on documentElement, and removeLoadingScreen removes it, so under V1 the inline property should still be present while the class is stuck. Y8's payload lists "body inline style" but not documentElement inline style (htmlInline), so the corroborating check that would distinguish a true V1 stall from a misread is absent. The payload also omits the classification inputs Y4b requires for a clean call: readyState not complete means "do not classify as hidden yet, wait for wait_ready first", and Y8 gives no readyState rule. Add htmlInline, add the readyState rule, and save the full diagnose JSON per arm to the repo, not just a classification label.

3. A FLAGGED pass is still a pass in the win criteria, which contradicts the flag. The design says a pass achieved only after removal "is a FLAGGED pass, counted separately in the summary, never folded silently into the headline pass count", but the win criteria in the same file never mention flagged passes. Under the current accuracy formula, a flagged B pass with fewer errors beats an unflagged A pass. That is exactly the contamination the question asks about: the intervention masks a real user-facing defect (a real user opening a new tab in this Zen during such a window sees a blank page for minutes), and then the masked run is allowed to win. The Y4b fix design allows a flagged pass for a runner test because the intervention is on the test tab and the flag is disclosed, but even there it is paired with a tracked item to fix or disable the extension. Y8's design has no such tracked item and no rule for what a flag does to the verdict.

Exact replacement, to be written into the design and the briefs before any executor runs:

- Pre-flight diagnose is read-only. Poll 250 ms up to 2.0 s for the extension's own removal. If V1 persists after the poll, the arm does NOT start. The result is INFRA-BLOCKED under the Q2 replacement, not a flagged pass. Removal on the pre-flight tab is permitted only as a diagnostic probe after the gate has already failed, to distinguish V1 from OTHER_HIDDEN for the incident record, and a probe removal never converts a failed gate into a pass.
- The executor's own tab gets its own diagnose, immediately after the executor's new_tab and before any spec step. This requires a hold protocol the current briefs do not have: amend both briefs so the executor, after new_tab, waits for a coordinator go-ahead before proceeding, and the coordinator runs diagnose_body on the executor's tab (same payload, plus htmlInline, with the full JSON saved). Only a clean VISIBLE diagnose releases the executor. If the executor's tab is TZ_STUCK_V1, the coordinator removes the class with the exact Y4b eval, waits 500 ms, re-diagnoses, and the run proceeds only if visible, as a FLAGGED run. A flagged run cannot win on accuracy over an unflagged run (see Q1 replacement), and the flag, the diagnose JSON, and the removal are in the run report and in the verdict. If the executor's tab is OTHER_HIDDEN, the arm stops, the run is INFRA-BLOCKED under Q2, and the tab is left open for later inspection, not closed by the executor.
- Until that hold protocol exists in the briefs, no executor runs. The current briefs plus the current pre-flight section do not add up to a guarded run.

## Q5. What else could produce a false win for B (or for A) that this design does not catch?

Verdict: AMEND. The design catches the order effect and n=1 in its known-confounds section, which is honest, but it misses the following, each with a required fix. None of these alone is a BLOCK, but together they mean the current metrics table invites misreading.

1. The pre-flight tab changes Zen state, and the design never analyses it. Opening a fresh tab via the E1 driver and then closing it is not a neutral probe. It warms the fixture HTTP server and the extension's content-script chain (the ContentScripts.json fetch and the storage.local.get that gate removal), so the executor's tab loads into a warmer browser than a cold first tab would, which can only reduce hidden-body incidence and therefore masks the true rate. It also changes tab count, focus, and the current handle: close_tab closes the current tab, and the design never specifies how the coordinator verifies the handle it closes is the pre-flight handle and not a user tab, nor which WebDriver session the pre-flight uses, nor whether that session is deleted before the executor's new_session. hand_drive.py keeps a single sid variable and a single opened list per driver process, and its finally block deletes the session only if sid is not None; a pre-flight session that is never deleted is a second live session on Marionette's single session slot, which Y4b records as a leak that blocks all remote control until Zen restarts. Fix: specify the pre-flight session lifecycle in full (own session, own handle recorded, delete_session after close, verify the handle inventory before and after), save the handle list per arm, and state in the report that pre-flight warms the browser so hidden-body incidence in E1 is a lower bound, not a true rate. Also, pre-flight runs "before the executor launches", but a codex executor takes minutes to start and to read its inputs before its first driver command (A reads a 67-line spec plus a 335-line fixture plus hand_drive.py, B reads a 22,145-byte plan plus hand_drive.py), so a pre-flight result is stale by the time the executor opens its tab, and stale by a different amount per arm. The Q4 hold protocol (diagnose on the executor's own tab) is the fix for this too.

2. Coordinator unblinding. The coordinator knows A's result before B runs, because A runs first and B runs second. Nothing in the design blinds the coordinator's later decisions: how strictly pre-flight is judged, whether a retry is granted, how a B deviation is judged against the plan, or how errors are counted. The deviation rule says the comparison of "plan followed verbatim" is decided by the coordinator reading the B run report against the plan file, not by the executor's own claim, which is right, but the coordinator is the same person who merged the plan and who knows whether A passed. Fix: the deviation judgment and the error count must be done from the written artefacts (plan file, out.log, --json stream) with the judgment recorded as a line-by-line table (plan step, what the executor did, verbatim or deviation, defect or improvisation), and the coordinator must record A's result in a sealed note before B launches and must not re-open the A verdict while judging B. A stronger fix, if a second pair runs under Q3, is to have the B deviation judgment done by a fresh reader who has not seen A's result.

3. The merge is a confound, not just a step. Condition B as built is deliberation plus coordinator merge plus executor, not deliberation alone. The merge made contested choices against the fixture HTML (base skeleton draft-3, name reads by lastElementChild, star class string, explicit input dispatch after clear, dropping two steps by majority). If B wins, the win could be the coordinator's merge skill, not the deliberators'. If B loses, the loss could be a merge defect, not a deliberation failure. The design must label the condition honestly in every verdict sentence: "deliberated plan (3 drafts + coordinator merge)", never "deliberation" alone, and must list the merge decisions that could have changed the outcome (the two dropped steps and the explicit dispatches) in the report.

4. Granularity inflates B's counts. The plan has 58 steps and 64 JSON commands for a 28-step spec, because deliberators split finds, types, and checks into separate steps. A direct executor will naturally run fewer driver commands (it can combine a find and a check into one eval, for example). The metrics table records driver commands and tool calls per arm with no normalisation, so a naive reader will conclude B is "less efficient" even if B is faster in wall time, or will conclude A is "more efficient" when A simply did fewer checks. Fix: report driver commands and tool calls alongside wall time and alongside checks performed, and never compare raw counts across arms without stating the granularity difference. The win criteria correctly do not use these counts, but the table must carry the caveat in its caption.

5. Two clocks, and reading time inside wall time. The metrics record executor-recorded start/end AND coordinator-observed launch-to-final-report wall, with both stated, which is good, but the design never says which is primary when they disagree, nor what is inside each. Executor start is the first action (date before reading inputs), so wall time includes reading the spec and fixture (A) or the plan (B), which are different sizes and therefore different reading costs, and includes codex process startup and final report writing, which are not execution. Coordinator wall includes all of that plus codex launch latency. Fix: freeze the primary wall as executor-recorded start (first date call) to end (last date call after cleanup), report the coordinator wall as a sanity check, and report the difference. If the difference exceeds 60 s, the report must explain it before any verdict.

6. out.log counting is contaminated as specified. Quoted: "Driver commands run (counted from the executor report + /tmp/e1/out.log lines)." out.log is a single file that the X start-infra script truncates with `: > /tmp/e1/out.log` on every infra start, so starting infra for B destroys A's log unless the coordinator archives it first, and out.log also contains pre-flight diagnose lines and any coordinator probes sent through step.sh, which are not executor driver commands. step.sh itself counts lines in out.log as its completion signal, so interleaved lines can confuse it. Fix: archive out.log per arm to out-a.log and out-b.log before the next infra start, never truncate without archiving, and count driver commands only between the executor's new_session and delete_session lines, with session boundaries marked. Also verify the brief md5s before launch: the design verifies spec, fixture, hand_drive.py, and plan md5s, but not the executor briefs, step.sh, or the infra scripts, which live in /tmp/e1 on the laptop and are not in the VM repo. A stale brief on the laptop would silently change the condition. Add brief, step.sh, and infra-script md5s to the verified-inputs section, with the VM repo copies as the reference.

7. Tab and session leakage between arms. The fixture keeps state in memory per tab, so a fresh tab is fresh state, but only if A's tab is actually closed and A's session actually deleted before B's pre-flight. The design never requires a handle inventory check between arms. If A crashes and its tab stays open with mutated state, B's new_tab still opens a fresh tab, but the Marionette current handle, the tab count, and the geckodriver session state are all polluted. Fix: between arms, the coordinator must list handles, confirm A's handle is gone, confirm no E1 session is live, and confirm ports 4451/8767 are free before starting B infra, and must log that check. The same check applies after B, before the report is written.

8. PASS/FAIL is blind to hidden-body. The fixture's __agyVerify reads the contacts model plus the DOM banner, and eval reads succeed on a hidden tab, because computed visibility does not block JavaScript. A run whose tab was hidden for the whole execution can therefore PASS every DOM check while a human looking at the screen sees a blank page. That is why the pre-flight and the Q4 executor-tab diagnose are load-bearing, not optional, and why a flagged run must be labelled in the verdict, not just in an appendix. It is also why the design's "Check failures recorded (a check whose read differed after its one retry)" metric can be zero on a hidden tab: the reads do not differ, they are just invisible.

9. Token and money cost is uncounted, and the executor compliance rules are unverifiable. A is forbidden from reading any plan file and B is forbidden from reading the spec or fixture, but both executors run with danger-full-access and filesystem access, and the design specifies no audit of what files they actually read. ## Infra appendix: wrong or unsafe

The appendix correctly diagnoses X's stop-infra.sh: `pkill -f` matches the SSH command string itself and drops the session, and X's scripts are correctly left unedited. The replacement as specified is not yet safe:

- Quoted: "kill by exact PID only, with pkill -x geckodriver only if its cmdline shows port 4451." pkill -x matches by process name only, it cannot filter by cmdline, so the "only if" is a human intention, not something the command enforces. Run as written, `pkill -x geckodriver` kills every geckodriver on the machine, including Y4's and any live driver's. The safe form is per-PID: for each pid in `pgrep -x geckodriver`, read /proc/<pid>/cmdline, kill only the pid whose cmdline contains --port 4451 and whose parent is the E1 driver python process (or is dead, for an orphan), SIGTERM, wait up to 5 s, SIGKILL only if still alive, then verify with a second pgrep that it is gone. The same per-PID rule applies to the holder, driver, and HTTP server.
- The PID recording is unspecified and unreliable as described. X's start-infra.sh echoes "holder pid $!", "driver pid $!", "http pid $!" to stdout, but writes no PID file. Worse, the driver and HTTP server are launched as `setsid nohup python3 ... &`, so $! is the setsid wrapper PID, not necessarily the python PID, and killing the wrapper does not guarantee the python child dies. The Y8 scripts must write a PID file (for example /tmp/e1/pids, one line per role with PID and full cmdline snapshot), must verify each recorded PID's cmdline matches the intended process before killing it, and must be tested with a dry run against a dummy sleep process before they are ever run against a live geckodriver.
- X's stop-infra.sh does not kill the holder (sleep 7200 holding the FIFO) or the geckodriver at all, it only runs `pgrep -x geckodriver` as a check. So "stop" as written leaves both running, and the next start's `mkfifo` and port checks inherit a live geckodriver on 4451. The Y8 stop script must kill holder, driver, HTTP server, and the verified E1 geckodriver, in that order, and must verify ports 4451/8767 free and no E1 geckodriver remains before it prints INFRA_DOWN.
- X's start-infra.sh truncates the evidence: `: > /tmp/e1/out.log` on every start destroys the previous arm's driver log. The Y8 start script must archive out.log to a per-arm file before truncating, or use per-arm log filenames from the start.
- X's start-infra.sh builds the driver by `sed 's/WD_PORT = 4450/WD_PORT = 4451/'` with no assertion afterwards. If hand_drive.py changes upstream, the sed silently fails to match and the driver runs on the wrong port. The Y8 script must grep the built file for WD_PORT = 4451 and exit non-zero if it is absent.
- The appendix omits the whole Y4b preflight that the design otherwise relies on: no stale-geckodriver sweep by PID with parent check, no Marionette single-session lock check, no Zen liveness check at run time (the design's "Zen PID 27958 alive" is a snapshot from 18:24, stale by run time), no fixture-server loopback check, and no handle inventory. Those checks must be in the Y8 start script, failing closed, before any tab opens.
- hand_drive.py launches geckodriver with stdout and stderr to DEVNULL and no PID file, which Y4b's fix design explicitly corrects (log file plus PID file, cleanup on session POST failure). The Y8 appendix does not mention this, so the E1 driver as built still has the orphan bug: a session POST timeout orphans the geckodriver because __exit__ never runs. If Y8 does not fix hand_drive_e1.py, the design must at least record the orphan risk and the manual sweep that covers it.
