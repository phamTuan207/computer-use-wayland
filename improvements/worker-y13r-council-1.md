## F4: PARTIAL

Claim in the log: launch_y13.py performs the runner-quiet check before flock (patterns for run_*.py / hand_drive_e1.py, own ancestry excluded, codex matches warn only) AND preflight re-checks it after the lock (redteam H5). Verified by a launcher dry run refusing on a dummy run_foo.py process.

What I verified, mechanically, line by line in both copies:

- Launcher, launch_y13.py lines 72-73: RUNNER_PATTERNS = (re.compile(r"(^|/)run_[^/\s]*\.py"), re.compile(r"hand_drive_e1\.py")). check_runner_quiet lines 136-157: scans /proc, skips pids in _own_ancestry(), refuses exit 2 on any RUNNER_PATTERNS match, warns only on "codex" substring matches.
- Launcher _own_ancestry lines 81-101: walks /proc/<pid>/stat ppid chain, parses after the last ")", breaks on ppid <= 1 or a repeated pid. Correct, cycle-safe.
- Runner preflight, run_codex_y5.py lines 3475-3501: same regex inline at line 3496, same raw NUL-separated cmdline (read from /proc/<pid>/cmdline, decoded, no NUL replacement before matching), same "hand_drive_e1.py" substring check, same ancestry walk via _ppid_of (lines 187-197, parses after the last ")", correct). One difference: the preflight walk has no cycle guard (while _pid > 1, adds every ppid unconditionally). In practice ppid chains terminate at 1; this is a robustness nit, not a live bug.
- Ancestry exclusion proven live: a parent script /tmp/y13r/run_foo2.py (cmdline "python3 /tmp/y13r/run_foo2.py", absolute path, regex-matching) spawned a child that imported the real launch_y13 and called check_runner_quiet; the child printed CHECK-PASSED at 20:24:58 +07 with the matching ancestor alive. The control (an unrelated checker while the same parent lived) refused exit 2 naming pid 127256. Ancestry exclusion is correct in the launcher.

What the regex catches and what it misses (mechanical table, 20:21:53 +07, re.search on exact /proc-style NUL-separated cmdlines):

- CATCH: argv[0] bare ("run_codex_y5.py" alone); absolute path ("python3 /tmp/.../run_codex_y5.py"); "./run_codex_y5.py"; "../run_codex_y5.py"; other absolute runners (run_agy_y2.py, run_live.py absolute).
- MISS: bare relative launch ("python3 run_codex_y5.py" from the ship dir, cmdline "python3\0run_codex_y5.py\0"); bare relative plus args ("python3 run_codex_y5.py all"); bare relative other runner ("python3 run_agy_y2.py"); flock wrapper argv ("flock -w 60 <lock> python3 run_codex_y5.py all"); shell -c string ("bash -c python3 run_codex_y5.py all"); bare relative run_live.py.
- Correctly no match: unrelated "python3 my_script.py"; "myrun_codex_y5.py" (the (^|/) anchor correctly refuses a mid-component match).
- False-positive note: a __pycache__ .pyc path (".../run_codex_y5.cpython-311.pyc") matches, because the pattern has no end anchor and ".py" occurs inside "cpython-311.pyc". Unlikely in a real cmdline; noted, not weighted.

Root cause of the miss: /proc cmdlines are NUL-separated, and the pattern anchors the run_ token on start-of-string or "/". In a bare-relative launch the token is preceded by NUL (argv separator) or by a space (inside a -c string), neither of which the anchor accepts. The code never normalizes NULs before matching; it only replaces NULs with spaces when building the refusal message, after the match has already been decided.

Live proof of the miss (20:22:47 +07): a dummy process with cmdline "python3 run_codex_y5.py" (pid 126714, launched bare-relative from /tmp/y13r, alive and sleeping) was NOT refused. The real check_runner_quiet printed only "[launch_y13] WARNING: codex process running (pid 126714): python3 run_codex_y5.py" (the incidental "codex" substring warning, because the filename contains "codex") and then CHECK-PASSED. A bare-relative run_agy_y2.py would not even warn. By contrast the absolute-path dummy (pid 126797, "python3 /tmp/y13r/run_codex_y5.py") was refused exit 2 with "live slot busy, runner process running: pid 126797", and the bare-relative hand_drive_e1.py dummy (pid 127091) was refused exit 2, because the hand_drive check is a plain substring and NULs do not matter for it. So the hand_drive half of F4 is fully working in every form; the run_*.py half is broken exactly for the launch form the launcher itself uses (launch_y13.py line 299 execs ["flock", "-w", "60", LOCK_PATH, "python3", "run_codex_y5.py"] with cwd=SHIP_DIR, i.e. bare relative).

How much does the miss matter? Bounded, but real. Three guards limit it for known runners: (a) flock serializes launcher launches (a second launcher blocks 60s on the lock, then fails); (b) preflight requires the lock to be held by an ancestor (run_codex_y5.py lines 3596-3615: "no flock holder ... run must be launched under flock", "held by ..., not by an ancestor"), so a direct bare-relative launch without flock is refused at preflight anyway; (c) the launcher refuses when predecessor ports (Y9 8769/4449, Y8b 8767/4451) or own ports (8771/4452) answer. The miss bites precisely in the case Council A F4 named: a runner that holds no lock and no known port, launched bare-relative (or via a flock wrapper, or a shell -c string). Y11b's proof runner (name unknown) and Y14's runner are the named instances; E1 is covered by the hand_drive substring. Between launcher start and the Y13 server coming up on 8771 there is also a window where the process check is the only guard against a second Y13, and it misses the first Y13's own exec form.

False positives, proven live as well: during the ancestry test, a child checker refused naming pid 127253, a bash process whose -c string merely contained the text "/tmp/y13r/run_foo.py" (my own test command). The regex matches a path mention anywhere in the cmdline, not an actual python process executing the file. In real operation any concurrent shell command mentioning the absolute runner path (md5sum, cat, git show, a review grep) trips a launch refusal. That fails closed (a refused launch, not a collision), so it is the less serious direction, but it makes the check noisy and it is the same one-line root cause as the miss: the check matches raw cmdline text instead of argv tokens.

Fix required (F4): normalize the cmdline before matching in BOTH copies (replace NUL with space, then anchor on start, "/", or space), and re-test live with a bare-relative dummy, a flock-wrapped dummy, and a shell -c dummy, all of which must now refuse. Better, tokenize argv on NUL and require a python interpreter token before the script token; that also kills the path-mention false positive. At minimum the NUL normalization plus a live bare-relative re-test. Also add the missing cycle guard to the preflight ancestry walk for symmetry with the launcher.
