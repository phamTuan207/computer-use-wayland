## D. Marionette browserElement-null slot: risks of the adopted method

- Risk 1: the restart loses unflushed state. PROVEN: F3 log 22:36:24 notes sessionstore was NOT rewritten on exit (recovery.jsonlz4 still 22:04), and the LMS login tab opened about 22:26 was lost (login page only, trivially reopenable). Mitigation: use `pkill -TERM`, never -KILL; wait for a clean exit (F3: clean exit after 1s, no zen/gecko processes left); verify zero processes before relaunch. Never restart twice in a row without a fresh diagnosis; a second restart after a failed first one is how unflushed state compounds.
- Risk 2: the restart runs while another worker holds the slot. The session cap is shared (1 TOTAL). If F1, F2, or a live runner holds a Marionette or BiDi session when the restart kills Zen, their session dies with it and their evidence is lost. Mitigation: the restart ladder runs ONLY in the F3 serial slot (todolist hang 1), with the single live runner holding the lock, and only after confirming no other live runner is active.
- Risk 3: the cleanup closes a real tab. The resurrected set is 39 fixture tabs mixed with 28 real ones (OPT-ZEN P3). A cleanup driven by count (67 minus 39) instead of identity can close a real tab and still hit the count. Mitigation: identity cleanup only (full ordered title + URL list before and after, target 28, every real tab present in the after-list), sacrificial tab FIRST, end the session on a live tab (gate G-TAB), never DELETE /session while current is a discarded tab.
- Risk 4: the rejected omni.ja patch (D-2). This voice VETOES it as a live method: repacking a shipped omni.ja on the owner's daily browser, with no verified signature story and silent overwrite on every Zen update, risks a browser that will not start in the morning. That is the one failure this council must never cause. The patch stays a redteam attack surface only.
- What must never happen in D: a restart while the owner is at the keyboard; a -KILL on zen-bin; a cleanup by count; a POST retry loop (blind retries recreate the 22:06-22:31 outage pattern: 5 failures, same string, no diagnosis between them).

## E. Zen wedge / workspace switching: risks of the adopted method

- Risk 1: another menu miss while the owner sleeps. F3 opened the Omarchy launcher at 22:43:15 and the Omarchy system menu at 22:45:38 (Reboot / Shutdown / Logout / Screensaver / Suspend / Lock). Both were closed with Escape and verified closed by observe, and no menu item was clicked. But a system menu left open overnight, or a wrong item clicked, could reboot or suspend the machine. Mitigation: bar clicks are BANNED outright (owner order 22:45). Workspace and menu by COMMAND only. Any menu opened by accident is closed with Escape immediately and verified closed by observe before the next step. Never issue a command whose effect was not read from config first.
- Risk 2: switching to the wrong workspace strands Zen. ZT-05 switches away and back twice; if the return switch fails, Zen sits on the wrong workspace and the owner wakes to a missing browser. Mitigation: after every switch, `hyprctl activeworkspace` plus `hyprctl clients` must show Zen on the expected workspace, and the DOM active title must be unchanged. If the return fails, switch back by command at once and report; do not continue the scenario.
- Risk 3: the wedge reappears during a live run and the runner restarts blind, destroying the evidence again. The 22:25 wedge was restarted with no signature captured, which is why its mechanism is unknown. Mitigation: the wedge signature capture (hyprctl clients/workspaces/activewindow, Zen PID and flags, BiDi getTree, one Marionette POST with exact error) runs BEFORE any restart, every time. A restart without a signature is a safety violation, not a shortcut.
- Risk 4: focus steal. Switching workspaces or clicking the sidebar while the owner is at the keyboard steals focus (17:59 incident). Mitigation: live workspace steps run only with the owner away (explicit flag) or in the handed-over window; the moment the user returns, stop.
- What must never happen in E: a bar click; a guessed workspace command; a restart without a signature capture; a menu left open; a workspace switch that strands Zen.

## F. Pill measurement 2.2.3: risks of the adopted method

- Risk 1: loading hyprglass LIVE while the F-team works. Gate G-PILL (todolist line 33) forbids it: "never load hyprglass live when F-team is working on the machine". The whole Y6 method runs NESTED (Hyprland nested, separate socket) for exactly this reason. Live Hyprland PID 1515 must show hyprbars ONLY before and after every step (Y6r V7; Y6e log states live plugin list unchanged, verified byte-identical by Y6r Council 2). Mitigation: the load-only trial (A8) records the live plugin list before and after; any hyprglass entry in the live list aborts the run at once.
- Risk 2: wrong-target reload. The launcher shell carries WAYLAND_DISPLAY=/run/user/1000/wayland-1, the LIVE socket, so a BARE `hyprctl reload` reloads LIVE (Y6r Council 3). The live chain includes visuals-login.lua, which would schedule visuals.py and load glass live. Mitigation: the adopted method adds NO reload at all (Y6r R2, A7). If a future step ever needs a reload, it runs only through the nest() wrapper with the nested socket, never bare. This voice treats any bare `hyprctl reload` in a fix diff as a veto item.
- Risk 3: config mix-up. The y6e conf must be staged as the active NEST conf only (A1). Editing the live optics (native/hyprglass-local-optics.lua, blur 0.0) or live visuals-login.lua would change the owner's daily pill. Mitigation: A3 restricts the marker to the nest copy of optics.lua ONLY; the fix diff must show no live-file change; md5 verification on both sides (nest conf 9ccb27017ab63a9d2bce1d9651425d3b).
- Risk 4: duplicate layer() on parse 3 (Y6r open item O1, overwrite vs error unresolved). The adopted method avoids creating a parse 3 (no manual reload), but the risk is not gone: any future reload would trigger it. Mitigation: watch the retry log for a parse-3 error; if one appears, record it and stop, do not work around it live.
- Risk 5: false-negative pill verdict. A retry that measures with the WRONG conf staged (the live A1 blocker: the y6e conf was never installed as active conf, so the retry dies at the ldd pre-flight on the old backup-1 conf) or with a missing profile would report "pill does not bend" about a pill that was never glassed. That is worse than no measurement: it would kill a correct design on false evidence. Mitigation: A8 load-only trial first, A2 positive gate (marker plus layers.enabled true), A9 fresh re-review before any measurement run. No arms run on an unreviewed fix.
- What must never happen in F: hyprglass loaded live; a bare hyprctl reload; any edit to a live optics or visuals file; a pill measurement on an unreviewed fix; a verdict drawn from a run whose profile gate did not pass.

## G. Hidden-body decisive experiment + composite/blind test design: risks

- Risk 1: the experiment itself hides a real user tab. Phase 1 opens up to 30 new tabs; Phase 4 disables the Transparent Zen extension and re-enables it. If a tab is opened on the wrong window, or the extension is not re-enabled, the owner wakes to a changed browser. Mitigation: the experiment runs only under the Zen lock, only with the owner away (explicit flag), never navigates, types into, or clicks a user tab, never touches the tab with the open alert, and Phase 4 ends with re-enable confirmed and the original state verified.
- Risk 2: the class-removal intervention masks a real defect. Removing `tz-hidden` from a test tab makes the test pass while a real user opening a new tab in the same window still sees a blank page for minutes. Mitigation (Y4b): removal happens on test tabs only, test origin only, logged as intervention, and the pass is a FLAGGED pass counted separately, never folded into the headline count. The intervention is disclosed in the test report and tracked as a separate item to fix or disable the extension. Never remove the class on a non-test tab.
- Risk 3: `ensure_visible` focus steal. The landed `ensure_visible` switches to the first non-test handle, which is a user tab by definition in a live Zen (Y4b fix design). Mitigation: the switch-away step is removed entirely; `ensure_visible` internals are replaced, name and call sites kept. Never use a real click as a recovery probe.
- Risk 4: disable-extension as a standing procedure. Disabling Transparent Zen would "fix" the symptom by removing the user's daily extension without the user's decision. Mitigation: disable-extension only as a one-off diagnostic inside Phase 4, with immediate re-enable. Never as a standing procedure. No separate clean profile for live runs (Y4b rejects it).
- Risk 5: blind executor harm. ZT-B runs blind on the live Zen; a misread step could close an owner tab (the redteam BLOCK on ZT-A v1 was exactly a blind Ctrl+W closing an owner tab; v2 fixed it with the pre-close check and identity cleanup). Mitigation: v2 rules bind the executor (ZT-A rules 4, 5, 6, 9): snapshot first, identity cleanup, pre-close check before EVERY Ctrl+W, ZT-00 gate first, stop at the first BLOCKED gate, 90 minutes maximum.
- What must never happen in G: an intervention on a non-test tab; a flagged pass reported as a clean pass; an extension left disabled; a user tab navigated, typed into, or closed; a live run while the owner is at the keyboard.
