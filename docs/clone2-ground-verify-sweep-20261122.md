## Headline findings

### 1. NEW and usable: the three-facts verification model (dev.to, 2026-11-14)

The single most on-topic piece in the window is "The screen is not the state: verifying that a browser action actually happened, and recovering when it did not", by maptosite, DEV Community, published 2026-11-14T21:35:28Z (https://dev.to/maptosite/the-screen-is-not-the-state-verifying-that-a-browser-action-actually-happened-and-recovering-when-326k). It was found by host web search, not by the engine (see recall limits).

Its model: every web action produces three separate facts, almost never established by the same observation.

1. The input reached the element. The click or keystrokes arrived at the intended control, not an overlay, not a different element with the same label, not a field that re-rendered and dropped it.
2. The page changed in response. Something in the DOM moved: a URL, a status line, a disabled button, a row in a list.
3. The effect persisted somewhere the page does not control. A confirmation number, a record in an account, a message in a recipient's inbox, a charge in a ledger.

Fact 1 is the easiest and least interesting. Fact 2 is what most automation treats as success. Fact 3 is the only one that survives closing the tab, and it is usually checked last, or not at all. The article's tool contract: "act, then read what changed, then read the record. If you cannot read the record, say so instead of inferring it."

The failure modes it names, verified without a screenshot for the five listed first, with one exception stated below:

- Optimistic UI. A framework updates state before the server answers. Reading the DOM right after the click tells you what the app hoped would happen.
- Element handles expire. Between the click and the follow-up read, the page re-rendered and every reference points at nothing or at a different node. Recovery is a fresh read of the page before touching it again, not a retry with the old references.
- Same name, different item. Two "Cancel" buttons, one per booking. The defence is to read each control in relation to the surrounding record (whose name, which date, which amount) before acting.
- Overlay interception. A cookie banner or modal covers the target. If the tool reports the element was intercepted by another element, that is the page telling the truth: dismiss the blocker, then re-read.
- Masked screens. When a password, card number or one-time code is on the page, a well-built harness refuses to screenshot. The article says to verify through signals that are not secret: the field's own state after entry (masked length, a "valid" tick, the last four digits where the site shows them), an error region that stayed empty, a button that became enabled, the network-level artefact of the fill itself, and, once submitted, a confirmation page that names the item and amount. If none of those exist, the honest output is "filled, not verified", not "done".
- Input never recorded by the page (the exception). A browser-level dialog, a JavaScript confirm, a native file chooser, a permission prompt, a passkey request, holds focus outside the document, so the page records nothing. The article's rule here is the opposite of screenshot-free: stop and look at the pixels once, because the screenshot is the only view that includes browser-level windows drawn over the page, then answer the window once. Its instrument-the-delta example log also cites screenshot evidence (evidence=shot:order-confirmed.png). So the article is not a blanket "never screenshot" rule; it is "verify without a screenshot wherever the page can answer, and look at the pixels once when only the pixels can".
- Retry from the record, not from the log. External actions persist after the response is lost, so the retry rule is: read the current state before acting again; if the state is ambiguous, do not guess in the direction of action; never treat "already done" as an invitation to do it again. The effect key must be derived from the fact (action plus target plus consequential inputs), not from the run that carries it.
- Instrument the delta, not the intention. Log what was expected to change, what actually changed, and where the record can be re-read later when the screenshot is gone.

Usable for this project: the three-facts split maps directly onto the V12 sent-bubble gate (fact 2, the page changed) and the record read (fact 3, the message in the thread). One qualification: the V12 gate is a single DOM read serving as both facts, fact 2 and fact 3 at once, and a truly independent fact-3 read from the recipient side, outside the page's control, is not part of the benchmark. The "filled, not verified" wording and the fresh-read-before-retry rule are directly adoptable. The masked-screen section is the closest published statement to verifying without any screenshot at all. Note also that the masked-screen signal list includes "whether focus was placed" as a verification signal, which is adjacent to this project's open question about caret and focus checks without answering it as a primary confirmation.

### 2. NEW and usable: observe-act-observe through the accessibility tree, with machine-readable errors (November 2026)

Vercel Labs' agent-desktop (open source, Apache 2.0, Rust CLI and C library) shipped v1.0.0 on 2026-10-28 and v1.0.2 on 2026-10-30, with v1.3.1 released 2026-11-13. It was covered by six independent pieces in the window, all found by host web search. The first five were found by the sweep; the sixth (Raghu Juluri) was missed by the sweep and found only on re-check, see the note after the list.

- itxtayab, DEV Community, November 2026 (https://dev.to/itxtayab/agent-desktop-let-ai-agents-use-your-computers-apps-without-screenshots-20h): the core loop is three commands, observe, act, observe again. "agent-desktop snapshot --app Finder -i", "agent-desktop click @s8f3k2p9:e8", "agent-desktop snapshot --app Finder -i". Refs belong to their snapshot; when the UI changes an action returns STALE_REF or AMBIGUOUS_TARGET. Checked 2026-11-03: 11,728 stars, 796 forks, about 3,800 stars gained in a single day.
- piekwerk, DEV Community, November 2026 (https://dev.to/piekwerk/vercel-agent-desktop-computer-use-for-coding-agents-through-the-accessibility-tree-5fap): v1.0.2, observe-act-observe loop, STALE_REF and AMBIGUOUS_TARGET errors. "Actions are safe to retry because refs stay stable." - gabrielanhaia, DEV Community, November 2026 (https://dev.to/gabrielanhaia/vercels-agent-desktop-lets-coding-agents-click-native-apps-without-moving-your-mouse-38p1): v1.0.2 released 2026-10-30, about 6,900 stars on 2026-11-02. ### 3. CORROBORATION: DOM assertions and failure classification in production browser agents (dated, one outside the window)

"Computer-Use Agent Browser Automation in Production: Action Replay, DOM Assertions, and Human Handoff for Stable Web Tasks", oh-bug.com (https://www.oh-bug.com/posts/computer-use-agent-browser-automation-production/), returned by the engine's web lane. Its page metadata says Published 2026-07-05T23:06:20Z, four months before the window, so it is corroboration only because the date is outside the window, not because the date is unknown. It corroborates the same shape from a production angle: the model proposes a target, the executor maps it to a DOM or accessibility node, checks the element is visible, stable, can receive events, and is enabled, then acts; every action carries an envelope with preconditions and expected_after_action (for example "result table is visible", "network idle or loading spinner disappears"); failures are classified as observation, location, action, assertion, permission, or uncertain side effects, and uncertain side effects get "query result state; do not blindly retry submission". Its Playwright example asserts toBeVisible and toBeEnabled before clicking.

A second engine web item, "Computer Use agent: how it works and how to control it", lite.ego.app (https://lite.ego.app/article/computer-use-agent), is also dated, not undated: its text states "Research scope: September 9, 2026" and "This November 12, 2026 maintenance review read the current vendor tool contract". The November 12, 2026 maintenance review is inside the window, so the piece is in-window evidence by date. Its substance is a general comparison of pixel, DOM, protocol, and API control that argues for state, approvals, evaluation, and evidence, so it corroborates the shape rather than adding a click-verification method.

### 6. ADJACENT but outside the window: the read-act-read loop (2026-10-20)

"Coordinate Clicks Are a Trap: Driving a GUI Agent Without Pixel Guessing", dev.to, published 2026-10-20T22:03:56Z (https://dev.to/galagent/coordinate-clicks-are-a-trap-driving-a-gui-agent-without-pixel-guessing-452i), is 2 days older than the window start (2026-10-22) and is NOT counted as in-window evidence. It is worth one line because it states the loop plainly: read the accessibility tree before you click, move focus with TAB or arrow keys and confirm the focused field by reading the tree again, verify after every action ("did the screen change at all, did the expected text appear, did the node count change"), treat "nothing happened" as an error, and wait for a specific predicate with a timeout. "Your AI Agent Can't See What It Clicks", dev.to, published 2026-10-10T01:06:05Z, 43 days before 2026-11-22, is also outside the window and argues for a second screenshot pass, the opposite approach; it is listed only to mark the contrast.
