### F1 (redteam HIGH, C2-1): check_manifest exemption is dead code. UPHELD, HIGH.

Evidence, first-hand from the code on todolist-push:

- tests/realistic/launch_y13.py:1197 reads `if (not rel_root and _is_entry_pyc_rel(rel)):`.
- tests/realistic/launch_y13.py:295-303, `_is_entry_pyc_rel`, returns False unless rel starts with `__pycache__/`, and returns False when the name after that prefix contains `/`.
- An entry .pyc lives under `__pycache__/`, so in the check_manifest walk rel_root is `"__pycache__"` (truthy) and `not rel_root` is False. The only way `not rel_root` is True is rel_root `""`, where rel cannot start with `__pycache__/` and `_is_entry_pyc_rel` is False. The conjunction can never be True for any input. The exemption is dead code.
- main() order, launch_y13.py:1472-1477, is check_go, check_marker, write_token, check_manifest, _check_entry_pyc, _scan_ship, so check_manifest refuses the entry .pyc before _check_entry_pyc ever runs.
- The module-top scan exemption is different and does work: launch_y13.py:354-355 exempts on `_is_entry_pyc_rel(_rel)` alone. So a legit entry .pyc passes the scan and then refuses at check_manifest. The two layers disagree.
- Live proof (redteam A2L, 7/7 as defined, log logs/a2launcher-run3.log in the redteam work dir): legit entry .pyc by absolute-path py_compile, by relative-path py_compile, legit run_live .pyc, and import run_live then launcher all refuse rc 2 with `[launch_y13] REFUSED: planted bytecode in ship: __pycache__/<stem>.cpython-312.pyc` (the run_codex_y5 stem cases name run_codex_y5.cpython-312.pyc; the run_live case names run_live.cpython-312.pyc), .pyc still on disk, _check_entry_pyc never runs. The isolated function is correct (redteam A2x 8/8, council 2 probe2x, council 3 H8), which bounds the defect to the one condition at :1197.
- The verifier does NOT contradict this: verifier A2h tested _check_entry_pyc in isolation (driver), and A2i tested the module-top scan exemption, not check_manifest. Council 1's claim that "launcher scan + check_manifest exempt top-level entry .pyc" is wrong on the check_manifest half; see Disagreement resolutions.

Fix (exact): in launch_y13.py:1197, drop `not rel_root and`, so the line reads `if _is_entry_pyc_rel(rel): continue`. `_is_entry_pyc_rel` already requires the `__pycache__/` prefix and no subdir, so no wider exemption is created. Then add a launcher-path test that a legitimate entry .pyc for each of the 3 stems is verified and deleted and the run proceeds (redteam A2L cases with expectations flipped to rc 0), and that a forged entry .pyc refuses via the marshal comparison, not via the blanket planted-bytecode refusal. Note the interaction with F5: after this fix, a relative-path py_compile .pyc reaches _check_entry_pyc and refuses there until F5 is also fixed.

It is the round-2 headline fix failing on the live path, not a residual edge: the documented launcher flow cannot proceed with a legitimate entry .pyc, any -m or import probe or py_compile bricks the ship for the launcher until manual deletion, and the marshal adjudication the round was built around never runs on any live path. Fix (exact): in the launcher, build the exec env from os.environ with PYTHONPATH, PYTHONHOME, and PYTHONSTARTUP deleted, not passed through; do the same for the _check_entry_pyc fresh-compile subprocess env. The env scrub and refusal close the child-process channels; the startup channel stays a documented limit.

Severity note: council 2 rated this LOW on threat-model grounds (needs env control, outside the ship-tamper model). This adjudication keeps HIGH. The launcher itself inherits the operator environment and passes it through to the runner, so the threat is a poisoned operator environment, which the fix closes cheaply; and the observed effect is planted code executing in both entry points while the run proceeds normally, which is exactly the class of failure the -P claim was supposed to close. The docstring claim is false as written, and a false safety claim in the code is itself a HIGH defect. Redteam M3 records the HIGH rating as debatable on the same threat-model grounds; the rating stands, and BLOCK stands on F1 regardless.

### F5 (redteam MEDIUM, verifier defect 1, C1-F8): relative-path py_compile .pyc refused by _check_entry_pyc. UPHELD, MEDIUM.

Re-test with the A3h cases (relative-path py_compile self-heals to direct verify rc 0, absolute-path control still passes, forged still refuses). Severity stays MEDIUM: fail-closed with trivial recovery (delete the .pyc), but it breaks the documented self-heal path for the natural relative-path form, and it interacts with F1 (after the F1 fix, the relative-path case moves from refusing at check_manifest to refusing here).
