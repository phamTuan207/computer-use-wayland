## Strongest attacks (summary)

1. **The central finding is inverted.** `remote.prefs.recommended=false` is not a bug the report discovered; it is a deliberate choice, and Mozilla's own docs say the recommended set is "mostly useful for internal Firefox CI suites" and that the user pref file takes precedence. The report cherry-picks about 17 prefs from a claimed 100+ entry set, publishes no inventory of the set, and gives no audit trail for what was excluded and why. The same set contains entries the report itself rejects in section 5 (Safe Browsing off, `resume_from_crash=false`, origin-policy weakening, single-process mode). You cannot cite the set as authority for the picks while disowning it for the rejects without showing the selection rule. No rule is shown.
2. **No local failure is ever cited.** The report never names one crash, hang, unload, dialog block, slow shutdown, oomd kill, or RDD crash observed on this host in R3 prep or A1 runs. Every P0 is justified by a shipped default plus a community issue, never by a reproduced local symptom. Under the repo's own standard (README: "Accuracy is measured, not claimed", "A claim of fixed without a passing live test is worth nothing"), a pref with no local symptom and no local measurement is speculation.
3. **The verification plan is the risk.** P0-1 and P0-2 require deliberate kill -9 crash tests on the frozen daily profile the night before the run. P0-5 requires a 30 s busy loop. P0-7 requires a restart and a re-enable. If any of those verifications fails, there is no time and no stated rollback. A frozen setup means the burden is on the proposer to prove safety without touching the frozen profile; this report proves it by proposing to crash the frozen profile.
4. **No apply mechanism, no revert plan.** The report never states how prefs get set (user.js, about:config on a live profile, enterprise policy), in what order, or how each one is reverted after the run. About:config edits on a running browser can be overwritten at shutdown; prefs.js edits require the browser closed. Most P0/P1 values persist into the owner's daily use (max_resumed_crashes -1, script timeout 0, captive portal off, backup off, testmode on). A proposal with no revert plan is a permanent change smuggled in as a run tweak.
5. **P0-8 and P0-9 contradict each other.** P0-8 removes the in-browser memory safety net (unload off). P0-9 then proposes weakening the external safety net (oomd 50%/20 s to 85%/60 s) that Omarchy deliberately set so a misbehaving app dies instead of the whole Hyprland session. Together they remove both nets and invite exactly the whole-session loss Omarchy's comment warns about (Hyprland SIGBUS mid-memcpy). Neither proposal acknowledges the other.
6. **P0-7 is the profile-mutation trap.** Three of five extensions are unidentified GUIDs, no dedicated automation profile is shown to exist despite the report's own "prefer" language, and no extension is tied to any observed failure. Disabling the daily profile's extensions the night before the run is the single most invasive proposal in the list, presented as if it were a pref flip.
7. **Community evidence is treated as fact where it matters most.** #16718 (single reporter, GTX 1660Ti, open), #16694 (single reporter, open, 2026-11-18), the seria.moe RAM blog, discussion #9087 on the unloader removal, and the post-1.24.3b perf cluster (closed 2026-11-23/24, fixes not in this build) are all second-tier by the report's own grading, yet P0-1, P0-9, and P1-C all depend on them. The report's section 2 also pads the risk picture with issues it then admits are irrelevant (#16714 macOS, #16746 drag-and-drop avoided by CDP, #16706 resize-while-gaming, #16727 fixed after 1.24.3b).
8. **Prompt bias.** The prompt opencode was given demands "Concrete SAFE optimizations worth applying", a P0 apply list, and "find what is MISSING" beyond the in-place list, with no "do nothing / nothing needed" outcome offered. It primes with gh-16587, gh-16624, and bug 2075175, then asks for a P0 list. A prompt that presupposes an apply list will produce one even when the evidence only supports two dialog suppressions. Add the degraded evidence base the report itself admits (websearch 402 for every query, SUMO bot-walled, Reddit empty, Discord unfetchable, no Zen stability docs) and the P0 list is built on the weakest tier of evidence the prompt allowed.
9. **Stale rationales smuggled in as current.** P1-F and P1-G trace to 2015-2018 Marionette/Puppeteer test-harness comments (B2G emulator slowness, multi-window Selenium focus). Bugzilla 1595878, which first collected these prefs, explicitly warns the Remote Agent "should not go out of its way to alter the runtime environment of the user's browser session" outside automation. Applying decade-old CI prefs to a live 55-task benchmark on a real laptop is not "cherry-picking the automation set", it is importing a test harness into production.
10. **The rejected list is mostly right, and that helps the red team.** I agree with rejecting `media.rdd-process.enabled=false`, Safe Browsing off, origin/permission weakening, fission/process-count collapse, and Twilight builds. Two disagreements: (a) the rejection of `dom.min_background_timeout_value=0` as "raises CPU in every background tab" uses logic that should also defer P1-A, which raises CPU the same way; the report is inconsistent with itself. (b) Section 6's "additive" suggestion `app.update.disabledForTesting=true` should have been in the rejected list: it is a test-only pref that duplicates the already-live `app.update.enabled=false`, with no verification and no need. Likewise P1-C smuggles `widget.dmabuf.force-enabled` back in paired form after section 5 rejected it standalone as unvetted for this hybrid host.

## Method note on Zen source

- I fetched Zen 1.24.3b release notes and the Firefox/Mozilla upstream docs via web search (see log above). A direct fetch of `searchfox.org/firefox-main/source/remote/shared/RecommendedPreferences.sys.mjs` returned HTTP 406 from the fetcher, so I did not reproduce the full COMMON_PREFERENCES inventory from source; that gap is stated, not papered over. The report's claim that the file is 23,496 bytes with 100+ entries inside the installed `omni.ja` is therefore not independently confirmed by me, and the council should not treat it as confirmed until someone with laptop access extracts it and publishes a hash plus the full entry list.
- Zen's own repo (zen-browser/desktop, tag 1.24.3b) carries Zen UI and patches, not the upstream Firefox `firefox.js` defaults or `RecommendedPreferences.sys.mjs`, which live in mozilla-central / the shipped omni.ja. Line-number citations to `defaults/preferences/firefox.js` are upstream-Firefox lines, not Zen-specific lines, and Zen may override defaults in its own pref files; the report never checks Zen's own overrides. That is a hole in every "LOCAL-VERIFIED line N" citation in the report.
