## Lens and bar

Speed/benefit only. A proposal gets APPLY only if it shows a concrete, measurable benefit to the run: it avoids a hard stop, removes a measured stall, or stops a slow drift. Change for its own sake gets REJECT or DEFER.

Framing the whole list: the honest run range is 19-31 hours and the biggest serial cost is coordinator work, not the browser. No browser pref saves hours. The real currency here is different: a modal dialog nobody can dismiss, a crash loop that ends in a locked profile, a whole-browser SIGKILL, or seconds of stall on every background-tab command under load. Those are worth voting for even when they save zero minutes in the happy path, because in the unhappy path they cost a task or the run. Speculative tuning with no measured symptom and no failure mode it prevents gets DEFER, not APPLY.

Two findings that shape most votes:

1. The central finding stands. `remote.prefs.recommended=false` does skip Gecko's RecommendedPreferences set. Firefox Source Docs confirm the set exists, is applied when remote protocols start, and that a user pref takes precedence over it. Cherry-picking the safe entries by hand is the right response, not flipping `recommended` back to true, because flipping it true would also apply the security-weakening entries the report correctly rejects (Safe Browsing off, origin-policy off, and others).
2. Bug 1960734 (fixed, Firefox 139) disabled the process-priority/QoS manager for Remote Protocols, and bug 1963001 measured why: under CPU saturation, background-tab `NewWindow` commands took 13-266 ms with the manager off versus 1.3 s, 5.1 s and 4.6 s hangs with it on, and a 20-tab test took 7.0 s total versus 29.7 s. That fix was delivered through the recommended-prefs path, so with `recommended=false` this run has lost it. That single fact is the strongest speed evidence in the whole report, and it makes P1-A the highest-value speed item.

## Per-proposal votes

| Proposal | Vote | Reason | Evidence |

| P0-1 `toolkit.startup.max_resumed_crashes` to -1 | APPLY | Hard-stop avoidance. Default is 3; after 3 unclean startups the browser takes the safe-mode path, and open Zen issue 16694 says safe mode never opens a window on Linux/Wayland and keeps the profile lock. A crash loop then becomes a permanent hang the watchdog cannot restart out of. Cost is zero. Benefit is not speed in the happy path, it is that the run cannot die this way. | Report section 4 P0-1, shipped default 3 (firefox.js line 860, as reported); issue 16694 confirmed open, filed 2026-11-18, via GitHub issues search |

The report is right to keep `resume_from_crash=true` and not copy Mozilla's `false`. | Report section 4 P0-2, shipped default 1; MozillaWiki session restore page confirms default 1 for `max_resumed_crashes` and default true for `resume_from_crash` |
| P0-3 `browser.warnOnQuit` to false | APPLY | Removes a modal dialog no automation client can dismiss on any quit path (CDP close, Marionette quit, wrapper script). | P0-5 `dom.max_script_run_time` to 0 and `dom.max_chrome_script_run_time` to 0 | APPLY, with a backstop | Removes an unanswerable dialog. Setting 0 trades that for a script that can burn CPU indefinitely, so the coordinator's own command timeouts and tab-kill path must stay the backstop. A hung script with a coordinator timeout is recoverable; a modal dialog is not. Removing a proxy from the network path is a measurable latency removal, unlike most items here. Condition: do it on a dedicated automation profile, not by mutating the daily profile, and identify the three unidentified XPIs first (report truncates their IDs). If one of them is needed by a task, keep only that one deliberately. | Report section 4 P0-7, extension list as reported from the live profile; not re-verified from this VM |
| P0-8 Confirm `browser.tabs.unloadOnLowMemory` is false, leave it false | APPLY, as verify-and-pin, not a change | Prevents silent tab discard, which forces a full page reload plus state rebuild, minutes per incident and a possible task failure. Cost is memory growth, mitigated by 32 GB, A1 hygiene, and P0-9. Agree D4 becomes unnecessary, which removes a variable. | Report section 4 P0-8, line 372 as reported; Firefox Source Docs Tab Unloading; Mozilla Connect developer comment on the Linux default; independent search confirms true on macOS/Windows, false on Linux |

Condition: verify first (`systemctl show systemd-oomd`, `systemctl show user.slice`, journal for killed zen-bin), change only for the run session (85 percent / 60 s as proposed), and revert after. Do not permanently change the Omarchy default without the owner's decision. Not live-verified from this VM. | Report section 4 P0-9, `/etc/systemd/oomd.conf.d/10-omarchy.conf` as reported; not re-verified from this VM |

## P2 verdict

Agree with skipping all four as stated, with one conditional flip.

- P2-A `browser.translations.enable` to false: agree DEFER. Benefit exists only if a task hits a foreign-language page and triggers a multi-hundred-MB model download. No R3-L3 task is known to do that. Conditional flip: if any task's target page is non-English, this becomes APPLY before that task, since the download would cost minutes and the pref costs nothing.
- P2-B idle-animation surface (`toolkit.cosmeticAnimations.enabled` to false): agree DEFER. The post-1.24.3b perf cluster is code-side, not pref-side, and idle CPU cost is unmeasured. Revisit only if idle CPU is measurably non-zero.
- P2-C `dom.ipc.reportProcessHangs` to false: agree SKIP. It only suppresses hang telemetry, with no behavioural gain on a release build. No speed benefit at all.
- P2-D `browser.tabs.remote.unloadDelayMs` to 0: agree SKIP. Irrelevant while P0-8 keeps the unloader off.

## Summary

- P0: 9 APPLY, 0 REJECT, 0 DEFER. All nine are hard-stop or silent-loss avoidance with zero or near-zero cost. P0-1, P0-2, P0-3 and P0-4 are the core: they stop the run dying from a crash loop, a lost session, or an unanswerable dialog. P0-7 (extensions, proxy removal) and P0-9 (oomd) are the other two that prevent an external killer.
- P1: 5 APPLY (A, B, D, F, H), 0 REJECT, 3 DEFER (C, E, G). P1-A is the strongest speed item in the entire list, with the only real measurement behind it (bug 1963001: seconds per background-tab command under load). P1-B and P1-D and P1-F are weak APPLYs: small, cheap, and honest about being small. P1-C is correctly conditional, P1-E and P1-G are speculation without a symptom.
- P2: agree skip all four, with P2-A flipping to APPLY if any task target is non-English.
- Rejected list: agree with all 11 rejections, with the strongest agreement on the single-process items and on `remote.active-protocols`, which I verified dead in Firefox 141.
- Totals across P0/P1: 14 APPLY, 0 REJECT, 3 DEFER.
- Honest accounting: nothing here saves hours. The quantifiable saving is seconds at the D1 restart (P0-6), seconds per background-tab command under load (P1-A, the only item that can add up to real minutes across 55 tasks), and the avoidance of multi-minute stalls: a locked profile (P0-1), a lost session (P0-2), a hung quit (P0-3), a portal tab hijack (P1-H), an oomd kill (P0-9), or a proxy in the network path (P0-7). Judge the list on those avoided stalls, not on the headline run time.

Apply on a dedicated automation profile where the report says profile, not the daily one.
